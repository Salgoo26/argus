# Argus

개인정보처리시스템의 접속기록을 모아 이상 행위를 자동으로 찾고, 취급자의 소명을 업무 근거와 함께 받아 점검 보고까지 잇는 접속기록 점검 시스템

## 1. 왜 만들었나

정보보호 담당자로 일하며 개인정보처리시스템의 접속기록을 매월 점검했습니다. 그때 겪은 불편을 기능으로 옮겼습니다.

| 실무에서 겪은 일 | Argus |
|---|---|
| 월 단위 점검이라 몇 주 지난 행위를 소명받았고, 취급자는 무엇을 조회했는지 기억하지 못했다 | 탐지 배치가 5분마다 돌아 행위 직후 탐지하고 소명을 자동으로 요청한다. 소명 화면에 해당 접속기록이 함께 보인다 |
| 야간 접속·접속량 급증 같은 기준을 보고서를 보며 하나하나 대조했다 | 룰 기반 자동 탐지. 담당자가 화면에서 룰을 만들고 고치며, 변경 이력이 남는다 |
| 소명은 기억에 의존한 글뿐이라 확인할 방법이 없었다 | 소명에 근거 첨부(결재 문서·요청 메일)와 관련 업무 티켓을 붙이고, 담당자가 승인·반려·재요청한다 |
| 기록을 메일로 보내고, 사유를 모으고, 결재 문서에 다시 옮겨 적었다 | 탐지·소명·판정이 한 화면에서 이어지고, 점검 보고서에 취급자·룰·건수·소명 요지가 함께 실린다 |
| 소명 미제출자에게 일일이 연락했다 | 소명 기한(7일)과 임박·초과 알림, 접속 중 화면 알림과 웹 푸시 |
| 화면 경유 기록과 DB 직접 접근 기록을 따로 점검하고 따로 보고했다 | 두 경로를 한 원장에 모으되, 탐지·소명·보고서는 경로별로 나눈다 |

왜 자동화인가. 민간 기업은 수동 점검도 적법합니다(안전성 확보조치 기준 §8②). 접속기록을 자동화된 방식으로 분석해 탐지하고 소명받는 조치는 공공시스템에만 의무입니다(§17). Argus는 민간 의무(§8)를 기본으로 충족하면서, 공공시스템 기준(§17)의 탐지 방식과 누락 사례까지 참고해 민간 조직도 같은 수준의 점검을 할 수 있게 하는 것을 목표로 합니다.

## 4. 개인정보 보호 설계

Argus의 접속기록에는 처리한 정보주체가 들어가므로 Argus 자신도 개인정보처리시스템입니다. 세 가지 원칙을 지켰습니다.

1. 감시 시스템이 또 하나의 개인정보 저장소가 되지 않게 한다. 플랫폼은 회원 내부 번호만 보내고, 검색 조건은 값 없이 키 이름만, SQL 원문은 게이트웨이에만 둔다. 화면과 보고서의 정보주체는 기본 마스킹(`member_10***`)이다. 실측에서 원장 731건 전체에 이메일·전화번호 형태의 값이 0건이었다
2. 기록할 수 없으면 내보내지 않는다. 접속기록을 남기지 못하면 화면 경유는 응답을, DB 직접은 쿼리 결과를 막는다. CSV 같은 개인정보가 기록 없이 나가는 경로를 없애기 위해서다
3. 감시받는 쪽이 기록을 고칠 수 없다. 플랫폼과 Argus의 DB를 완전히 분리하고, 원장은 추가만 가능하며 해시체인으로 이어진다

감시 대상 쇼핑몰도 최소 수집으로 만들었습니다. 생년월일·성별은 받지 않고, 카드번호는 결제창 안에서만 입력되어 쇼핑몰 서버에 오지 않으며, 환불계좌는 암호화해 저장합니다. 탈퇴하면 즉시 파기하고 법정 보존분만 분리 보관합니다.

## 6. 판단이 필요했던 지점

DB 직접 접근의 "처리한 정보주체". DB 툴로 조회하면 누구의 정보를 봤는지 화면처럼 알 수 없습니다. 안내서는 대량 처리 시 검색 조건문을 정보주체 정보로 기록할 수 있되, 해당 시점 백업 등 책임 추적 조치를 함께 요구합니다(93쪽). 그래서 SQL을 해석하지 않고, PostgreSQL이 결과와 함께 주는 열 정보(테이블 OID·열 번호)로 회원 식별 열을 찾아 그 값만 기록하게 했습니다. 결과에 회원 식별 열이 없는 쿼리는 정규화 SQL과 원문 지문으로 남기고, 시점 백업이 없으므로 이 부분은 부분 충족으로 판정했습니다.

소명은 자동으로 요청한다. 담당자가 모든 탐지건을 먼저 보고 요청하면 병목이 생기고 방치됩니다. 사람의 판단을 "요청할지"가 아니라 "받아들일지"에 쓰도록 했고, 오탐은 담당자가 사유를 적고 요청을 취소합니다.

탐지 알림은 심각도 상만 보낸다. 모든 탐지를 알리면 담당자가 알림을 무시하게 됩니다. 중·하는 목록과 기한 관리로 다룹니다.

웹 푸시는 라이브러리 없이 구현했다. 표준(RFC 8291·8292)을 이미 쓰고 있던 암호 라이브러리로 직접 구현해 새 의존성을 늘리지 않았고, 테스트에서 받는 쪽 입장으로 복호화해 정확성을 확인했습니다. 푸시 내용에는 종류·심각도·탐지건 번호만 담아 개인정보가 브라우저 푸시 서버를 거치지 않게 했습니다.

## 7. 알려진 한계와 다음 버전

| 한계 | 계획 |
|---|---|
| 화면 경유 기록의 임시 버퍼가 플랫폼 DB 안에 있고, DB 게이트웨이의 공용 계정이 DB 소유자 권한이라 전송 전 기록을 지울 수 있는 위치다 | 버퍼를 플랫폼 DB 밖으로 옮기고 공용 계정 권한을 분리 |
| 원장 트리거는 DB 소유자·슈퍼유저가 끌 수 있다. 보고서 기준점을 출력해 결재 문서에 붙이는 운영을 전제로 한다 | 외부 기준점 보관(WORM 저장소 등) |
| 보관 기간이 지난 접속기록을 지우는 파기 배치가 없다(지금은 무기한 보관) | 파기 전용 경로와 함께 구현 |
| DB 직접 접근의 시점 백업이 없어 검색 조건문 기록은 부분 충족 | 시점 복구(PITR)와 재현 절차 |
| 보호 대상 등록부의 관리 화면(미분류 컬럼 표시 포함)과 Argus 계정 관리 화면을 아직 공개하지 않았다. 판정은 테이블 단위이고, 화면 경유 기록의 데이터 유형은 코드의 기록 표시로 따로 관리된다 | 관리 화면 공개, 컬럼 단위 판정, 자동 식별, 화면 기록도 등록부를 따르게 |
| 존재하지 않는 아이디의 로그인 실패는 기록하지 않는다(행위자를 특정할 수 없음) | 접속지 기준 집계로 대응 검토 |
| 공휴일 달력이 없어 업무시간 외 판정은 야간·주말만 | 공휴일 반영 |
| DB 접속 토큰은 접속할 때만 재직·잠금을 확인한다. 이미 열린 연결은 말소 뒤에도 만료(최대 1시간)까지 유지되고, 역할이 바뀌어도 발급된 토큰은 쓸 수 있다 | 말소·역할 변경 시 토큰 폐기와 연결 종료 |

## 8. 구조

<!-- 아키텍처 그림 한 장 (docs/images/architecture.png) -->

| 구성 | 역할 |
|---|---|
| platform-web · platform-api | 감시 대상 쇼핑몰. 고객 화면(`/`)과 관리자 화면(`/admin`) |
| platform-relay | 플랫폼의 접속기록을 Argus로 전송(HMAC 서명, 재시도, 중복 제거) |
| db-gateway | DB 툴 접속을 중계하며 실사용자 기준으로 기록(TLS 필수, 1시간 접속 토큰) |
| argus-api · argus-worker · argus-web | 수집 API, 원장, 탐지 배치·알림, 담당자·취급자 화면 |
| platform-db · argus-db | 두 DB는 네트워크까지 분리 |

## 9. 실행

```bash
git clone https://github.com/Salgoo26/argus.git && cd argus
bash scripts/init-env.sh          # .env 생성(무작위 비밀값)
docker compose up -d --build      # 플랫폼 http://localhost:3000 · Argus http://localhost:3001
bash scripts/e2e.sh               # 전체 시나리오 자동 검증
```

계정 준비, 시연 순서, DB 툴 접속 방법은 [실행 안내](docs/run.md)에 있습니다.

## 10. 만든 방식

문제 정의 → 요구사항·정책 → 아키텍처·API·DB 설계 → 구현 → 자체 점검 → 조치 순서로 진행했고, 단계마다 설계 문서에 결정과 기각한 대안을 남겼습니다. 구현은 AI 코딩 도구로 했습니다. 문제 정의, 법령 해석, 설계 결정, 구현 결과 검수와 점검 판정은 직접 했습니다. 모든 변경은 PR과 CI(테스트·린트·E2E·보안 검사)를 거쳐 반영했습니다.
