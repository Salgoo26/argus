## 1. 시스템 구성

| | 시스템 | 역할 | 구현 수준 |
|---|---|---|---|
| **플랫폼** | 커머스 플랫폼 (+간단 결제) | 감시 대상 개인정보처리시스템. 단일 앱이되 계정 유형(사용자/관리자)에 따라 UI 분기 | 최소구현 (무대장치) |
| **Argus** | 접속기록 점검 서비스 | 플랫폼의 접속기록을 수집·탐지·소명관리·보고 | **메인 산출물, 전체 구현** |

- 두 시스템은 **분리**. Argus는 플랫폼으로부터 API로 접속기록을 전송받는다.
- **포지셔닝**: 상용 솔루션 컨셉(인포세이퍼·유비세이퍼PSM 등과 동일 포지션). 단 **MVP는 단일 고객사(테넌트 1개) 기준으로 구현**하고, 멀티테넌시는 확장 포인트로만 남긴다.

### 1-1. 플랫폼 도메인 선정 경위 (2026-09-15)

정보보호/개인정보보호 채용 수요는 금융권이 압도적(수집된 58개 채용 기업 중 약 42%)이며, 법적 깊이 측면에서도 금융·보험이 유리하다(민감정보·고유식별정보 처리 → §8① 접속기록 2년 보관, §7② 암호화 의무). 보험 비교·중개 모델이 복잡도 대비 이점이 크다고 보아 후보로 검토했다.

**그럼에도 커머스를 선택한 이유**: 이 프로젝트의 메인 산출물은 Argus이고 플랫폼은 무대장치다. 무대장치 선정에 시간을 쓰는 것은 1차 시도의 실패 패턴(도메인 고민으로 스코프 확대)을 반복할 위험이 있다. 구현이 가장 빠른 커머스로 진행하고, 다른 도메인으로의 교체 여부는 필요해지는 시점에 판단한다(현 시점에서 교체를 전제한 추상화 설계는 하지 않음).

### 1-2. 점검 대상 접근 경로 범위 (2026-09-23)

**개인정보처리시스템의 범위** (개인정보위 「안전성 확보조치 기준 안내서」 2024.10):
- 데이터베이스를 구성·운영하는 시스템 그 자체 (DBMS)
- DB의 개인정보를 처리할 수 있도록 구성한 **응용프로그램** (Web서버, WAS 등 = 백오피스)
- 개인정보 처리를 위해 구성된 파일처리시스템 (FTP서버, 백업서버 등)

§8①의 "개인정보처리시스템에 접속한 자"는 DB 직접 접속자와 응용프로그램 사용자를 구분하지 않으므로, **법적으로는 두 경로 모두 접속기록 보관·점검 의무 대상**이다.

**실무·시장에서의 구분**:

| | DB 직접 접근 | 응용프로그램 경유 |
|---|---|---|
| 구조 | 2티어 — 쿼리툴로 DB 직접 접속 | 3티어 — 웹 → WAS → DB |
| 접근 주체 | DBA·개발자 등 소수 | CS·운영 등 다수 취급자 |
| 로그 원천 | DB 쿼리 로그·감사 로그 | WAS 에이전트, 네트워크 미러링, 애플리케이션 로그 |
| 대표 솔루션 | DB 접근제어 (DBSAFER 등) | 접속기록 관리 (UBI SAFER-PSM, 스파이스웨어 원 등) |
| ISMS-P 인증기준 | 2.6.4 데이터베이스 접근 | 2.6.3 응용프로그램 접근 |
| 정상 기준선 | 운영 DB 개인정보 조회의 업무 필요가 원래 드묾 → **조회 사실 자체**가 점검 대상에 가까움 | 조회가 일상 업무 → **양·시간·패턴의 이상치**가 점검 대상 |
| "처리한 정보주체" 추출 | 어려움 (SQL 텍스트·결과 건수만 남음) | 쉬움 (애플리케이션이 회원 ID를 직접 기록) |

**결정: 두 경로 모두 Argus의 점검 대상으로 설계하되, 구현은 단계적으로 진행한다.**

| 단계 | 범위 | 비고 |
|---|---|---|
| **1단계 (MVP)** | **응용프로그램(백오피스) 경유 접근** | Walking Skeleton 포함 전체 MVP 기능 |
| **2단계 (여유 시)** | **DB 직접 접근** | 1단계 완료 후 착수 여부 판단 |

**1단계부터 설계에 반영하는 것 (최소)**:
- 접속기록 수집 스키마에 **`접근 경로` 필드(APP / DB)**를 둔다. 1단계에는 APP 값만 수집된다.
- 탐지 룰의 조건식에서 **접근 경로로 필터**할 수 있게 한다. (두 경로는 정상 기준선이 반대이므로 룰을 경로별로 달리 적용해야 하기 때문)

**2단계에서 추가하는 것**:
- DB 감사 로그 수집기 (예: PostgreSQL `pgaudit` 로그 파싱 → Argus 전송)
- DB용 부가 필드: 실행 쿼리문, 결과 건수
- DB 전용 탐지 룰: 개인정보 테이블 SELECT, WHERE 없는 전체 조회, 결제수단 테이블 접근, 개인정보 테이블 DML(UPDATE/DELETE) 등
- 액터 추가: DBA·개발자
- "처리한 정보주체 정보" 추출 방식 (SQL 결과셋에서 정보주체를 특정하는 문제 — 설계 시 별도 검토)

**의의**: 시장에서는 DB 접근제어와 접속기록 관리가 별도 제품으로 나뉘어 있다. Argus가 2단계까지 가면 두 경로를 한 화면에서 점검하는 구조가 되며, Argus의 탐지·소명·보고 코어는 §2 3호 규격으로 정규화되어 있어 경로와 무관하게 재사용된다. 또한 본인 실무 경험의 본체가 DB 직접 접근 점검이었다는 점에서, 2단계는 경험 기반 서사를 완성하는 의미도 갖는다.

## 2. 법적 근거 — 이 서비스가 존재하는 이유

| 조문 | 내용 | 우리 기능과의 대응 |
|---|---|---|
| 안전조치기준 §2 1호 | **개인정보처리시스템 정의**: 데이터베이스시스템 등 개인정보를 처리할 수 있도록 체계적으로 구성한 시스템 (안내서상 DB·응용프로그램·파일처리시스템 포함) | 1-2절 접근 경로 범위 판단의 근거 |
| 안전조치기준 §2 3호 | **접속기록 정의**: 식별자, 접속일시, 접속지 정보, 처리한 정보주체 정보, 수행업무 등 | 접속기록 데이터 스펙 그 자체 (3절) |
| 안전조치기준 §8① | 접속기록 **1년 이상** 보관(5만명 이상·고유식별정보·민감정보 처리 시 2년). **단서: 정보주체는 제외** | LOG-01 보관 정책 / 로깅 지점 한정 |
| 안전조치기준 §8② | 접속기록 및 **개인정보 다운로드 상황을 확인·점검**하는 **주기·방법·사후조치절차를 내부 관리계획으로 정하고 이행** | **서비스 전체의 존재 근거**. 점검 주기를 Argus 설정값으로 두는 근거 (아래 주석) |
| 안전조치기준 §8③ | 접속기록의 **위·변조 및 도난·분실 방지** 조치 | 로그 무결성 (비기능) |
| 안전조치기준 §6①2호 | 접속 IP 등을 **분석하여 유출 시도 탐지 및 대응** | LOG-03 이상행위 탐지 |
| **안전조치기준 §17①** | **공공시스템 접속기록 등을 자동화된 방식으로 분석하여 불법적인 유출 및 오용·남용 시도를 탐지하고 그 사유를 소명하도록 하는 등 필요한 조치** | **LOG-03 탐지 + LOG-06~08 소명 — 핵심 2기능이 그대로 명문화된 조항** |
| 안전조치기준 §5③ | 접근 권한 부여·변경·말소 내역 **3년** 보관 | PLT-14 |
| 안전조치기준 §7②5·6호 | **신용카드번호·계좌번호 암호화 저장** | PLT-05 결제수단 정보 |
| 안전조치기준 §12① | 개인정보 출력 시 **용도 특정**, 출력 항목 최소화 | PLT-13 다운로드 감시 / **LOG-10 마스킹 해제 사유 입력** |
| PIPA §2 1호 나목 | 다른 정보와 **쉽게 결합**하여 알아볼 수 있는 것도 개인정보 | LOG-10 내부 식별자 마스킹의 근거 |

> **§8② 문구 변경 주석 (2026-09-23 확인)**: 2024.10 안내서에는 접속기록을 **"월 1회 이상 점검"**하고 다운로드 확인 시 사유를 반드시 확인하도록 되어 있다. 반면 본 프로젝트가 참조하는 **2026.7.1 고시(제2026-9호) §8② 원문에는 "월 1회" 문구가 없으며**, 점검 주기·방법·사후조치절차를 내부 관리계획으로 정하도록 조직 자율에 위임하고 있다. 개정 경위는 확인하지 못했다. Argus에서는 점검 주기를 고정값이 아닌 **설정값**으로 두는 근거로 활용한다.

### 핵심 포지셔닝 (§17① 발견의 함의)

**민간에는 접속기록 점검의 "자동화" 의무가 없다.** §8②는 점검 주기·방법을 내부 관리계획으로 정하라고만 할 뿐, 수동 점검도 적법하다. 반면 **공공시스템운영기관에는 §17①이 "자동화된 분석 → 탐지 → 소명 요구"를 법정 의무로 명시**한다.

→ Argus의 포지셔닝은 **"공공시스템에만 의무화된 수준의 조치를, 민간 개인정보처리자도 이행할 수 있게 하는 도구"**다. 법정 최소기준(수동 점검)을 상회하는 자율적 조치이며, 동시에 §17①이라는 명확한 기능 명세 레퍼런스를 갖는다. 공공시스템 지정 기준(§14: 100만명 이상 / 취급자 200명 이상 등)에 미달하는 조직이 1차 타겟.

## 3. 접속기록 데이터 스펙

| 필드 | 설명 | 예시 | 구분 |
|---|---|---|---|
| 식별자 | 접속한 개인정보취급자 계정 | `cs_kim` | §2 3호 필수 |
| 접속일시 | 행위 발생 시각 | `2026-09-15 23:41:07` | §2 3호 필수 |
| 접속지 정보 | 접속 IP 등 | `10.20.3.55` | §2 3호 필수 |
| 처리한 정보주체 정보 | 조회·처리 대상 회원 **내부 식별자(PK)** 또는 건수 | `member_10293` (표시 표기 — 저장·전송 표기는 [[DB스키마.md]] 2-1절) | §2 3호 필수 |
| 수행업무 | `LOGIN` / `READ` / `UPDATE` / `DOWNLOAD` / `EXPORT` / `UNMASK` 등 | `DOWNLOAD` | §2 3호 필수 |
| **접근 경로** | `APP`(응용프로그램 경유) / `DB`(DB 직접 접근) | `APP` | **Argus 확장 필드** — 1단계는 APP만 수집 |

> **자기참조 구조**: "처리한 정보주체 정보"가 포함되므로 **접속기록 자체가 개인정보**이며, 따라서 **Argus도 개인정보처리시스템에 해당**한다. Argus 자신의 접속기록도 §8 대상이 된다. 상세는 [[액터별_플로우.md]] 9절.

### 4-2. 관리자 UI (= 1단계 감시 대상 행위가 발생하는 곳)

> 1단계에서는 **이 관리자 UI를 경유한 접근**을 로깅·점검한다. 플랫폼 DB에 대한 직접 접근은 2단계에서 다룬다(1-2절).

| ID | 기능 | 설명 | 우선순위 | 비고 |
|---|---|---|---|---|

### 4-3. 시드 데이터

- 회원 데이터 수백~수천 건 (탐지 룰의 "대량 조회/다운로드"가 성립할 규모)
- 상품·주문·결제 데이터
- 1:1 문의 데이터 (일부는 취급자 조회와 매칭되고, 일부는 매칭되지 않도록 설계 — 연동 대조 시연용)
- 취급자 계정 3~5개 (CS팀 / 마케팅팀 / 운영팀 등 소속 구분)
- 과거 접속기록 (baseline 비교, "전월 대비 증가율" 룰이 동작하려면 필요)
