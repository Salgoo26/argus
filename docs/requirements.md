## 1. 시스템 구성

| | 시스템 | 역할 | 구현 수준 |
|---|---|---|---|
| **플랫폼** | 커머스 플랫폼 (+간단 결제) | 감시 대상 개인정보처리시스템. 단일 앱이며 고객 화면과 관리자 화면은 URL 경로로 구분(`platform-web/app/(shop)` 고객, `app/admin` 관리자) | 최소 구현 (감시 대상 시스템) |
| **Argus** | 접속기록 점검 서비스 | 플랫폼의 접속기록을 수집·탐지·소명관리·보고 | **전체 구현** |

- 두 시스템은 **분리**. Argus는 플랫폼으로부터 API로 접속기록을 전송받는다.
- **포지셔닝**: 상용 접속기록 관리 솔루션(인포세이퍼·유비세이퍼PSM 등)과 같은 위치의 서비스로 설계한다. 다만 **MVP는 단일 고객사(테넌트 1개) 기준으로 구현**하고, 멀티테넌시는 확장 포인트로만 남긴다.

### 1-1. 플랫폼 도메인 선정

감시 대상 시스템으로 커머스를 골랐다. 회원가입·동의, 주문·결제(결제수단 암호화), 배송지, 1:1 문의, 탈퇴·파기까지 개인정보 처리 흐름이 다양하고 구현 범위가 명확하다. 이 프로젝트의 중심은 Argus이므로 플랫폼은 접속기록이 발생하는 관리자 업무를 갖춘 최소 구현으로 둔다. 다른 도메인으로의 교체 여부는 필요해지는 시점에 판단하며, 교체를 전제한 추상화 설계는 하지 않는다.

- 기각: 보험 비교·중개 플랫폼 — 민감정보·고유식별정보를 처리해 법적 요건(§8① 접속기록 2년 보관, §7② 암호화 의무)은 더 풍부하지만, 감시 대상 시스템의 구현 범위가 커진다.

### 1-2. 점검 대상 접근 경로 범위

**개인정보처리시스템의 범위** (개인정보위 「안전성 확보조치 기준 안내서」 2024.10):
- 데이터베이스를 구성·운영하는 시스템 그 자체 (DBMS)
- DB의 개인정보를 처리할 수 있도록 구성한 **응용프로그램** (Web서버, WAS 등 = 백오피스)
- 개인정보 처리를 위해 구성된 파일처리시스템 (FTP서버, 백업서버 등)

§8①의 "개인정보처리시스템에 접속한 자"는 DB 직접 접속자와 응용프로그램 사용자를 구분하지 않으므로, **법적으로는 두 경로 모두 접속기록 보관·점검 의무 대상**이다.

**실무·시장에서의 구분**:

| | DB 직접 접근 | 응용프로그램 경유 |
|---|---|---|
| 구조 | 2티어 — 쿼리툴로 DB 직접 접속 | 3티어 — 웹 → WAS → DB |
| 접근 주체 | DBA·개발자 등 소수 | CS·운영 등 다수 취급자 |
| 로그 원천 | DB 쿼리 로그·감사 로그 | WAS 에이전트, 네트워크 미러링, 애플리케이션 로그 |
| 대표 솔루션 | DB 접근제어 (DBSAFER 등) | 접속기록 관리 (UBI SAFER-PSM, 스파이스웨어 원 등) |
| ISMS-P 인증기준 | 2.6.4 데이터베이스 접근 | 2.6.3 응용프로그램 접근 |
| 정상 기준선 | 운영 DB 개인정보 조회의 업무 필요가 원래 드묾 → **조회 사실 자체**가 점검 대상에 가까움 | 조회가 일상 업무 → **양·시간·패턴의 이상치**가 점검 대상 |
| "처리한 정보주체" 추출 | 어려움 (SQL 텍스트·결과 건수만 남음) | 쉬움 (애플리케이션이 회원 ID를 직접 기록) |

**결정: 두 경로 모두 Argus의 점검 대상으로 설계하되, 구현은 단계적으로 진행한다.**

| 단계 | 범위 | 비고 |
|---|---|---|
| **1단계 (MVP)** | **응용프로그램(백오피스) 경유 접근** | Walking Skeleton 포함 전체 MVP 기능 |
| **2단계** | **DB 직접 접근** | 1단계 완료 후 착수 (아래 "2단계에서 추가하는 것") |

**1단계부터 설계에 반영하는 것 (최소)**:
- 접속기록 수집 스키마에 **`접근 경로` 필드(APP / DB)**를 둔다. 1단계에는 APP 값만 수집된다.
- 탐지 룰의 조건식에서 **접근 경로로 필터**할 수 있게 한다. (두 경로는 정상 기준선이 반대이므로 룰을 경로별로 달리 적용해야 하기 때문)

**2단계에서 추가하는 것** (v0.1에 포함, 상세는 [아키텍처_설계서](architecture.md) 3-4):
- **DB 접근 게이트웨이(프록시형)**: DB 툴은 게이트웨이로만 접속하고, 게이트웨이가 공용 계정으로 DB에 중계하면서 SQL·결과를 가로채 기록하고 Argus로 전송한다.
  - 기각: DB 감사 로그 수집기(pgaudit 로그 파싱) — 공용 계정 뒤의 실사용자와 조회 결과의 정보주체를 알 수 없다.
- **DB 접속 토큰**: 플랫폼 관리자 화면에서 발급(1시간, 사유 입력 없음)하고 DB 툴 비밀번호로 사용한다. 실사용자 = 플랫폼 관리자 아이디(3티어와 같은 아이디라 별도 매핑 불필요)
- DB용 부가 필드: DB 계정, **정규화 SQL**(리터럴 치환), 테이블·컬럼, 결과 건수, 원문 참조·지문. **SQL 원문·매개변수는 게이트웨이 저장소에만**(Argus 미보유)
- "처리한 정보주체 정보": **조회 결과에서 회원번호 추출**. 게이트웨이는 SQL을 해석하지 않고, PostgreSQL 응답의 열 정보(테이블 OID·열 번호)로 회원을 가리키는 열을 찾아 결과 행에서 그 값만 읽는다. 회원 열이 없는 조회, 식·함수 결과, 변경 문장(UPDATE 등)·COPY는 "정보주체 미특정" + 건수 + 원문 참조로 남기며, 원문 SQL(검색조건문) 기록으로 갈음하는 해석이다(안내서 2024.10 90쪽). 조회 결과 값은 어디에도 저장하지 않는다. 미특정 처리의 책임추적성 조치(시점 복구 백업으로 재현)는 v0.2 — [아키텍처_설계서](architecture.md) 3-4 "정보주체 기록 방식"
- 데이터 유형 판정: 어느 테이블이 어떤 데이터 유형인지, 어느 열이 회원 식별 열인지는 Argus의 **보호 대상 등록부**가 정한다([정책정의서](policy.md) 1-6)
- DB 전용 탐지 룰 ([정책정의서](policy.md) 1-3 "2단계 룰") — 기본 3개(야간·주말·전월 대비 급증), 나머지는 담당자가 룰 빌더로
- 액터 추가: DBA·개발자 (플랫폼 관리자 계정을 가진 사람이 토큰으로 접속)
- **v0.2 이월**: 명령어 통제(범위별 사전 결재·범위 밖 거부), 권한 그룹·DB 롤 분리, Agent 방식 인증, 미특정 처리의 정보주체 기록(시점 복구 재현), 사고 조사(재현) 체계(시점 복구 백업·재현 도구·백업 보관 기간과 파기 정책의 관계)
- **경로 구분**: Argus는 담당자·취급자 모두에게 기록이 화면 경유(3티어)인지 DB 직접(2티어)인지 구분해 보여 준다(접속기록·탐지건·소명·보고서 전부). 두 경로는 성격이 다른 기록이고 실무에서도 보고를 따로 하므로, **탐지 기준·소명 작성 기준·보고를 경로별로 분리**한다([정책정의서](policy.md) 1-5·3-3)

**의의**: 시장에서는 DB 접근제어와 접속기록 관리가 별도 제품으로 나뉘어 있다. Argus가 2단계까지 가면 두 경로를 한 화면에서 점검하는 구조가 되며, Argus의 탐지·소명·보고 코어는 §2 3호 규격으로 정규화되어 있어 경로와 무관하게 재사용된다.

## 2. 법적 근거 — 이 서비스가 존재하는 이유

| 조문 | 내용 | 우리 기능과의 대응 |
|---|---|---|
| 안전조치기준 §2 1호 | **개인정보처리시스템 정의**: 데이터베이스시스템 등 개인정보를 처리할 수 있도록 체계적으로 구성한 시스템 (안내서상 DB·응용프로그램·파일처리시스템 포함) | 1-2절 접근 경로 범위 판단의 근거 |
| 안전조치기준 §2 3호 | **접속기록 정의**: 식별자, 접속일시, 접속지 정보, 처리한 정보주체 정보, 수행업무 등 | 접속기록 데이터 스펙 그 자체 (3절) |
| 안전조치기준 §8① | 접속기록 **1년 이상** 보관(5만명 이상·고유식별정보·민감정보 처리 시 2년). **단서: 정보주체는 제외** | LOG-01 보관 정책 / 로깅 지점 한정 / LOG-20 2년 보관 대상 표시 |
| 안전조치기준 §8② | 접속기록 및 **개인정보 다운로드 상황을 확인·점검**하는 주기·방법·사후조치절차를 내부 관리계획으로 정하고 이행 | **서비스 전체의 존재 근거**. 점검 주기를 Argus 설정값으로 두는 근거 (아래 주석) |
| 안전조치기준 §8③ | 접속기록의 **위·변조 및 도난·분실 방지** 조치 | 로그 무결성 (비기능), LOG-09 원장 기준점 |
| 안전조치기준 §6①2호 | 접속 IP 등을 **분석하여 유출 시도 탐지 및 대응** | LOG-03 이상행위 탐지 |
| **안전조치기준 §17①** | **공공시스템 접속기록 등을 자동화된 방식으로 분석하여 불법적인 유출 및 오용·남용 시도를 탐지하고 그 사유를 소명하도록 하는 등 필요한 조치** | **LOG-03 탐지 + LOG-06~08 소명 — 핵심 2기능이 그대로 명문화된 조항** |
| 안전조치기준 §5①③ | 최소 권한 차등 부여, 접근 권한 부여·변경·말소 내역 **3년** 보관 | PLT-10·14, LOG-19 |
| 안전조치기준 §7②5·6호 | **신용카드번호·계좌번호 암호화 저장** | PLT-05 결제수단 정보 |
| 안전조치기준 §12① | 개인정보 출력 시 **용도 특정**, 출력 항목 최소화 | PLT-13 다운로드 감시 / **LOG-10 마스킹 해제 사유 입력** |
| PIPA §2 1호 나목 | 다른 정보와 **쉽게 결합**하여 알아볼 수 있는 것도 개인정보 | LOG-10 내부 식별자 마스킹의 근거 |

> **§8② 문구 변경 주석**: 2024.10 안내서에는 접속기록을 "월 1회 이상 점검"하고 다운로드 확인 시 사유를 반드시 확인하도록 되어 있다. 반면 본 프로젝트가 참조하는 **2026.7.1 고시(제2026-9호) §8② 원문에는 "월 1회" 문구가 없으며**, 점검 주기·방법·사후조치절차를 내부 관리계획으로 정하도록 조직 자율에 위임하고 있다. 개정 경위는 확인하지 못했다. Argus에서는 점검 주기를 고정값이 아닌 **설정값**으로 두는 근거로 활용한다.

### 핵심 포지셔닝 (§17①의 함의)

**민간에는 접속기록 점검의 "자동화" 의무가 없다.** §8②는 점검 주기·방법을 내부 관리계획으로 정하라고만 할 뿐, 수동 점검도 적법하다. 반면 **공공시스템운영기관에는 §17①이 "자동화된 분석 → 탐지 → 소명 요구"를 법정 의무로 명시**한다.

따라서 Argus의 포지셔닝은 **"공공시스템에만 의무화된 수준의 조치를, 민간 개인정보처리자도 이행할 수 있게 하는 도구"**다. 법정 최소기준(수동 점검)을 상회하는 자율적 조치이며, 동시에 §17①이라는 명확한 기능 명세 레퍼런스를 갖는다. 공공시스템 지정 기준(§14: 100만명 이상 / 취급자 200명 이상 등)에 미달하는 조직이 주 대상이다.

## 3. 접속기록 데이터 스펙

| 필드 | 설명 | 예시 | 구분 |
|---|---|---|---|
| 식별자 | 접속한 개인정보취급자 계정 | `cs_kim` | §2 3호 필수 |
| 접속일시 | 행위 발생 시각 | `2026-09-15 23:41:07` | §2 3호 필수 |
| 접속지 정보 | 접속 IP 등 | `10.20.3.55` | §2 3호 필수 |
| 처리한 정보주체 정보 | 조회·처리 대상 회원 **내부 식별자(PK)** 또는 건수 | `member_10293` (표시 표기 — 저장·전송 표기는 [DB스키마](db-schema.md) 2-1절) | §2 3호 필수 |
| 수행업무 | `LOGIN` / `LOGOUT` / `READ` / `CREATE` / `UPDATE` / `DELETE` / `DOWNLOAD` / `EXPORT` (`UNMASK`는 v0.2) | `DOWNLOAD` | §2 3호 필수 |
| **접근 경로** | `APP`(응용프로그램 경유) / `DB`(DB 직접 접근) | `APP` | **Argus 확장 필드** — 1단계는 APP만 수집 |

> **자기참조 구조**: "처리한 정보주체 정보"가 포함되므로 접속기록 자체가 개인정보이며, 따라서 Argus도 개인정보처리시스템에 해당한다. Argus 자신의 접속기록도 §8 대상이 된다. 상세는 [액터별_플로우](actor-flows.md) 9절.

## 4. 기능 요구사항 — 플랫폼 (감시 대상, 최소구현)

### 4-1. 사용자 UI

> **로깅 없음**: 안전조치기준 §8① 단서("정보주체는 제외한다")에 따라 고객의 행위는 접속기록 대상이 아니다. 로깅 지점은 관리자 UI에만 심는다.

| ID | 기능 | 설명 | 우선순위 |
|---|---|---|---|
| PLT-01 | 회원가입 | 감시 대상 처리시스템의 수집·고지·동의 흐름을 갖춘 최소 구현. 동의 항목은 이용약관(필수)·개인정보 수집·이용(필수)·만 14세 이상 확인(필수)·마케팅 수신(선택)이며, 필수와 선택을 구분해 각각 받고 항목마다 목적·항목·보유 기간을 알린다(PIPA §15②, §22①). 동의 이력(항목·버전·시각·IP), 개인정보 처리방침·이용약관 페이지. 필수 항목은 이메일(아이디)·비밀번호·이름·휴대폰 번호와 만 14세 확인이다. **생년월일·성별은 받지 않는다**(쓸 목적 없음 — 최소수집 §16①). 주소는 가입 항목에서 빼고 배송지로 받는다 | Must |
| PLT-02 | 로그인 / 로그아웃 | 고객 계정 인증. 고객·관리자 화면은 계정 유형이 아니라 URL 경로로 구분한다(`platform-web/app/(shop)` 고객, `app/admin` 관리자) | Must |
| PLT-03 | 마이페이지 | 내 정보 조회·수정(이메일 제외), 비밀번호 변경, 선택 동의 철회·재동의, 배송지 관리(여러 개, 기본 배송지), 회원 탈퇴(**v0.1: 즉시 파기**). 카드는 저장하지 않으므로 관리 화면 없음 | Must |
| PLT-04 | 주문 (간이) | 상품 목록(시드)에서 주문 생성. 상품 1개·상태 PAID만 다루고, 취소·환불 처리는 v0.2. 로그인 필수(비로그인이면 로그인 화면을 거쳐 원래 상품으로 돌아옴), 등록된 배송지에서 선택(없으면 "마이페이지에서 등록" 안내), 주문에 배송 정보 스냅샷 저장 | Must |
| PLT-05 | **결제 (간이)** | 카드 결제는 **PG 목업 결제창**에서 한다. 결제할 때마다 카드사를 고르고 카드번호·유효기간을 직접 입력하며, 카드번호는 결제창(브라우저) 안에만 있고 플랫폼 서버로 보내지 않는다(실제로도 카드번호는 PG만 받음). 플랫폼은 카드번호·끝 4자리를 받지도 저장하지도 않고 PG 거래 정보(카드사·거래번호·승인 시각·금액)만 저장하며, 카드 저장·관리 기능은 없다. 결제창은 형식 확인(자릿수·Luhn·유효기간) 없이 입력만 받는다 — 목업의 목적은 "카드번호가 쇼핑몰 서버에 오지 않는 구조"를 보이는 것이고 검증이 아니다. **환불계좌만 직접 수집해 앱 레벨에서 암호화**한다(§7②6호). 관리자 "전체 보기"는 결제수단 데이터 유형으로 기록·탐지. 기각: PG 분리 없이 카드번호 직접 저장 — 실무(PCI DSS·여신전문금융업법)와 어긋나고 수집 최소화 위반. 기각: 빌링키 발급·카드 관리 | Must |
| PLT-06 | 1:1 문의 등록 | 고객이 문의 접수. **"업무시스템 연동 대조"(스트레치) 성립의 전제** | Must |

### 4-2. 관리자 UI (= 1단계 감시 대상 행위가 발생하는 곳)

> 1단계에서는 **이 관리자 UI를 경유한 접근**을 로깅·점검한다. 플랫폼 DB에 대한 직접 접근은 2단계에서 다룬다(1-2절).

| ID | 기능 | 설명 | 우선순위 | 비고 |
|---|---|---|---|---|
| PLT-10 | 관리자 화면 진입 | 관리자 화면(`/admin`)은 고객 화면과 URL 경로로 나뉘고 관리자 계정(`operator`)으로 로그인한다. 메뉴·버튼은 역할별 접근 범위에 따라 노출하고(`/admin/auth/me`의 `permissions`), 허용 여부는 서버가 기능마다 검사한다(범위 밖 `403`, 접속기록 `FAILURE`) — 정책정의서 4-5 | Must | |
| PLT-11 | 회원 목록 / 상세 조회 / 검색 | 취급자가 고객 개인정보를 조회. 검색은 이름·이메일·연락처(부분 일치)·상태·가입일, 조건은 요청 본문으로 보내고 접속기록에는 키 이름만, 정보주체는 결과로 보인 회원 전부(0건도 기록) — 정책정의서 6-2 | Must | **감시 대상** |
| PLT-13 | 회원 목록 다운로드 | 엑셀/CSV export | Must | **감시 대상 — 대표적 이상행위** |
| PLT-16 | 주문·결제 조회 / 검색 | 결제수단 정보 포함 조회. 검색은 주문번호·회원번호·상태·주문일(PLT-11과 같은 기록 방식) | Must | **감시 대상 — 민감도 높은 항목** |
| PLT-17 | 1:1 문의 처리 (CS) / 검색 | 문의 확인, 고객정보 조회, 답변 등록. 검색은 상태·회원번호·작성일·제목(PLT-11과 같은 기록 방식) | Must | **정상 업무 맥락의 기준선** |
| PLT-14 | 취급자 계정·권한 관리 | ADMIN 전용 "계정·권한" 메뉴. 부여(임시 비밀번호 한 번만 표시·첫 로그인 변경 강제)·역할/팀 변경·말소(퇴직), 모든 변경에 사유 필수, 본인 계정 변경 불가. 권한 이력 append-only, 3년 보관(§5③) — 정책정의서 4-5 | Should | |
| PLT-15 | **접속기록 생성·전송** | 관리자 로그인·로그아웃과 모든 개인정보 접근 행위를 3절 규격(접근 경로 = `APP`)으로 기록하고 Argus로 전송. 권한 밖이라 거부된 요청도 `FAILURE`로 기록 | **Must** | **두 시스템의 연결고리** |

### 4-3. 시드 데이터

- 회원 데이터 수백~수천 건 (탐지 룰의 "대량 조회/다운로드"가 성립할 규모)
- 상품·주문·결제 데이터
- 1:1 문의 데이터 (일부는 취급자 조회와 매칭되고, 일부는 매칭되지 않도록 설계 — 연동 대조 시연용)
- 취급자 계정 3~5개 (CS팀 / 마케팅팀 / 운영팀 등 소속 구분, 역할 ADMIN·OPS·CS·MARKETING 지정, 계정마다 권한 이력 `GRANT` "초기 계정")
- 과거 접속기록 (baseline 비교, "전월 대비 증가율" 룰이 동작하려면 필요)

### 5-4. 탐지 룰 기본값 (상세는 [정책정의서](policy.md) 1-3절)

아래 표의 앞 7개는 접근 경로 = APP 대상이고, 접속지 룰 2개는 두 경로 모두(전체), 특정 회원 반복 처리는 APP 대상이다.

| 룰 | 유형 | 조건 |
|---|---|---|
| 야간 접속 | EVENT | 22:00~06:00 조회·다운로드 |
| 주말 접속 | EVENT | 토·일 접속 |
| 결제수단 정보 조회 | EVENT | 대상 데이터 = 결제수단 |
| 대량 다운로드 | EVENT | 1회 50건 이상 |
| 대량 조회 | AGGREGATE | 1시간 내 100건 이상 |
| 전월 대비 급증 | AGGREGATE | 전월 동기 대비 200% 이상 |
| 퇴직자 계정 접속 | EVENT | 행위 시점에 이미 퇴직 상태였던 계정의 접속 |
| 허용 범위 밖 접속지 | EVENT | 접속지가 허용 대역(기본값 사설망) 밖 |
| 짧은 시간 여러 접속지 | AGGREGATE | 1시간 내 고유 접속지 3곳 이상 |
| 특정 회원 반복 처리 | AGGREGATE | 하루 동안 같은 회원 개인정보 20번 이상 처리 |
| (스트레치) 업무 맥락 없는 조회 | — | 대응하는 1:1 문의 티켓 없이 고객 상세 조회 |

2단계 기본 룰(**접근 경로 = DB**)은 야간 접근(상)·주말 접근(중)·전월 대비 급증(중) 3개다. 개인정보 데이터를 처리한 문장만 대상이다.
