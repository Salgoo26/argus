## 2. 시스템 구성

```
┌──────────────── 플랫폼 ────────────────┐        ┌──────────────── Argus ────────────────┐
│                                        │        │                                       │
│  platform-web (Next.js)                │        │  argus-web (Next.js)                  │
│   └ 고객 UI / 관리자 UI                  │        │   └ 정보보호 담당자 / 취급자(소명) UI     │
│         │                              │        │         │                             │
│  platform-api (FastAPI)                │        │  argus-api (FastAPI)                  │
│   ├ 업무 API                            │        │   ├ 수집 API  ◀──────────── ① ─────┐  │
│   ├ [Agent] 접속기록 미들웨어 ──┐         │        │   ├ 취급자 동기화 API ◀─── ② ─────┐ │  │
│   │                            ▼        │        │   ├ 탐지·소명·보고 API              │ │  │
│   │                      [outbox 테이블]  │        │   └ (argus-worker) 탐지·파기 배치   │ │  │
│  platform-relay ───────────────────────┼── ① ──┼─────────────────────────────────┘ │  │
│   (취급자 변경 이벤트) ──────────────────┼── ② ──┼───────────────────────────────────┘  │
│         │                              │        │         │                             │
│   [platform DB]                        │        │   [argus DB] ← 접속기록 원장            │
│    회원·주문·결제·문의·취급자·outbox      │        │    (append-only + 해시체인)            │
└────────────────────────────────────────┘        └───────────────────────────────────────┘
```

- Argus의 접속기록 원장은 **argus DB**다. 플랫폼 outbox는 전송 확인 후 삭제되는 임시 버퍼일 뿐이다.
- 플랫폼 관리자가 Argus 원장을 수정할 수 없으므로, DB 분리 자체가 §8③ 무결성·직무분리에 유리하다.
- `platform-relay`와 `argus-worker`는 각각 API와 **같은 이미지를 쓰되 실행 명령만 다른 별도 컨테이너**다. API 프로세스를 여러 개 띄워도 배치·전송이 중복 실행되지 않게 하기 위함이다.

## 3. 접속기록 수집 구조 (에이전트형 미들웨어)

### 3-1. 상용 솔루션 방식과의 대응

| 상용 솔루션 (Java/WAS) | Argus (Python/FastAPI) | 적용 |
|---|---|---|
| Servlet Filter — 모든 요청 통과 | **ASGI 미들웨어** | 1단계 — 식별자·접속일시·접속지 |
| ThreadLocal — 요청 ↔ SQL 연결 | **contextvars** | 1단계 — 요청 컨텍스트에 사용자·수행업무 보관 |
| URL → 업무 매핑 설정 | **라우트 데코레이터** (`@access_log(action=..., data_category=...)`) + 명시적 제외 `@access_log_exempt("사유")` | 1단계 — 수행업무·데이터 유형. **`/admin` 라우트에 둘 다 없으면 앱 기동 거부** (2026-09-30) |
| JDBC 드라이버 교체 — SQL·결과셋 가로채기 | **SQLAlchemy 이벤트 훅** | **업그레이드 경로** — 정보주체·건수 자동 추출 |
| BCI (바이트코드 삽입) | 몽키패칭 / OpenTelemetry 자동 계측 | 채택 안 함 |
| 네트워크 미러링 | — | 채택 안 함 |

### 3-2. 한 건이 만들어지는 흐름

1. 취급자가 관리자 UI에서 요청 → Caddy가 실제 접속 IP를 헤더로 전달 → platform-api 미들웨어 진입. 로그인 토큰에서 **식별자**, 요청에서 **접속일시·접속지(IP)** 확보. (접속지 IP는 **Caddy가 넘긴 헤더만 신뢰**하도록 trusted proxy 설정)
   - **화면 서버(Next.js)는 신뢰 프록시가 아니다** (2026-10-01, 구현 M5에서 발견): Next.js rewrite 프록시는 원래 요청자 IP를 `X-Forwarded-For`에 넣지 않으면서 **클라이언트가 보낸 `X-Forwarded-For`는 그대로 전달**한다(Next.js 소스로 확인). 화면 서버를 신뢰하면 누구든 헤더 한 줄로 **접속지를 위조**할 수 있다(§2 3호 접속지 정보의 신뢰성 훼손). 따라서 로컬에서는 화면 경유 요청의 접속지가 화면 서버 IP로 기록되고(로컬은 Docker 포트 포워딩으로 원래 IP가 어차피 보이지 않아 실질 손실 없음), 운영에서는 Caddy가 `/api`를 **화면을 거치지 않고 API로 직접** 보낸다.
2. 라우트 데코레이터가 **수행업무·데이터 유형**을 컨텍스트에 기록.
3. 핸들러가 처리 결과로 **처리한 정보주체(회원 내부 PK) 또는 건수**를 컨텍스트에 기록. (1단계는 명시적 기록, 이후 SQLAlchemy 훅으로 자동화 검토)
   - **대상이 정해진 요청**(상세 조회·수정 등)은 업무 로직보다 **먼저** 대상 PK를 기록한다 — 업무가 실패해도 "누구를 대상으로 시도했는지"가 남도록. (2026-09-30)
   - 정보주체를 기록하기 **전에** 실패한 요청(입력 검증 오류 400 등)은 `subject.count = 0`으로 적재한다.
4. **응답 헤더를 보내기 직전** 미들웨어가 컨텍스트를 모아 **접속기록 1건(event_id, 결과 상태 포함)을 outbox에 적재** — 업무 트랜잭션과 **별도 트랜잭션**. **적재에 실패하면 응답을 막고 500 `ACCESS_LOG_UNAVAILABLE`을 반환한다(fail-closed).** (2026-09-30 개정 — 기존 "응답 직후")
5. platform-relay가 outbox를 읽어 **Argus 수집 API로 전송** → 성공 응답 시 outbox에서 삭제, 실패 시 재시도.
6. Argus는 event_id로 중복을 걸러 **원장에 append**.

- 로깅 지점은 **관리자 라우트에만** 적용한다(§8① 단서: 정보주체 제외).
- 고객 UI 요청은 미들웨어가 기록하지 않는다.
- **로그아웃은 기록하지 않는다**(`@access_log_exempt`) — 개인정보 처리가 없고 수행업무 코드(API명세서 2-3)에도 없다. (2026-09-30)
- **`request.path`에는 실제 URL이 아니라 라우트 템플릿**(`/admin/members/{member_id}`)을 싣는다 — 경로 변수에 실린 값이 원장에 남지 않게. 대상 회원은 `subject.ids`로 이미 기록된다. (2026-09-30)
- 처리되지 않은 예외도 `result=FAILURE`로 적재한 뒤 예외를 다시 던진다.

**적재 시점을 "응답 헤더 직전 + fail-closed"로 바꾼 이유 (2026-09-30, 구현 M2)**

| 구분 | 내용 |
|---|---|
| 문제 | "응답 직후" 적재는 적재가 실패해도 CSV 등 개인정보가 **기록 없이 이미 나간 상태**가 된다 |
| 원칙 | **기록할 수 없으면 내보내지 않는다** |
| 대가 | 응답이 적재 시간만큼 늦어지고, 플랫폼 DB 장애 시 관리자 기능이 멈춘다 |
| 한계 | 수정(UPDATE)은 업무 커밋이 먼저라 적재 실패 시 "수정은 됐는데 500"이 가능하다 — 보호 효과는 주로 **조회·다운로드** |
| 구현 | 응답 시작 메시지를 가로채야 하므로 순수 ASGI 미들웨어, 가장 바깥에 배치(쿠키 연장 미들웨어보다 바깥) |

**문패 누락 시 기동 거부 (2026-09-30)**: 관리자 라우트를 새로 만들며 데코레이터를 빠뜨리면 기록 누락이 **조용한 사고**가 된다. 기동 시 전 `/admin` 라우트를 검사해 문패(`@access_log`)도 제외 표시(`@access_log_exempt`)도 없으면 앱이 뜨지 않게 해 **즉시 드러나는 실패**로 바꾼다.

### 3-3. outbox 테이블

| 컬럼 (예시) | 용도 |
|---|---|
| `event_id` (UUID) | 기록 고유번호. Argus 중복 판별 기준 |
| `payload` (JSON) | 접속기록 본문 (§2 3호 필드 + 확장 필드 + 결과 상태) |
| `attempts`, `next_retry_at` | 재시도 관리 |
| `created_at` | 적재 시각 |

- 전달 보장: **at-least-once 전송(재시도) + 수신 측 멱등(event_id)** → 결과적으로 정확히 한 번 저장.
- 원래 Transactional Outbox는 업무 변경과 같은 트랜잭션으로 묶지만, Argus는 ①조회(READ)에는 업무 쓰기 트랜잭션이 없고 ②실패한 수정 시도도 감사상 의미가 있어 **별도 트랜잭션**으로 적재한다.

## 4. DB 분리 시 이슈와 대응

| # | 이슈 | 원인 | 대응 |

| 1 | 취급자 정보 동기화 | 퇴직자 룰·소명 대상 지정·A5 로그인에 소속·재직상태 필요, 계정 원장은 플랫폼 | **취급자 동기화 API**(생성/변경/퇴직 이벤트 push). A5의 Argus 계정도 이 동기화로 발급 |

| 5 | 마스킹 해제 시 PK까지만 노출 | Argus는 회원 원본 정보 미보유 | **의도된 경계**. 이름 확인은 플랫폼에서 조회해야 하며 그 조회는 다시 플랫폼 접속기록에 남음 — 최소처리 원칙에 부합 |
| 6 | 업무시스템 연동 대조(스트레치) | 문의 티켓이 플랫폼 DB에 있어 조인 불가 | 확장 필드에 티켓 ID 포함(`context.ticket_id`) 또는 Argus → 플랫폼 조회 API. 스트레치 착수 시 결정 |

## 5. 상용 솔루션 리서치 요약 (2026-09-23)

**공통 원리**: 조회(SELECT)는 DB에 흔적을 남기지 않으므로, 어떤 솔루션도 고객사 업무 DB에서 접속기록을 "읽어오지" 않는다. **행위가 일어나는 지점(WAS·네트워크·DB 통신)에서 가로채 기록을 만들고, 솔루션의 수집 서버로 전송**한다. 업무시스템 경유 접근에 대해서는 **WAS Agent(SW) 방식이 현재 주류**이며, 네트워크 방식은 유실 우려·암호화 트래픽 문제로 선호도가 낮아지는 추세.

| 제품 | 공개된 수집 방식 | 비고 |
|---|---|---|
| **INFOSAFER** (피앤피시큐어) | 3티어: WAS TRACER 센서를 업무시스템에 설치해 "WAS 내 세션정보 파싱" → 운영장비로 직접 전송. 2티어: "DB 통신 파싱", DBSAFER 연동 또는 DB 서버 로그 수집 | DBSCANNER로 DB 내 개인정보 위치 자동 검출. 국정원 검증 암호모듈 + WORM 백업 |
| **UBI SAFER-PSM** (이지서티) | BCI, FILTER, CONTENTS FILTERING, CLOUD FILTERING. Agent(SW) 방식을 주로 사용. "소스 코드 수정 없이 부하 최소화", "OSI 7계층 네트워크 콘텐츠 필터링" | 자사 주장: 24년 연속 매출 1위, 누적 22,781개 시스템 |
| **WEEDS BlackBox Suite** (위즈코리아) | SW: BCI 플러그인 + Java 필터 + JDBC 드라이버 교체 / 네트워크: 콘텐츠 필터링 + 미러링 / DB 로컬로깅 | 자사 주장: 조달청 누적 점유율 1위, 약 1,000개 고객사. 구축 전 ID 체계·DB 정보·개인정보 활용 현황 환경 분석 |

**3-tier 실사용자 식별의 핵심**: 요청 진입점(필터/BCI)에서 세션 사용자를 잡아 요청 스레드에 보관하고, 같은 스레드에서 실행된 SQL·결과셋(JDBC 계층)을 그 사용자에게 연결한다. WAS가 공용 DB 계정 하나로 접속해도 실제 취급자가 식별되는 이유. (벤더 내부 구조는 비공개이며, 이 설명은 각 벤더가 명시한 기술의 일반적 동작 원리에 기반함)

**사용자 재직 경험과의 대응**: 재직 당시 DBSAFER(DB 접근제어) 연동으로 **개발자의 SQL 직접 접근 기록을 점검**했고, 백오피스 경유 조회·수정 기록은 **쿼리로 추출해 정보보안팀에 제출**만 했다(점검은 팀 내 다른 담당자). → Argus 1단계는 이 "추출 → 전달 → 판단" 수작업을 자동화하고, 2단계는 본인이 직접 수행했던 DB 직접 접근 점검을 담는다.

## 6. 범위 밖 / 한계

- **DB 직접 접속(DBA·개발자의 SQL 툴 접속)**: 앱 레벨 Agent로는 기록되지 않음. 2단계에서 pgaudit 감사로그 → 수집기 → 동일 수집 API(`access_path=DB`)로 다룬다. DB 접근제어 게이트웨이 자체는 구현하지 않는다.
- **개인정보 자산(테이블·컬럼) 자동 검출(DB 스캔)**: 상용의 DBSCANNER에 해당. 2단계에서 "읽기 전용 계정으로 메타데이터(information_schema)만 조회"하는 형태로 검토.
- **정보주체 자동 추출**: 1단계는 핸들러가 명시적으로 기록. 자동화는 SQLAlchemy 훅 업그레이드 경로로 남김.

### 7-2. VM 구성

```
┌──────────── VM 1대 (Linux, RAM 2GB 이상) ─────────────┐
│  클라우드 방화벽: 80/443 외부 오픈, SSH(22)는 키 인증만     │
│                                                        │
│  Docker Compose                                        │
│   ├ caddy          ← 유일한 외부 입구, HTTPS 자동 발급      │
│   ├ platform-web   ├ platform-api   ├ platform-relay   │
│   ├ platform-db                                        │
│   ├ argus-web      ├ argus-api      ├ argus-worker     │
│   ├ argus-db                                           │
│   └ backup (일 1회 pg_dump)                             │
│     ※ DB·API는 내부 도커 네트워크에만 존재, 외부 비노출       │
└────────────────────────────────────────────────────────┘
```

| Caddy 역할 | 내용 |
|---|---|
| 라우팅 | `shop.<도메인>` → platform-web / `shop.<도메인>/api` → platform-api / `argus.<도메인>` → argus-web / `argus.<도메인>/api` → argus-api |
| HTTPS | 인증서 자동 발급·갱신 (§7④ 전송구간 암호화) |
| 접근통제 | 플랫폼 관리자 경로·Argus 전체를 **허용 IP 목록**으로 제한 (허용 IP는 코드가 아닌 서버 설정으로 관리) |
| 실제 IP 전달 | 취급자 IP를 헤더로 전달 → 앱은 Caddy만 trusted proxy로 신뢰. **`/api`는 화면 서버를 거치지 않고 API로 직접 라우팅**(3-2 #1) |
| 기타 | 업로드 크기 제한(소명 첨부), 보안 헤더 |

- 로컬 개발(Walking Skeleton)에서는 Caddy·backup 없이 시작하고 첫 배포 때 추가한다.
- 로컬에서는 브라우저 → 화면 서버(Next.js rewrite, 같은 출처 프록시) → API 구조로 CORS 없이 동작한다.

**배포 체크리스트 — 접속지 신뢰성** (2026-10-01, 구현 M5에서 도출)
- [ ] Caddy가 클라이언트가 보낸 `X-Forwarded-For`를 **덮어쓰는지**(신뢰 프록시 설정) 확인
- [ ] API의 `*_TRUSTED_PROXIES`가 **Caddy 주소만** 담는지 확인
- [ ] `/api` 경로가 화면 서버를 거치지 않고 API로 직접 가는지 확인
- [ ] 위조 헤더(`X-Forwarded-For: 8.8.8.8`)를 붙인 요청 → 원장에 실제 IP가 기록되는지 실측
- [ ] 보안 헤더(CSP·X-Frame-Options 등)는 Caddy에서 부여

## 8. CI/CD 파이프라인

### 8-1. 흐름

> 아래 흐름도는 **목표 상태**다. 항목별 도입 시점은 **8-5를 따른다**(대상 파일·산출물이 아직 없는 항목은 그것이 생기는 시점에 추가). — 2026-09-28 명시

```
[feature 브랜치] ──PR──▶ ① CI (PR 검사)
                          ├ lint·타입체크 (ruff / eslint·tsc)
                          ├ 테스트 (pytest + Postgres 서비스 컨테이너)
                          ├ 보안 스캔 [report-only]
                          │   ├ gitleaks (시크릿)
                          │   ├ CodeQL (SAST, Python·JS) — GitHub 기본 설정
                          │   └ Trivy config (Dockerfile — compose 파일은 Trivy가 인식하지 않아 대상 외)
                          ├ 도커 빌드 가능 여부 확인 (push 안 함)
                          └ Skeleton 시나리오 E2E — 별도 Compose 프로젝트로 전체 스택 기동 + 시나리오 + 해시체인 검증 (M6)
        │ merge
        ▼
[main] ──────────────────▶ ② 빌드 & 게시
                          ├ 변경된 앱만 이미지 빌드 (경로 필터)
                          ├ Trivy 이미지 스캔 [report-only, 결과는 Security 탭]
                          └ GHCR에 push (태그: 커밋 SHA)
        │ 릴리스 태그 v*
        ▼
[tag v1.2.0] ────────────▶ ③ 배포 (CD)
                          ├ 해당 SHA 이미지에 버전 태그 부여
                          ├ SSH로 VM 접속
                          ├ DB 백업(pg_dump) → 마이그레이션(Alembic, 일회성 컨테이너)
                          ├ docker compose pull && up -d
                          └ 헬스체크(/healthz) 실패 시 직전 버전 태그로 롤백

[상시] Dependabot — 의존성 취약점 알림 + 업데이트 PR 자동 생성
[상시] GitHub push protection — 시크릿이 포함된 push 자체를 차단
```

### 8-2. 설계 결정

| 항목 | 결정 | 이유 |
|---|---|---|
| 브랜치 | main + feature 브랜치, **1인 개발이어도 PR로 병합** | PR·CI 결과가 그대로 **변경관리 증적**이 됨 |
| 배포 트리거 | **릴리스 태그(v*) 푸시** (main 머지 시 자동 배포 아님) | 서버가 상시 기동 상태가 아니고, 버전 단위 이력·롤백이 명확 |
| 이미지 레지스트리 | GHCR (공개 레포 → 무료) | 이미지에 시크릿이 들어가지 않도록 Trivy가 이미지 내 시크릿도 검사 |
| 보안 스캔 정책 | **report-only로 시작** → 보안성 검토 단계에서 결과를 근거로 조치 → 이후 Critical/High에서 배포 차단(gate)으로 전환 | 기존 방침("보안 조치는 기능 구현 후 별도 점검 단계")과 정합. "파이프라인이 쌓아둔 결과로 취약점을 추적·조치했다"는 증적 확보 |
| DB 마이그레이션 | 배포 시 **백업 → 마이그레이션 → 기동** 순서, 하위 호환되는 변경 위주 | 롤백 시 앱은 이전 이미지로, DB는 백업 복구(수동) |
| 롤백 | 이전 버전 태그로 compose 재기동 | 이미지 태그가 불변이라 재현 가능 |

### 8-5. 구현 시점

| 시점 | 구현 범위 |
|---|---|
| Walking Skeleton 착수 시 (M0) | ① CI(lint·테스트·gitleaks), CodeQL, Dependabot, push protection |
| **첫 Dockerfile이 추가되는 PR (M1)** | ① **Trivy config + 도커 빌드 가능 여부 확인** 추가 |
| 프론트엔드 앱이 추가되는 PR (M5) | ① eslint·tsc, Dependabot에 npm 생태계 추가 |
| 시나리오 E2E가 생기는 PR (M6) | ① **e2e job** — 실행마다 일회용 `.env`(무작위 값) 생성 → 별도 Compose 프로젝트(`argus-e2e`)로 빈 DB에서 전체 스택 기동 → API 수준 시나리오(화면 서버 경유) + 해시체인 검증 → 볼륨까지 정리. 로컬과 같은 스크립트(`scripts/e2e.sh`)를 써서 README 경로가 CI에서 그대로 검증됨 |
| Skeleton 로컬 동작 후 | ② 이미지 빌드·**Trivy 이미지 스캔**·GHCR |
| 첫 배포 시 | ③ CD, VM 세팅, Caddy, 백업 |

- **원칙: 점검 도구는 점검 대상이 생기는 PR에서 함께 도입한다.** 대상이 없을 때 미리 넣지 않고(빈 스캔·오류 방지), 대상이 생긴 뒤 미루지도 않는다(점검 공백 방지).
- 개정 경위(2026-09-28): 기존 표는 Trivy 전체를 "Skeleton 로컬 동작 후"로 묶어 8-1(PR 단계에 Trivy config)과 불일치. 구현 M0에서 발견. Trivy는 **config(설정 파일 대상, PR 단계)** 와 **image(빌드 산출물 대상, main 빌드 단계)** 로 성격이 달라 분리함. 기존 시점을 유지하면 M1~M6 동안 추가되는 Dockerfile이 검사 없이 누적됨.

### 8-6. 알려진 개선 과제 (보안성 검토 단계로 이관)

- **SSH 포트 외부 노출**: GitHub Actions 러너의 출발지 IP가 고정되지 않아 1차에는 키 인증만으로 운영. 보안성 검토 단계에서 Tailscale 또는 클라우드 IAP 터널로 **SSH 공개 노출 제거**를 개선 과제로 수행.
- **시크릿 관리 고도화**: VM `.env` → 클라우드 Secret Manager 이관 검토.
- **보안 스캔 gate 전환**: report-only → Critical/High 차단.
- **DAST**: OWASP ZAP 기본 스캔을 배포 후 점검 단계에서 수행.
- **GitHub Actions 커밋 SHA 고정**: 태그(`@v4`) 대신 SHA로 고정해 공급망 공격 대비 (구현 M0에서 제기, 2026-09-28).
- **해시체인 외부 앵커링** (구현 M1에서 제기, 2026-09-29): 해시체인만으로는 ①끝부분 레코드 삭제 ②권한자의 전체 재계산을 탐지하지 못함 → 체인 머리(최신 `id`·`hash`)를 DB 밖(WORM 저장소, 외부 로그 등)에 주기 기록. 상용 솔루션의 WORM 백업(5절 INFOSAFER)과 같은 취지. 상세는 [[DB스키마.md]] 3-5 "알려진 한계"
- **`access_log` TRUNCATE·DELETE 방어** (M1, 2026-09-29): 트리거는 UPDATE만 차단하며, 테이블 소유자는 TRUNCATE·DELETE가 가능 → `BEFORE TRUNCATE`(및 파기 롤 외 `BEFORE DELETE`) 트리거 검토. 단 소유자는 트리거 자체도 제거할 수 있으므로, 근본 대응은 외부 앵커링과 함께 봐야 함
- **append 경로 강제** (M1, 2026-09-29): 앱 계정이 append 함수를 거치지 않고 직접 INSERT하는 것을 DB가 막지 못함(검증 시 체인 불일치로 사후 탐지는 됨) → `SECURITY DEFINER` append 함수 + 앱에는 EXECUTE만. M1에서는 정규화 로직 이중 구현(SQL·Python) 위험 때문에 기각
- **HMAC 신·구 키 병행** (M1, 2026-09-29): [[API명세서_시스템간.md]] 1-2 #4가 규정하지만 Skeleton은 출처당 키 1개 → 키 교체 시 무중단 전환을 위해 구현
- **로그인 실패 제한의 한계** (구현 M2에서 제기, 2026-09-30): ①잠금 해제가 스크립트뿐이고 시간 경과로 풀리지 않음 → 일부러 틀려 정상 사용자를 잠그는 서비스 거부 가능 ②계정 단위로만 계산 → 여러 계정에 흔한 비밀번호를 대입하는 password spraying 미탐지 ③IP 단위 제한 없음 ④존재하지 않는 ID 대입은 Argus에 보이지 않음(정책정의서 4-3의 대가)
- **JWT 로그아웃 후 토큰 유효** (M2): 로그아웃해도 토큰은 만료(30분) 전까지 유효 → 서버 측 폐기 목록 또는 세션 저장소 검토
- **취급자 명부 소속 이력** (M2): Argus 명부는 현재 상태만 보유 — 부서 이동 후 과거 기록을 조회하면 현재 소속으로 보임. 탐지는 수 분 내 판정·`log_summary`·`rule_snapshot`으로 보완. 필요 시 명부 이력화
- **relay ↔ argus-api 구간 평문(http)** (M2): 도커 내부망 통신. HMAC으로 무결성·인증은 확보되나 기밀성은 내부망에 의존 — API명세서 1-1은 HTTPS 전제
- **DB 직접 접속 미기록** (M2): DBeaver 등으로 DB에 직접 접속한 조회는 Agent가 기록하지 못함 — 6절의 2단계(pgaudit) 범위
- **플랫폼 DB 계정 1개(소유자) 운영** (M2): 무대장치라 Argus 같은 권한 분리를 하지 않음 — ISMS-P 점검 실습의 발견사항 후보
- **DEAD 건 운영 알림·재처리 도구 부재** (M2): 현재 ERROR 로그뿐 (API명세서 7절 미결)
- **Argus 계정 관리 이력 부재** (구현 M4에서 제기, 2026-10-01): 담당자 계정 생성·비밀번호 설정·잠금 해제를 관리 스크립트(CLI)로 하므로 Argus 접속기록·상태 이력 어디에도 남지 않음 — 안전조치기준 §5③(권한 부여·변경·말소 내역 3년 보관) 관점의 점검 대상

## 10. 구현 작업 방식 (2026-09-23)

| 역할 | 도구 | 하는 일 |
|---|---|---|
| 코드 작성·실행·테스트·커밋 | **Claude Code** (Claude 데스크탑 앱 Code 탭, 사용자 Windows PC의 레포 폴더) | `CLAUDE.md`와 `docs/`를 읽고 마일스톤 단위로 구현, 세션마다 `docs/implementation-log.md` 작성 |
| 기록·설계 변경 판단·검토 | **Cowork "구현" 방** (레포 폴더 연결) | 구현 로그를 읽어 `진행기록.md` 동기화, 설계 변경 시 원본 문서 개정, 설계 대비 검토 |

- Claude Code는 claude.ai 프로젝트 문서함을 직접 읽지 못하므로 `CLAUDE.md` + `docs/` 사본이 다리 역할을 한다.
- 설계 문서의 **원본은 claude.ai 프로젝트**다. 레포의 `docs/`는 사본이며 직접 수정하지 않는다.
- Cowork "구현" 방은 매일이 아니라 **마일스톤 완료 시·설계 변경 발생 시**에만 연다.
- 사용자 PC 준비물: Git for Windows, Docker Desktop(WSL2), GitHub 계정 + GitHub CLI(`gh`, 로그인은 사용자가 직접), VS Code(선택).
