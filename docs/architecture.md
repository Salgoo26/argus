## 2. 시스템 구성

```
┌──────────────── 플랫폼 ────────────────┐        ┌──────────────── Argus ────────────────┐
│                                        │        │                                       │
│  platform-web (Next.js)                │        │  argus-web (Next.js)                  │
│   └ 고객 UI / 관리자 UI                  │        │   └ 정보보호 담당자 / 취급자(소명) UI     │
│         │                              │        │         │                             │
│  platform-api (FastAPI)                │        │  argus-api (FastAPI)                  │
│   ├ 업무 API                            │        │   ├ 수집 API  ◀──────────── ① ─────┐  │
│   ├ [Agent] 접속기록 미들웨어 ──┐         │        │   ├ 취급자 동기화 API ◀─── ② ─────┐ │  │
│   │                            ▼        │        │   ├ 탐지·소명·보고 API              │ │  │
│   │                      [outbox 테이블]  │        │   └ (argus-worker) 탐지·파기 배치   │ │  │
│  platform-relay ───────────────────────┼── ① ──┼─────────────────────────────────┘ │  │
│   (취급자 변경 이벤트) ──────────────────┼── ② ──┼───────────────────────────────────┘  │
│  db-gateway (2티어, 2026-10-05) ───────┼── ① ──┼──▶ 같은 수집 API (access_path=DB)   │
│   └ DB 툴 ↔ platform-db 중계 + 자체 버퍼 │        │                                       │
│         │                              │        │         │                             │
│   [platform DB]                        │        │   [argus DB] ← 접속기록 원장            │
│    회원·주문·결제·문의·취급자·outbox      │        │    (append-only + 해시체인)            │
└────────────────────────────────────────┘        └───────────────────────────────────────┘
```

- Argus의 접속기록 원장은 **argus DB**다. 플랫폼 outbox는 전송 확인 후 삭제되는 임시 버퍼일 뿐이다.
- 플랫폼 관리자가 Argus 원장을 수정할 수 없으므로, DB 분리 자체가 §8③ 무결성·직무분리에 유리하다.
- `platform-relay`와 `argus-worker`는 각각 API와 **같은 이미지를 쓰되 실행 명령만 다른 별도 컨테이너**다. API 프로세스를 여러 개 띄워도 배치·전송이 중복 실행되지 않게 하기 위함이다.

## 3. 접속기록 수집 구조 (에이전트형 미들웨어)

### 3-1. 상용 솔루션 방식과의 대응

| 상용 솔루션 (Java/WAS) | Argus (Python/FastAPI) | 적용 |
|---|---|---|
| Servlet Filter — 모든 요청 통과 | **ASGI 미들웨어** | 1단계 — 식별자·접속일시·접속지 |
| ThreadLocal — 요청 ↔ SQL 연결 | **contextvars** | 1단계 — 요청 컨텍스트에 사용자·수행업무 보관 |
| URL → 업무 매핑 설정 | **라우트 데코레이터** (`@access_log(action=..., data_category=...)`) + 명시적 제외 `@access_log_exempt("사유")` | 1단계 — 수행업무·데이터 유형. **`/admin` 라우트에 둘 다 없으면 앱 기동 거부** (2026-09-30) |
| JDBC 드라이버 교체 — SQL·결과셋 가로채기 | **SQLAlchemy 이벤트 훅** | **업그레이드 경로** — 정보주체·건수 자동 추출 |
| BCI (바이트코드 삽입) | 몽키패칭 / OpenTelemetry 자동 계측 | 채택 안 함 |
| 네트워크 미러링 | — | 채택 안 함 |

### 3-2. 한 건이 만들어지는 흐름

1. 취급자가 관리자 UI에서 요청 → Caddy가 실제 접속 IP를 헤더로 전달 → platform-api 미들웨어 진입. 로그인 토큰에서 **식별자**, 요청에서 **접속일시·접속지(IP)** 확보. (접속지 IP는 **Caddy가 넘긴 헤더만 신뢰**하도록 trusted proxy 설정)
   - **화면 서버(Next.js)는 신뢰 프록시가 아니다** (2026-10-01, 구현 M5에서 발견): Next.js rewrite 프록시는 원래 요청자 IP를 `X-Forwarded-For`에 넣지 않으면서 **클라이언트가 보낸 `X-Forwarded-For`는 그대로 전달**한다(Next.js 소스로 확인). 화면 서버를 신뢰하면 누구든 헤더 한 줄로 **접속지를 위조**할 수 있다(§2 3호 접속지 정보의 신뢰성 훼손). 따라서 로컬에서는 화면 경유 요청의 접속지가 화면 서버 IP로 기록되고(로컬은 Docker 포트 포워딩으로 원래 IP가 어차피 보이지 않아 실질 손실 없음), 운영에서는 Caddy가 `/api`를 **화면을 거치지 않고 API로 직접** 보낸다.
2. 라우트 데코레이터가 **수행업무·데이터 유형**을 컨텍스트에 기록.
3. 핸들러가 처리 결과로 **처리한 정보주체(회원 내부 PK) 또는 건수**를 컨텍스트에 기록. (1단계는 명시적 기록, 이후 SQLAlchemy 훅으로 자동화 검토)
   - **대상이 정해진 요청**(상세 조회·수정 등)은 업무 로직보다 **먼저** 대상 PK를 기록한다 — 업무가 실패해도 "누구를 대상으로 시도했는지"가 남도록. (2026-09-30)
   - 정보주체를 기록하기 **전에** 실패한 요청(입력 검증 오류 400 등)은 `subject.count = 0`으로 적재한다.
4. **응답 헤더를 보내기 직전** 미들웨어가 컨텍스트를 모아 **접속기록 1건(event_id, 결과 상태 포함)을 outbox에 적재** — 업무 트랜잭션과 **별도 트랜잭션**. **적재에 실패하면 응답을 막고 500 `ACCESS_LOG_UNAVAILABLE`을 반환한다(fail-closed).** (2026-09-30 개정 — 기존 "응답 직후")
5. platform-relay가 outbox를 읽어 **Argus 수집 API로 전송** → 성공 응답 시 outbox에서 삭제, 실패 시 재시도.
6. Argus는 event_id로 중복을 걸러 **원장에 append**.

- 로깅 지점은 **관리자 라우트에만** 적용한다(§8① 단서: 정보주체 제외).
- 고객 UI 요청은 미들웨어가 기록하지 않는다.
- **로그아웃은 기록하지 않는다**(`@access_log_exempt`) — 개인정보 처리가 없고 수행업무 코드(API명세서 2-3)에도 없다. (2026-09-30)
- **`request.path`에는 실제 URL이 아니라 라우트 템플릿**(`/admin/members/{member_id}`)을 싣는다 — 경로 변수에 실린 값이 원장에 남지 않게. 대상 회원은 `subject.ids`로 이미 기록된다. (2026-09-30)
- 처리되지 않은 예외도 `result=FAILURE`로 적재한 뒤 예외를 다시 던진다.

**적재 시점을 "응답 헤더 직전 + fail-closed"로 바꾼 이유 (2026-09-30, 구현 M2)**

| 구분 | 내용 |
|---|---|
| 문제 | "응답 직후" 적재는 적재가 실패해도 CSV 등 개인정보가 **기록 없이 이미 나간 상태**가 된다 |
| 원칙 | **기록할 수 없으면 내보내지 않는다** |
| 대가 | 응답이 적재 시간만큼 늦어지고, 플랫폼 DB 장애 시 관리자 기능이 멈춘다 |
| 한계 | 수정(UPDATE)은 업무 커밋이 먼저라 적재 실패 시 "수정은 됐는데 500"이 가능하다 — 보호 효과는 주로 **조회·다운로드** |
| 구현 | 응답 시작 메시지를 가로채야 하므로 순수 ASGI 미들웨어, 가장 바깥에 배치(쿠키 연장 미들웨어보다 바깥) |

**문패 누락 시 기동 거부 (2026-09-30)**: 관리자 라우트를 새로 만들며 데코레이터를 빠뜨리면 기록 누락이 **조용한 사고**가 된다. 기동 시 전 `/admin` 라우트를 검사해 문패(`@access_log`)도 제외 표시(`@access_log_exempt`)도 없으면 앱이 뜨지 않게 해 **즉시 드러나는 실패**로 바꾼다.

### 3-3. outbox 테이블

| 컬럼 (예시) | 용도 |
|---|---|
| `event_id` (UUID) | 기록 고유번호. Argus 중복 판별 기준 |
| `payload` (JSON) | 접속기록 본문 (§2 3호 필드 + 확장 필드 + 결과 상태) |
| `attempts`, `next_retry_at` | 재시도 관리 |
| `created_at` | 적재 시각 |

- 전달 보장: **at-least-once 전송(재시도) + 수신 측 멱등(event_id)** → 결과적으로 정확히 한 번 저장.
- 원래 Transactional Outbox는 업무 변경과 같은 트랜잭션으로 묶지만, Argus는 ①조회(READ)에는 업무 쓰기 트랜잭션이 없고 ②실패한 수정 시도도 감사상 의미가 있어 **별도 트랜잭션**으로 적재한다.

### 3-4. DB 직접 접근 — 게이트웨이 중계 (2티어, 2026-10-05 확정 · 기능 레이어 8)

> 근거: [[진행기록.md]] "2026-10-02 ~ 10-05 기능 레이어 8(2티어) 설계 확정". 기존 6절의 pgaudit안을 대체한다.

```
[DB 툴(DBeaver 등)] ──(사용자=플랫폼 아이디, 비밀번호=DB 접속 토큰)──▶ [db-gateway] ──(공용 계정, 연결 1:1)──▶ [platform-db]
                                                                       │
                                                                       ├─ 원문(SQL·매개변수) → [gateway-data 볼륨] (게이트웨이만 마운트)
                                                                       ├─ 접속기록(정규화 SQL 등, access_path=DB) → [게이트웨이 버퍼] (같은 gateway-data 볼륨)
                                                                       └─ 게이트웨이 전송 루프 ──HMAC(출처 PLATFORM)──▶ Argus 수집 API ①
```

| 항목 | 설계 |
|---|---|
| 구조 | **게이트웨이(프록시형) 중계**. PostgreSQL 통신(프로토콜 v3)을 중계하며 SQL과 결과를 가로챈다. platform-db 포트는 **게이트웨이·앱만** 접근 가능(호스트·외부 미공개) → **네트워크 경로 기준으로** 게이트웨이 우회가 구조적으로 불가. 호스트(서버) 관리자 권한으로 컨테이너 안에서 직접 접속하는 경로(`docker compose exec platform-db psql`)는 앱 설계로 막을 수 없다 → 8-6 "2티어 한계" (2026-10-06 한정) |
| 인증 | 플랫폼 관리자 화면 로그인 → **DB 접속 토큰 발급**(1시간 고정, 시간 내 재사용 가능, 사유 입력 없음) → DB 툴 접속 시 `사용자 = 본인 플랫폼 아이디`, `비밀번호 = 토큰` → 게이트웨이가 토큰을 검증하고 아이디와 토큰의 주인이 같은지 확인 → **공용 계정**으로 DB에 연결 |
| 계정 상태 | 연결 시 플랫폼 계정 상태(퇴직·잠금)를 다시 확인한다(관리자 인증의 "매 요청 계정 상태 재확인"과 같은 원칙). 이를 위해 게이트웨이는 **`operator`를 조회한다** — 사용자 연결과 별개인 게이트웨이 자체 연결로, 조회에 실패하면 접속을 거부한다(fail-closed). 같은 조회로 인증 실패 시 "존재하는 아이디인지"(실패 기록 여부)도 판단한다 (2026-10-05 문구 명확화, 구현 착수 중 Claude Code 질의). 연결은 **토큰 만료 시각에 게이트웨이가 끊는다** |
| 공용 계정 | 플랫폼 DB의 기존 앱 계정. 비밀번호는 게이트웨이·platform-api 컨테이너의 `.env`에만 있고 사람은 모른다. DB에 사람별 계정을 만들지 않는다 |
| 실사용자 귀속 | 토큰 검증은 **연결 단위** → 그 연결의 모든 SQL에 실사용자를 붙인다. **사용자 연결 1개 = DB 연결 1개**(커넥션 풀링 금지 — 풀링하면 SQL과 사람의 대응이 깨짐). DB 자체 로그엔 공용 계정만 보이므로 "누가"의 기준 기록은 **게이트웨이 → Argus 원장**이다 |
| 원장 기록 | 실사용자 + DB 계정 + **정규화 SQL**(리터럴을 `$1`…로 치환, 예: `WHERE email = $1`) + 테이블·컬럼 + 건수 + **원문 참조·지문**. 필드는 [[API명세서_시스템간.md]] 2-3 `context` |
| 원문 저장 (D안) | SQL 원문·매개변수는 **게이트웨이 저장소(`gateway-data` 볼륨)에만** 둔다. Argus는 원문을 갖지 않는다(절대 규칙 #3 유지 — 매개변수에 이메일·이름이 실릴 수 있음). 지문 = SHA-256(원문 레코드)로, Argus 원장의 지문과 대조해 원문의 위·변조·유실을 확인한다. **조회 결과(행 데이터)는 저장하지 않는다** |
| 정보주체 식별 (C안) | **⏸ 보류 (2026-10-06, 사용자 결정 — SQL 재현 방식과 함께 재논의, 아래 "정보주체 기록 방식")**. v0.1은 **모든 DB 기록이 `subject_unresolved = true` + 건수 + 원문 참조**다. 보류된 설계안: **결과·조건에서 회원번호(PK) 추출**. 결과 컬럼 설명(RowDescription)이 주는 "원본 테이블·컬럼 번호"로 `member.id`·`*.member_id` 컬럼을 찾아 그 값을 모은다. UPDATE·DELETE는 조건이 회원 PK(`id = $1`, `member_id = $1`)면 매개변수에서 추출. `id` 없는 SELECT, PK 아닌 조건의 UPDATE·DELETE는 **"정보주체 미특정"** + 건수 + 원문 참조로 남긴다 |
| 수행업무 매핑 | `SELECT` → `READ` / `INSERT` → `CREATE` / `UPDATE`·`MERGE` → `UPDATE` / `DELETE`·`TRUNCATE` → `DELETE` / `COPY … TO` → `DOWNLOAD` / 연결 인증 → `LOGIN`(성공·실패. 존재하지 않는 아이디는 기록하지 않음 — API명세서 2-4 v0.4 규칙과 동일). **구현 세부(2026-10-06)**: `COPY … FROM` → `CREATE` / **안을 볼 수 없는 실행** — `SELECT 사용자함수()` → `READ`, `CALL`·`DO`·SQL `EXECUTE`(준비된 문장 실행) → `UPDATE`, 데이터 유형 `MEMBER_BASIC`, `subject_unresolved = true`(사용자 결정 — `NONE`이면 미특정 룰에도 안 걸리고 `PAYMENT`면 결제수단 룰 오탐) / `EXPLAIN`은 안의 문장 기준(`ANALYZE`는 실제 실행) / **파서가 못 읽은 문장**은 `READ`·`MEMBER_BASIC`·미특정으로 보수적으로 전송(대개 DB도 거부해 `FAILURE`) / fastpath 함수 호출은 기록할 수 없어 **연결 종료** |
| 데이터 유형 | 문장이 건드린 테이블로 정한다: `refund_account` → `PAYMENT`(계좌번호는 암호문이지만 결제수단 테이블 접근 자체가 점검 대상) / `member`·`member_consent`·`retained_member_record` → `MEMBER_BASIC` / `inquiry` → `INQUIRY` / `orders`·`payment`(PG 거래 정보) → `ORDER` / 그 외 → `NONE`. 여러 테이블이면 **가장 민감한 것**(PAYMENT > MEMBER_BASIC > INQUIRY > ORDER > NONE) |
| 기록 제외 | **사용자 테이블을 하나도 참조하지 않는 문장** — 시스템 카탈로그(`pg_catalog`·`information_schema`)만 읽는 문장, 테이블 없는 `SELECT`(`SELECT version()`), 시스템 함수 FROM(`pg_get_keywords()`) 등 DB 툴의 메타데이터·상태 조회(2026-10-06 범위 명확화 — Argus 전송만 제외하고 **원문 저장소에는 남긴다**). **단 제외하지 않는 것**: 사용자 스키마의 함수·프로시저 호출, `DO`·`CALL` — 테이블 이름 없이도 내부에서 개인정보 테이블을 읽거나 고칠 수 있음(게이트웨이가 내부를 볼 수 없으므로 `subject_unresolved`로 기록, 매핑은 아래 "수행업무 매핑" 구현 세부). 트랜잭션 제어·`SET`·`SHOW`도 제외. **DDL·DCL은 v0.1에서 게이트웨이 원문 저장소에만** 남기고 Argus 전송은 v0.2(명령어 통제와 함께 — 수행업무 코드에 해당 값이 없음) |
| 기록 실패 시 | **기록할 수 없으면 내보내지 않는다**(3-2와 같은 원칙). 결과 행은 흘려보내되 문장 완료 신호(CommandComplete) 전에 원문 저장·접속기록 적재를 마치고, 실패하면 완료 신호 대신 오류를 보내고 연결을 끊는다 → DB 툴에서는 쿼리 실패가 된다 |
| 구현 언어 | Python(asyncio) — 다른 컴포넌트와 같은 스택. SQL 파싱·정규화는 PostgreSQL 자체 파서를 쓰는 라이브러리 **`pglast` v8.x로 확정**(2026-10-06 구현 — PG18 파서, PG16 문법을 포함) |

**세부 결정** (진행기록에 정해지지 않았던 것)

| 항목 | 결정 |
|---|---|
| 게이트웨이 → Argus 전달 경로 | **게이트웨이 자체 버퍼 + 전송 루프** (2026-10-05 사용자 결정). 버퍼는 `gateway-data` 볼륨의 로컬 저장소(SQLite 기본안)이고, outbox 개념(event_id·재시도·건별 판정·413 분할·스스로 버리지 않음)과 relay 코드를 그대로 재사용한다. 서명은 **출처 `PLATFORM` 키** → 취급자 매칭 `(source_system, login_id)`이 3티어와 같다. **기각**: 플랫폼 outbox 적재(처음 선택했으나 재검토) — 공용 계정이 DB 소유자라 게이트웨이 접속자가 전송 전 기록을 지우거나 남의 이름으로 위조할 수 있음. 상용 DB 접근제어도 감사 기록을 **감사 대상 DB 밖 자체 저장소**에 둔다(§8③). outbox는 업무 트랜잭션과 기록을 묶기 위한 앱 패턴이라 게이트웨이엔 이유가 없음 |
| 토큰 검증 방식 | **서명 토큰 + 별도 발급 기록** (2026-10-05 사용자 결정). JWT(HS256) — `sub`=플랫폼 아이디, `jti`=토큰 ID, `aud`=`db-gateway`, `exp`=발급 후 1시간. 서명 키 `DB_GATEWAY_TOKEN_KEY`는 **platform-api·db-gateway에만**, 관리자 로그인 JWT 키와 별개(관리자 쿠키를 DB 비밀번호로 쓰지 못하게). **토큰 검증**은 서명·만료·`aud`·아이디 일치만으로 하고 **발급 기록(`db_access_token`)을 조회하지 않는다**(검증 근거로 쓰면 위장 가능). 계정 상태 확인을 위한 `operator` 조회는 이와 별개다(위 "계정 상태"). 발급 기록은 플랫폼 `db_access_token`(DB스키마 4절)에 감사용으로 남기며 토큰 값은 저장하지 않는다. 발급은 재직 중인 모든 관리자(권한 차등 PLT-14는 범위 밖 — 권한 그룹은 v0.2). **기각**: 토큰을 플랫폼 DB에 저장해 조회 — 공용 계정이 DB 소유자라 게이트웨이로 접속한 사람이 남의 토큰 행을 직접 넣어 위장할 수 있음 |
| DB 툴 ↔ 게이트웨이 구간 TLS | **v0.1부터 적용** (2026-10-05 사용자 결정). 게이트웨이가 토큰을 읽으려면 DB 툴이 비밀번호를 **평문(cleartext) 방식**으로 보내야 하므로, 게이트웨이가 TLS를 종단하고 **TLS가 아닌 연결은 인증 전에 거부**한다(§7④ 전송구간 암호화). 인증서는 v0.1 자체 서명(키·인증서는 db-gateway에만), DB 툴은 `sslmode=require`. 게이트웨이 ↔ platform-db는 도커 내부망 + SCRAM 인증 |

**구현 순서 (게이트 B 기준)**: ① 게이트웨이 중계 + 토큰 인증 + 원장 도착(정규화 SQL·테이블·컬럼·건수) + 원문 저장 → ② 회원번호 추출(C안) → ③ 탐지 룰([[정책정의서.md]] 1-3). 동결 전 못 들어간 항목은 README에 📋(설계 완료).
**상태 (2026-10-06)**: ① 완료 · **② 보류**(SQL 재현 방식과 함께 재논의, README 📋) · ③ 완료(경로별 탐지건, DB 기본 룰 3개, 화면 경로 구분·DB 기록 상세, 경로별 소명 안내, DB 전월 기준선 시드).

**3티어와의 차이**: 3티어는 앱이 회원번호를 직접 기록해 누락이 거의 없고, 2티어는 게이트웨이가 SQL·결과로 **추론**한다 → "정보주체 미특정"은 2티어의 구조적 한계다(v0.2: UPDATE·DELETE용 DB 트리거, 유일값 역조회로 축소).

**정보주체 기록 방식 — ② 보류와 재논의 (2026-10-06)**

- **계기**: 사용자 제안 "SQL을 저장해 두고, 사고 시 당시 백업에서 다시 실행해 대상을 찾는다".
- **근거**: 개인정보보호위원회 「개인정보의 안전성 확보조치 기준 안내서」(2024.10) 인쇄 90쪽(PDF 97번째 장). **검색조건문(쿼리)으로 대량의 개인정보를 처리한 경우** 그 검색조건문을 정보주체 정보로 기록할 수 있다. 다만 테이블 변경 등으로 추적이 어려울 수 있으므로 **"해당시점의 데이터베이스를 백업하는 등"** 책임 추적성 확보에 필요한 조치를 해야 한다. 예시: `SELECT * FROM student WHERE name LIKE '김%'`, `UPDATE member SET membership='VIP' …`. (2026-10-07 사용자가 PDF 원문에서 직접 확인)
- **해석 정리 (2026-10-07)**: 안내서 문구는 **대량 처리**를 전제로 한다. Argus 원문 저장소는 매개변수까지 남기므로 단건 조회(`WHERE id = 123`)도 원문만으로 대상이 드러나 이 해석과 어긋나지 않는다. 다만 Argus 원장(정규화 SQL)만으로는 대상을 알 수 없으므로 원문 저장소가 접속기록의 일부로서 보관·무결성·열람 통제를 갖춰야 한다(8-6). 남은 조건은 책임 추적성 조치(시점 백업)이고, v0.2 "사고 조사(재현) 체계"에서 다룬다
- **현재 충족 범위**: 쿼리 기록은 게이트웨이 원문 저장소(SQL·매개변수 + 지문)로 이미 있다. 책임추적성 조치는 **없다**. 백업이 하루 1회·7일 보관이라 당시 상태를 만들 수 없다 → v0.1은 **부분 충족**(8-6 "2티어 한계").
- **재현 방식의 숙제** (v0.2 후보 "사고 조사(재현) 체계", 11절):
  1. 시점 복구(PITR·WAL 보관)가 필요하다. 하루 1회 백업으로는 문장 실행 시점을 만들 수 없다.
  2. **백업 보관 기간 ↔ 파기 정책 충돌**. 재현이 성립하려면 백업을 접속기록 보관 기간(1년, 5만 명 이상 2년)만큼 둬야 하는데, 이는 "탈퇴 즉시 파기·백업 7일"(8-4, DB스키마 4-1)과 정면으로 부딪친다.
  3. 재현 불가 SQL이 있다. `ORDER BY` 없는 `LIMIT`, `now()`·`random()`, 트랜잭션·세션 상태에 기대는 문장.
  4. 재현 자체도 개인정보 처리다. 격리 환경에서 하고 재현 행위도 기록해야 한다.
  5. 원문 저장소 암호화(안내서 "필요시 암호화").
- **재논의 때 비교할 점 (Cowork 의견)**: 추출 방식(C안)은 회원번호만 남기므로 위 1·2번 충돌이 없고, 재현 방식은 구현이 가볍지만 백업 보관 정책을 바꿔야 한다. 두 방식은 배타적이지 않다(추출 + 원문 SQL 보존).
- **상용 사례 (공개 자료 한도)**: 국내 3티어 접속기록 솔루션(UBI SAFER-PSM)은 요청·응답 분석으로 정보주체를 자동 식별한다. IBM Guardium은 반환 결과 검사 규칙(extrusion rule)을 둔다. 국내 DB 접근제어(DBSafer 등)는 SQL·건수·실사용자 기록 수준까지만 확인됐다 → 사고 조사는 SQL 로그 + 백업 복구에 의존하는 셈이다.

**기각한 대안 (인증)**: A. 웹 로그인 + IP 묶기 — 로컬 Docker에선 모두 같은 내부 IP / B'. 임시 DB 계정(동적 자격증명) — 실계정이라 게이트웨이 우회 가능, 만료 처리(`VALID UNTIL`은 신규 로그인만 검사)·CREATEROLE 보호 부담 / C. PC Agent 재현 — 범위 과대. 상세는 진행기록.

## 5. 상용 솔루션 리서치 요약 (2026-09-23)

**공통 원리**: 조회(SELECT)는 DB에 흔적을 남기지 않으므로, 어떤 솔루션도 고객사 업무 DB에서 접속기록을 "읽어오지" 않는다. **행위가 일어나는 지점(WAS·네트워크·DB 통신)에서 가로채 기록을 만들고, 솔루션의 수집 서버로 전송**한다. 업무시스템 경유 접근에 대해서는 **WAS Agent(SW) 방식이 현재 주류**이며, 네트워크 방식은 유실 우려·암호화 트래픽 문제로 선호도가 낮아지는 추세.

| 제품 | 공개된 수집 방식 | 비고 |
|---|---|---|
| **INFOSAFER** (피앤피시큐어) | 3티어: WAS TRACER 센서를 업무시스템에 설치해 "WAS 내 세션정보 파싱" → 운영장비로 직접 전송. 2티어: "DB 통신 파싱", DBSAFER 연동 또는 DB 서버 로그 수집 | DBSCANNER로 DB 내 개인정보 위치 자동 검출. 국정원 검증 암호모듈 + WORM 백업 |
| **UBI SAFER-PSM** (이지서티) | BCI, FILTER, CONTENTS FILTERING, CLOUD FILTERING. Agent(SW) 방식을 주로 사용. "소스 코드 수정 없이 부하 최소화", "OSI 7계층 네트워크 콘텐츠 필터링" | 자사 주장: 24년 연속 매출 1위, 누적 22,781개 시스템 |
| **WEEDS BlackBox Suite** (위즈코리아) | SW: BCI 플러그인 + Java 필터 + JDBC 드라이버 교체 / 네트워크: 콘텐츠 필터링 + 미러링 / DB 로컬로깅 | 자사 주장: 조달청 누적 점유율 1위, 약 1,000개 고객사. 구축 전 ID 체계·DB 정보·개인정보 활용 현황 환경 분석 |

**3-tier 실사용자 식별의 핵심**: 요청 진입점(필터/BCI)에서 세션 사용자를 잡아 요청 스레드에 보관하고, 같은 스레드에서 실행된 SQL·결과셋(JDBC 계층)을 그 사용자에게 연결한다. WAS가 공용 DB 계정 하나로 접속해도 실제 취급자가 식별되는 이유. (벤더 내부 구조는 비공개이며, 이 설명은 각 벤더가 명시한 기술의 일반적 동작 원리에 기반함)

**사용자 재직 경험과의 대응**: 재직 당시 DBSAFER(DB 접근제어) 연동으로 **개발자의 SQL 직접 접근 기록을 점검**했고, 백오피스 경유 조회·수정 기록은 **쿼리로 추출해 정보보안팀에 제출**만 했다(점검은 팀 내 다른 담당자). → Argus 1단계는 이 "추출 → 전달 → 판단" 수작업을 자동화하고, 2단계는 본인이 직접 수행했던 DB 직접 접근 점검을 담는다.

**2티어(DB 접근제어) 조사 (2026-10-05, 공개 자료)**: DBSAFER·쿼리파이 DAC·INFOSAFER(2티어)의 공개 로그 항목은 **쿼리 원문·테이블·컬럼·건수·실사용자** 수준이며, 정보주체 단위 기록은 확인하지 못했다. Argus 2티어(3-4절)는 같은 게이트웨이 구조에 **결과·조건에서 회원번호를 추출**(C안)해 "누가 몇 건"에서 "누가 누구를"로 한 단계 더 간다. `ORDER BY` 없는 `LIMIT`처럼 재실행으로도 대상을 특정할 수 없는 조회가 있어, 결과에서 추출하는 방식이 유일한 방법이다. → **2026-10-06 C안 보류**: v0.1은 상용 DB 접근제어와 같은 수준(SQL·건수·실사용자 + 원문 저장)이다. 3-4 "정보주체 기록 방식".

| 사용자 실무 경험 (DBSafer) | Argus 2티어 v0.1 |
|---|---|
| PC Agent로 사번 로그인 | 관리자 화면에서 DB 접속 토큰 발급(Agent 방식은 v0.2) |
| 명령어(DML·DDL·DCL) **범위별 사전 결재** — 쿼리 단위가 아니라 "쓸 수 있는 명령어 범위" 승인 | **v0.2로 이월**(명령어 통제). 결재는 "할 수 있었다"의 근거일 뿐 "왜 했는가"의 근거가 아니므로 **소명은 여전히 필요** |

### 7-2. VM 구성

```
┌──────────── VM 1대 (Linux, RAM 2GB 이상) ─────────────┐
│  클라우드 방화벽: 80/443 외부 오픈, SSH(22)는 키 인증만     │
│   + DB 게이트웨이 포트는 관리자 허용 IP만 (2026-10-05)     │
│                                                        │
│  Docker Compose                                        │
│   ├ caddy          ← 웹 입구(유일), HTTPS 자동 발급         │
│   ├ platform-web   ├ platform-api   ├ platform-relay   │
│   ├ platform-db    ├ db-gateway     └ gateway-data(볼륨, db-gateway만) │
│   ├ argus-web      ├ argus-api      ├ argus-worker     │
│   ├ argus-db       └ argus-attachments(볼륨, argus-api만) │
│   └ backup (일 1회 pg_dump)                             │
│     ※ DB·API는 내부 도커 네트워크에만 존재, 외부 비노출       │
│     ※ platform-db 포트는 db-gateway·platform-api·relay      │
│       (+ 일회성 migrate·seed)만 내부망으로 접근             │
│       (DB 툴 입구는 db-gateway 하나 — 2026-10-05)           │
└────────────────────────────────────────────────────────┘
```

| Caddy 역할 | 내용 |
|---|---|
| 라우팅 | `shop.<도메인>` → platform-web(고객 `/`, 관리자 `/admin` — 한 앱, 2026-10-01) / `shop.<도메인>/api` → platform-api / `argus.<도메인>` → argus-web / `argus.<도메인>/api` → argus-api |
| HTTPS | 인증서 자동 발급·갱신 (§7④ 전송구간 암호화) |
| 접근통제 | 플랫폼 관리자 경로(`/admin`, `/api/admin`)·Argus 전체를 **허용 IP 목록**으로 제한 (허용 IP는 코드가 아닌 서버 설정으로 관리). 고객 화면은 공개. 고객용 앱 분리는 기각(컨테이너 증가) |
| 실제 IP 전달 | 취급자 IP를 헤더로 전달 → 앱은 Caddy만 trusted proxy로 신뢰. **`/api`는 화면 서버를 거치지 않고 API로 직접 라우팅**(3-2 #1) |
| 기타 | 업로드 크기 제한(소명 첨부 5MB), 보안 헤더 |

- **시크릿 배포 범위** (2026-10-02): 환불계좌 암호화 키 `PAYMENT_ENCRYPTION_KEY`는 platform-api·platform-seed에만, 첨부 볼륨은 argus-api에만 붙인다 — 컨테이너별 최소 시크릿·최소 마운트.

- **DB 툴 입구 = `db-gateway` 포트 하나** (2026-10-05): platform-db의 호스트 포트 공개를 없애고 게이트웨이 포트만 연다. 운영에서는 게이트웨이 포트를 클라우드 방화벽에서 **관리자 허용 IP로만** 연다(Caddy를 거치지 않는 TCP 입구이므로 IP 제한을 방화벽에서 건다). 원문 저장 볼륨 `gateway-data`는 db-gateway에만 붙이고 **백업 대상**에 넣는다(Argus 원장의 지문과 함께 복구돼야 대조 가능).

- 로컬 개발(Walking Skeleton)에서는 Caddy·backup 없이 시작하고 첫 배포 때 추가한다.
- 로컬에서는 브라우저 → 화면 서버(Next.js rewrite, 같은 출처 프록시) → API 구조로 CORS 없이 동작한다.

**배포 체크리스트 — 접속지 신뢰성** (2026-10-01, 구현 M5에서 도출)
- [ ] Caddy가 클라이언트가 보낸 `X-Forwarded-For`를 **덮어쓰는지**(신뢰 프록시 설정) 확인
- [ ] API의 `*_TRUSTED_PROXIES`가 **Caddy 주소만** 담는지 확인
- [ ] `/api` 경로가 화면 서버를 거치지 않고 API로 직접 가는지 확인
- [ ] 위조 헤더(`X-Forwarded-For: 8.8.8.8`)를 붙인 요청 → 원장에 실제 IP가 기록되는지 실측
- [ ] 보안 헤더(CSP·X-Frame-Options 등)는 Caddy에서 부여

## 8. CI/CD 파이프라인

### 8-1. 흐름

> 아래 흐름도는 **목표 상태**다. 항목별 도입 시점은 **8-5를 따른다**(대상 파일·산출물이 아직 없는 항목은 그것이 생기는 시점에 추가). — 2026-09-28 명시

```
[feature 브랜치] ──PR──▶ ① CI (PR 검사)
                          ├ lint·타입체크 (ruff / eslint·tsc)
                          ├ 테스트 (pytest + Postgres 서비스 컨테이너)
                          ├ 보안 스캔 [report-only]
                          │   ├ gitleaks (시크릿)
                          │   ├ CodeQL (SAST, Python·JS) — GitHub 기본 설정
                          │   └ Trivy config (Dockerfile — compose 파일은 Trivy가 인식하지 않아 대상 외)
                          ├ 도커 빌드 가능 여부 확인 (push 안 함)
                          └ Skeleton 시나리오 E2E — 별도 Compose 프로젝트로 전체 스택 기동 + 시나리오 + 해시체인 검증 (M6)
        │ merge
        ▼
[main] ──────────────────▶ ② 빌드 & 게시
                          ├ 변경된 앱만 이미지 빌드 (경로 필터)
                          ├ Trivy 이미지 스캔 [report-only, 결과는 Security 탭]
                          └ GHCR에 push (태그: 커밋 SHA)
        │ 릴리스 태그 v*
        ▼
[tag v1.2.0] ────────────▶ ③ 배포 (CD)
                          ├ 해당 SHA 이미지에 버전 태그 부여
                          ├ SSH로 VM 접속
                          ├ DB 백업(pg_dump) → 마이그레이션(Alembic, 일회성 컨테이너)
                          ├ docker compose pull && up -d
                          └ 헬스체크(/healthz) 실패 시 직전 버전 태그로 롤백

[상시] Dependabot — 의존성 취약점 알림 + 업데이트 PR 자동 생성
[상시] GitHub push protection — 시크릿이 포함된 push 자체를 차단
```

### 8-2. 설계 결정

| 항목 | 결정 | 이유 |
|---|---|---|
| 브랜치 | main + feature 브랜치, **1인 개발이어도 PR로 병합** | PR·CI 결과가 그대로 **변경관리 증적**이 됨 |
| 배포 트리거 | **릴리스 태그(v*) 푸시** (main 머지 시 자동 배포 아님) | 서버가 상시 기동 상태가 아니고, 버전 단위 이력·롤백이 명확 |
| 이미지 레지스트리 | GHCR (공개 레포 → 무료) | 이미지에 시크릿이 들어가지 않도록 Trivy가 이미지 내 시크릿도 검사 |
| 보안 스캔 정책 | **report-only로 시작** → 보안성 검토 단계에서 결과를 근거로 조치 → 이후 Critical/High에서 배포 차단(gate)으로 전환 | 기존 방침("보안 조치는 기능 구현 후 별도 점검 단계")과 정합. "파이프라인이 쌓아둔 결과로 취약점을 추적·조치했다"는 증적 확보 |
| DB 마이그레이션 | 배포 시 **백업 → 마이그레이션 → 기동** 순서, 하위 호환되는 변경 위주 | 롤백 시 앱은 이전 이미지로, DB는 백업 복구(수동) |
| 롤백 | 이전 버전 태그로 compose 재기동 | 이미지 태그가 불변이라 재현 가능 |

### 8-4. 백업

- 일 1회 `pg_dump` (platform DB, argus DB 각각), **보관 7일** 후 자동 삭제.
- **Argus 첨부 볼륨(`argus-attachments`)도 백업 대상** (2026-10-02) — DB의 첨부 행(해시)과 파일이 함께 복구돼야 무결성 검사를 통과한다.
- **게이트웨이 원문 볼륨(`gateway-data`)도 백업 대상** (2026-10-05) — Argus 원장의 원문 참조·지문과 대조할 원문이 함께 복구돼야 한다.
- 백업 파일도 개인정보(가상)·접속기록을 포함하므로 **암호화 저장**.
- **파기 정책과의 관계**: 원본에서 파기된 데이터가 백업에 남는 기간을 보관 주기(7일)로 한정 — 파기 정책 설명 시 함께 명시.
- **2티어 책임추적성과의 충돌 (2026-10-06)**: 안내서는 쿼리로 정보주체를 갈음할 때 "해당 시점 DB 백업 등"을 요구한다. 7일·일 1회 백업으로는 충족하지 못한다. 보관 기간을 늘리면 위 파기 원칙과 충돌한다 → v0.2 "사고 조사(재현) 체계"에서 함께 정한다(3-4 "정보주체 기록 방식", 11절).

### 8-5. 구현 시점

| 시점 | 구현 범위 |
|---|---|
| Walking Skeleton 착수 시 (M0) | ① CI(lint·테스트·gitleaks), CodeQL, Dependabot, push protection |
| **첫 Dockerfile이 추가되는 PR (M1)** | ① **Trivy config + 도커 빌드 가능 여부 확인** 추가 |
| 프론트엔드 앱이 추가되는 PR (M5) | ① eslint·tsc, Dependabot에 npm 생태계 추가 |
| 시나리오 E2E가 생기는 PR (M6) | ① **e2e job** — 실행마다 일회용 `.env`(무작위 값) 생성 → 별도 Compose 프로젝트(`argus-e2e`)로 빈 DB에서 전체 스택 기동 → API 수준 시나리오(화면 서버 경유) + 해시체인 검증 → 볼륨까지 정리. 로컬과 같은 스크립트(`scripts/e2e.sh`)를 써서 README 경로가 CI에서 그대로 검증됨 |
| Skeleton 로컬 동작 후 | ② 이미지 빌드·**Trivy 이미지 스캔**·GHCR |

- **원칙: 점검 도구는 점검 대상이 생기는 PR에서 함께 도입한다.** 대상이 없을 때 미리 넣지 않고(빈 스캔·오류 방지), 대상이 생긴 뒤 미루지도 않는다(점검 공백 방지).
- 개정 경위(2026-09-28): 기존 표는 Trivy 전체를 "Skeleton 로컬 동작 후"로 묶어 8-1(PR 단계에 Trivy config)과 불일치. 구현 M0에서 발견. Trivy는 **config(설정 파일 대상, PR 단계)** 와 **image(빌드 산출물 대상, main 빌드 단계)** 로 성격이 달라 분리함. 기존 시점을 유지하면 M1~M6 동안 추가되는 Dockerfile이 검사 없이 누적됨.

### 8-6. 알려진 개선 과제 (보안성 검토 단계로 이관)

- **SSH 포트 외부 노출**: GitHub Actions 러너의 출발지 IP가 고정되지 않아 1차에는 키 인증만으로 운영. 보안성 검토 단계에서 Tailscale 또는 클라우드 IAP 터널로 **SSH 공개 노출 제거**를 개선 과제로 수행.
- **시크릿 관리 고도화**: VM `.env` → 클라우드 Secret Manager 이관 검토.
- **보안 스캔 gate 전환**: report-only → Critical/High 차단.
- **DAST**: OWASP ZAP 기본 스캔을 배포 후 점검 단계에서 수행.
- **GitHub Actions 커밋 SHA 고정**: 태그(`@v4`) 대신 SHA로 고정해 공급망 공격 대비 (구현 M0에서 제기, 2026-09-28).
- **해시체인 외부 앵커링** (구현 M1에서 제기, 2026-09-29): 해시체인만으로는 ①끝부분 레코드 삭제 ②권한자의 전체 재계산을 탐지하지 못함 → 체인 머리(최신 `id`·`hash`)를 DB 밖(WORM 저장소, 외부 로그 등)에 주기 기록. 상용 솔루션의 WORM 백업(5절 INFOSAFER)과 같은 취지. 상세는 [[DB스키마.md]] 3-5 "알려진 한계"
- **`access_log` TRUNCATE·DELETE 방어** (M1, 2026-09-29): 트리거는 UPDATE만 차단하며, 테이블 소유자는 TRUNCATE·DELETE가 가능 → `BEFORE TRUNCATE`(및 파기 롤 외 `BEFORE DELETE`) 트리거 검토. 단 소유자는 트리거 자체도 제거할 수 있으므로, 근본 대응은 외부 앵커링과 함께 봐야 함
- **append 경로 강제** (M1, 2026-09-29): 앱 계정이 append 함수를 거치지 않고 직접 INSERT하는 것을 DB가 막지 못함(검증 시 체인 불일치로 사후 탐지는 됨) → `SECURITY DEFINER` append 함수 + 앱에는 EXECUTE만. M1에서는 정규화 로직 이중 구현(SQL·Python) 위험 때문에 기각
- **HMAC 신·구 키 병행** (M1, 2026-09-29): [[API명세서_시스템간.md]] 1-2 #4가 규정하지만 Skeleton은 출처당 키 1개 → 키 교체 시 무중단 전환을 위해 구현
- **로그인 실패 제한의 한계** (구현 M2에서 제기, 2026-09-30): ①잠금 해제가 스크립트뿐이고 시간 경과로 풀리지 않음 → 일부러 틀려 정상 사용자를 잠그는 서비스 거부 가능 ②계정 단위로만 계산 → 여러 계정에 흔한 비밀번호를 대입하는 password spraying 미탐지 ③IP 단위 제한 없음 ④존재하지 않는 ID 대입은 Argus에 보이지 않음(정책정의서 4-3의 대가)
- **JWT 로그아웃 후 토큰 유효** (M2): 로그아웃해도 토큰은 만료(30분) 전까지 유효 → 서버 측 폐기 목록 또는 세션 저장소 검토
- **취급자 명부 소속 이력** (M2): Argus 명부는 현재 상태만 보유 — 부서 이동 후 과거 기록을 조회하면 현재 소속으로 보임. 탐지는 수 분 내 판정·`log_summary`·`rule_snapshot`으로 보완. 필요 시 명부 이력화
- **DB 접속 토큰 즉시 폐기 불가** (2026-10-05): 서명 토큰이라 발급 후 1시간 안에는 되돌릴 수 없다. 게이트웨이가 연결 시 계정 상태(퇴직·잠금)를 재확인하고 퇴직자 룰이 잡지만, **이미 맺은 연결**은 만료까지 유지된다 → 폐기 목록(`jti` 차단)은 v0.2 검토
- **게이트웨이 자체 서명 인증서** (2026-10-05): `sslmode=require`는 암호화만 하고 서버 인증서를 검증하지 않아 **중간자 공격에 열려 있다** → 운영 배포 시 사설 CA 배포 + `verify-full` 또는 공인 인증서
- **relay ↔ argus-api 구간 평문(http)** (M2): 도커 내부망 통신. HMAC으로 무결성·인증은 확보되나 기밀성은 내부망에 의존 — API명세서 1-1은 HTTPS 전제
- ~~**DB 직접 접속 미기록** (M2): DBeaver 등으로 DB에 직접 접속한 조회는 Agent가 기록하지 못함 — 6절의 2단계(pgaudit) 범위~~ → **기능 레이어 8 게이트웨이 중계로 해소**(3-4절, 2026-10-05 설계 확정). 남는 한계는 아래 "2티어 한계"
- **2티어 한계** (2026-10-05 설계 확정 시 도출):
  - **공용 계정 = 플랫폼 DB 소유자**: 게이트웨이로 접속한 사람은 모든 테이블(outbox·operator·토큰 발급 기록 포함)을 읽고 고칠 수 있다. 명령어 통제·DB 롤 분리는 v0.2. v0.1은 **행위가 전부 기록된다**는 것으로 사후 통제
  - **3티어 outbox 노출**: 위와 같은 이유로 DB 경로에서 3티어 접속기록(전송 전 outbox 행)을 지우거나 가짜 행을 넣을 수 있다. 3티어 outbox는 "사람이 업무 DB에 직접 못 들어온다"는 전제의 설계였고, 2티어가 그 전제를 바꿨다. 행은 전송 즉시 지워져 노출은 수 초이고 그 행위 자체는 게이트웨이가 기록한다(2티어 기록은 게이트웨이 자체 버퍼라 해당 없음). 탐지 룰 후보 "DB 경로로 보안 테이블 접근"(정책정의서 1-3). **⭐ v0.2 필수 과제(사용자 지정): 3티어 버퍼를 DB 밖(platform-api 볼륨)으로 이전** — 상용 WAS Agent도 업무 DB가 아닌 로컬 큐에 버퍼링. 이전 시 "적재 실패 → 응답 차단(fail-closed)" 보장을 로컬 저장소 기준으로 다시 만들어야 함 (2026-10-05, 11절 미결)
  - **정보주체 미특정**: ~~`id` 없는 SELECT, PK 아닌 조건의 UPDATE·DELETE는 회원번호를 특정하지 못하고 건수·원문 참조만 남는다~~ → 2026-10-06 회원번호 추출(②) 보류로 **모든 DB 기록이 미특정**(건수 + 원문 참조). 안내서 해석상 원문 SQL 기록으로 "처리한 정보주체 정보"를 갈음하되, 책임추적성 조치(시점 백업)가 없어 **부분 충족**이다. 원문 저장소가 사실상 접속기록의 일부가 되므로 보관 기간·무결성·열람 통제도 접속기록 수준이어야 한다(3-4 "정보주체 기록 방식")
  - **게이트웨이 원문 저장소**: 매개변수에 개인정보가 실릴 수 있음 — 접근은 볼륨 마운트로만 제한, 열람 기록·파기 배치는 v0.2
  - **접속지(IP)**: 로컬 Docker에서는 DB 툴 접속 IP가 도커 브리지 주소로 보인다(3-2 화면 서버와 같은 성격의 로컬 한계)

## 10. 구현 작업 방식 (2026-09-23)

| 역할 | 도구 | 하는 일 |
|---|---|---|
| 코드 작성·실행·테스트·커밋 | **Claude Code** (Claude 데스크탑 앱 Code 탭, 사용자 Windows PC의 레포 폴더) | `CLAUDE.md`와 `docs/`를 읽고 마일스톤 단위로 구현, 세션마다 `docs/implementation-log.md` 작성 |
| 기록·설계 변경 판단·검토 | **Cowork "구현" 방** (레포 폴더 연결) | 구현 로그를 읽어 `진행기록.md` 동기화, 설계 변경 시 원본 문서 개정, 설계 대비 검토 |

- Claude Code는 claude.ai 프로젝트 문서함을 직접 읽지 못하므로 `CLAUDE.md` + `docs/` 사본이 다리 역할을 한다.
- 설계 문서의 **원본은 claude.ai 프로젝트**다. 레포의 `docs/`는 사본이며 직접 수정하지 않는다.
- Cowork "구현" 방은 매일이 아니라 **마일스톤 완료 시·설계 변경 발생 시**에만 연다.
- 사용자 PC 준비물: Git for Windows, Docker Desktop(WSL2), GitHub 계정 + GitHub CLI(`gh`, 로그인은 사용자가 직접), VS Code(선택).
