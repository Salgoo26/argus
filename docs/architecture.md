## 1. 결정 요약

| 항목 | 결정 | 비고 |
|---|---|---|
| 기술 스택 | **플랫폼·Argus 모두 Next.js(프론트) + FastAPI(백엔드, Python)** | 두 시스템의 스택 일관성. 플랫폼만 Next.js 풀스택으로 가볍게 가는 혼합안은 기각 |
| 레포 | 모노레포, **GitHub 공개 레포** | 실제 개인정보 없음(시드 100% 가상). 공개 레포라 CodeQL·시크릿 스캔·push protection·Dependabot 무료 |
| DB | **플랫폼 DB / Argus DB 완전 분리** (PostgreSQL 컨테이너 2개) | Argus는 플랫폼 업무 DB에 접근하지 않음 (1단계 기준). 한 인스턴스에 DB만 나누는 안은 슈퍼유저 하나가 양쪽을 만질 수 있어 기각 |
| 시스템 간 연결 | ① **접속기록 수집 API** ② **취급자 동기화 API** ③ **보호 대상 등록부 동기화**(게이트웨이 → Argus DB 구조 목록, Argus → 게이트웨이 등록부) | 세 통로 외 연결 없음. Argus는 플랫폼 DB에 접근하지 않는다. 외부로 나가는 통신은 웹 푸시 발송(브라우저 푸시 서비스)뿐 — 2-2절 |
| 시스템 간 인증 | **HMAC-SHA256 서명** + timestamp(±300초) | 인증 + 전송 중 위·변조 탐지 + 재전송 방지. API명세서 1-2절 |
| 접속기록 수집 방식 | **에이전트형 미들웨어** — 상용 솔루션의 WAS Agent 방식을 FastAPI로 재현 | 3절 |
| 유실 대비 | **outbox 테이블 + relay worker + event_id 멱등 수신**. outbox 적재는 **업무와 별도 트랜잭션** + 결과(성공/실패) 필드 기록 | §8③ 분실 방지. 실패한 시도도 감사 대상으로 남기기 위함 |
| 접근 경로 | 1단계 APP(백오피스 경유) / 2단계 DB(직접 접근) | 요구사항정의서 1-2절. 스키마에 `access_path` 필드 |
| DB 직접 접근 수집 방식 | **DB 접근 게이트웨이(프록시형) 중계** — DB 툴 ↔ `db-gateway` ↔ platform-db. 상용 DB 접근제어(DBSafer 등)와 같은 구조. 정보주체는 결과 열에서 회원번호를 추출(SQL 파싱 없음) | 3-4절. **pgaudit 감사로그 수집안은 폐기**(공용 계정 뒤의 실사용자를 알 수 없고, 조회 결과에서 정보주체를 뽑을 수 없음) |
| 보호 대상 판정 출처 | **Argus 보호 대상 등록부**(담당자가 분류, 관리 화면은 v0.2에서 노출) — 게이트웨이가 5분마다 받아 데이터 유형·회원 식별 열 판정에 쓴다. 받지 못하면 마지막 등록부, 한 번도 못 받았으면 고정 표(fail-closed) | 3-4절 "보호 대상 등록부 연동" |
| 알림 | **화면 알림(30초 확인) + 웹 푸시(급한 건만)**. 웹 푸시는 RFC 8291·8292를 `cryptography`로 직접 구현, 페이로드는 종류·심각도·탐지건 번호만 | 2-1·2-2절. 이메일 알림은 v0.2 |
| 원장 보호 (§8③) | append-only(UPDATE·DELETE·TRUNCATE 트리거) + 해시체인 + 점검 보고서의 원장 기준점(마지막 id·해시) | 2-4절. 소유자·슈퍼유저의 트리거 해제는 출력한 보고서로 사후 대조 |
| DB 접속 인증 | 관리자 화면에서 **DB 접속 토큰** 발급(1시간 고정, 사유 입력 없음) → DB 툴에 `사용자 = 본인 플랫폼 아이디`, `비밀번호 = 토큰` → 게이트웨이가 검증 후 **공용 계정**으로 중계. DB에 개인 계정을 만들지 않음 | 3-4절. 임시 DB 계정(Vault식 동적 자격증명)은 게이트웨이 우회가 가능해 기각 |
| 배포 형태 | **클라우드 VM 1대 + Docker Compose** | Vercel+VPS 하이브리드 검토 후 기각 — 7-1절 |
| 클라우드 | **컨테이너 기반 클라우드 VM(업체 미정)** | 파이프라인은 업체와 무관하게 동작 — 7-3절 |
| 리버스 프록시 | **Caddy** | HTTPS 자동 발급·갱신, 설정 간결. rate limit 부재는 앱 레벨 로그인 실패 제한으로 대체 |
| CI/CD | **GitHub Actions + GHCR**, 보안 스캔은 **report-only로 시작** | 8절 |
| 관리자 인증 | **JWT(HS256) `HttpOnly`·`SameSite=Strict` 쿠키, 30분 미사용 시 만료**(요청마다 재발급), 매 요청 계정 상태(퇴직·잠금) 재확인. 로그인 5회 연속 실패 시 잠금 | 안전조치기준 §5⑥(인증 실패 시 접근 제한)·§6④(일정 시간 미사용 시 접속 차단). 서버 세션은 [S] 스키마에 세션 테이블이 없어 기각. 정책정의서 4-3 |
| 권한 관리 | 플랫폼은 **역할(ADMIN·OPS·CS·MARKETING) → 기능 표**를 서버가 검사(거부 403도 접속기록 `FAILURE`). 플랫폼·Argus 모두 계정 부여·변경·말소에 사유를 받고 권한 이력(append-only)을 남긴다(Argus 계정 관리 화면은 v0.2에서 노출) | 안전조치기준 §5①(최소 권한)·§5③(권한 부여·변경·말소 내역). 2-3절 |

## 2. 시스템 구성

```
┌──────────────── 플랫폼 ────────────────┐        ┌──────────────── Argus ────────────────┐
│                                        │        │                                       │
│  platform-web (Next.js)                │        │  argus-web (Next.js)                  │
│   └ 고객 UI / 관리자 UI                  │        │   └ 정보보호 담당자 / 취급자(소명) UI     │
│         │                              │        │         │                             │
│  platform-api (FastAPI)                │        │  argus-api (FastAPI)                  │
│   ├ 업무 API                            │        │   ├ 수집 API  ◀──────────── ① ─────┐  │
│   ├ [Agent] 접속기록 미들웨어 ──┐         │        │   ├ 취급자 동기화 API ◀─── ② ─────┐ │  │
│   │                            ▼        │        │   ├ 탐지·소명·보고 API              │ │  │
│   │                      [outbox 테이블]  │        │   └ (argus-worker) 탐지·기한 순찰    │ │  │
│  platform-relay ───────────────────────┼── ① ──┼─────────────────────────────────┘ │  │
│   (취급자 변경 이벤트) ──────────────────┼── ② ──┼───────────────────────────────────┘  │
│  db-gateway (2티어) ───────────────────┼── ① ──┼──▶ 같은 수집 API (access_path=DB)   │
│   └ DB 툴 ↔ platform-db 중계 + 자체 버퍼 │        │                                       │
│     └ 구조 목록 전송·등록부 수신 ──────┼── ③ ──┼──▶ 보호 대상 등록부                  │
│         │                              │        │         │                             │
│   [platform DB]                        │        │   [argus DB] ← 접속기록 원장            │
│    회원·주문·결제·문의·취급자·outbox      │        │    (append-only + 해시체인)            │
└────────────────────────────────────────┘        └───────────────────────────────────────┘
```

- Argus의 접속기록 원장은 **argus DB**다. 플랫폼 outbox는 전송 확인 후 삭제되는 임시 버퍼일 뿐이다.
- 플랫폼 관리자가 Argus 원장을 수정할 수 없으므로, DB 분리 자체가 §8③ 무결성·직무분리에 유리하다.
- ③ 보호 대상 등록부 동기화는 게이트웨이가 시작하는 요청만 있다(구조 목록 `POST /ingest/v1/db-schema`, 등록부 `GET /ingest/v1/protection-registry`, 둘 다 출처 `PLATFORM` HMAC). Argus가 플랫폼 쪽으로 먼저 연결하는 통로는 없다(3-4절).
- `argus-worker`는 탐지 순찰마다 소명 기한 임박·초과를 판정하고 웹 푸시 대기분을 보낸다(2-1·2-2절). 보관기간 만료 파기 배치는 v0.2다.
- `platform-relay`와 `argus-worker`는 각각 API와 **같은 이미지를 쓰되 실행 명령만 다른 별도 컨테이너**다. API 프로세스를 여러 개 띄워도 배치·전송이 중복 실행되지 않게 하기 위함이다.

### 2-1. 알림과 소명 기한

받는 사람과 심각도별 수단(화면 알림 / 웹 푸시)은 [정책정의서](policy.md) 3-6, 소명 기한 규칙은 3-4가 정한다. 여기서는 구조만 다룬다.

| 항목 | 설계 |
|---|---|
| 알림 생성 | 탐지 배치·상태 전이와 **같은 트랜잭션**에서 `notification` 행을 만든다 — 업무는 바뀌었는데 알림만 빠지는 일이 없게. 행에는 본문이 없다(받는 사람·종류·탐지건 번호·심각도·차수·읽음 시각). 같은 (사람, 종류, 탐지건, 차수)는 유일성 제약으로 한 번만 생긴다 — 순찰이 같은 기한을 다시 판정해도 쌓이지 않는다 |
| 화면 알림 | argus-web 헤더의 배지·알림 목록이 접속해 있는 동안 30초마다 `GET /api/notifications`(최근 30개 + 안 읽은 수)를 확인한다. 접속하지 않은 동안 생긴 알림은 다음 접속 때 배지에 쌓여 있다. 클릭하면 해당 탐지건으로 간다 |
| 자체 접속기록 | 알림 API는 Argus 자체 접속기록에서 제외한다 — 정보주체를 처리하지 않고, 30초 확인이 원장을 채우지 않게. 알림이 가리키는 탐지건을 열면 그 조회가 `READ`로 남는다 |
| 소명 기한 | 소명 요청 때 `explanation.due_at` = 요청 시각 + `setting.explanation_due_days`(기본 7일). 재요청은 다시 7일 |
| 기한 순찰 | argus-worker가 탐지 순찰마다 현재 차수의 미제출 소명 요청(탐지건 상태 `REQUESTED`)을 보고, 남은 시간이 24시간 이하면 임박, 지났으면 초과 알림을 만든다. 기한을 넘긴 뒤 처음 판정하면 초과만 만든다. 탐지건 상태는 바꾸지 않는다(판단은 담당자). 판정 시각이 순찰 시각이라 알림은 탐지 주기만큼 늦을 수 있다. 기한 판정·푸시 발송이 실패해도 탐지 순찰은 계속한다 |
| 보고서 | 점검 보고서에 기한 초과 건수가 실린다 |

### 2-2. 웹 푸시

Argus 탭이 닫혀 있어도 브라우저가 켜져 있으면 받는 급한 알림이다. 화면 알림이 주 수단이고 웹 푸시는 추가 수단이다.

```
[argus-api / argus-worker] ──HTTPS(VAPID 서명 + 암호문)──▶ [브라우저 제조사 푸시 서비스] ──▶ [브라우저 서비스 워커 sw.js] ──▶ 알림 표시 → 클릭 시 Argus 로그인 → 탐지건 화면
```

| 항목 | 설계 |
|---|---|
| 구독 | 사용자가 알림 목록의 "알림 받기"로 허락하면 브라우저 구독(주소·공개키 `p256dh`·인증 비밀 `auth`)을 `POST /api/push/subscriptions`로 등록한다(`push_subscription`). 서비스 워커는 `argus-web/public/sw.js`. 사용자가 끄면 `POST /api/push/unsubscribe`로 지우고 브라우저 구독도 해제한다 |
| 브라우저 구독 맞추기 | 서버 구독과 브라우저 구독이 어긋나지 않게 화면이 맞춘다. 로그아웃 때 브라우저 구독도 해제한다 — 같은 브라우저를 쓰는 다음 사람에게 "받는 중"으로 보이지 않게(다음 사람은 "알림 받기"를 직접 누른다). 로그인한 계정이 정해지면 브라우저에 남은 구독을 지금 계정으로 다시 등록한다 — 로그아웃 없이 세션이 끝난 뒤(30분 미사용) 다시 로그인하면 화면은 "받는 중"인데 서버에는 구독이 없는 상태가 되기 때문이다. 서버의 VAPID 공개키가 바뀌었으면 옛 키로 만든 구독은 받을 수 없으므로 해제하고 "알림 받기"를 다시 누르게 한다 |
| 발송 대상 | 알림 중 (종류, 심각도)가 웹 푸시 대상인 행에 `push_pending`을 표시한다. 수동 소명 요청 직후 응답 뒤 백그라운드에서, 그리고 worker 순찰마다 대기분을 보낸다. 행 잠금(`FOR UPDATE SKIP LOCKED`)으로 두 곳이 같은 알림을 보내지 않는다. 활성 계정의 구독에만 보낸다 |
| 시도 | 한 번만 시도한다. 푸시 서비스가 404·410이면 구독을 지운다. 로그아웃·계정 비활성화·명부 퇴직 동기화 때도 그 사용자의 구독을 지운다 |
| 페이로드 | 제목 "Argus", 본문은 종류 문구와 심각도(예: "소명 요청이 있습니다 (심각도 상)"), 클릭 주소 `/detections/{id}`. 종류·심각도·탐지건 번호만 싣고 회원번호·취급자 이름·룰 상세는 넣지 않는다. 내용은 암호화되어 푸시 서비스가 볼 수 없지만, 알림이 언제 갔는지는 푸시 서비스에 남는다 |
| 직접 구현 | 웹 푸시 라이브러리(pywebpush)를 쓰지 않고 VAPID(RFC 8292, ES256 JWT)와 내용 암호화(RFC 8291, aes128gcm RFC 8188)를 이미 쓰는 `cryptography`·PyJWT로 구현했다. 새 의존성(HTTP 클라이언트 등)을 늘리지 않고, 이미 검증해 쓰는 암호 라이브러리만으로 처리하기 위해서다. 정확성은 테스트에서 구독자 쪽 RFC 8291 복호화와 VAPID 서명 검증으로 확인한다 |
| SSRF 차단 | 구독 주소는 알려진 브라우저 푸시 서비스의 https 주소만 받는다 — `fcm.googleapis.com`(Chrome·Edge), `updates.push.services.mozilla.com`·`*.push.services.mozilla.com`(Firefox), `web.push.apple.com`·`*.push.apple.com`(Safari), `*.notify.windows.com`(WNS). 포트 443, 사용자 정보 없는 주소만. 저장할 때 검사하고 보내기 직전에 다시 검사한다 — 서버가 사용자가 넣은 임의 주소로 요청을 보내는 통로가 되지 않게 |
| 키 | `ARGUS_VAPID_PUBLIC_KEY`·`ARGUS_VAPID_PRIVATE_KEY`·`ARGUS_VAPID_SUBJECT`(argus-api·argus-worker만, 8-3). 둘 다 비면 웹 푸시만 꺼지고 화면 알림은 그대로다. 하나만 있거나 짝이 맞지 않으면 기동을 거부한다(조용히 틀리지 않게). 키 생성은 `python -m app.scripts.vapid_keys` |
| 네트워크 | argus-api·argus-worker에서 위 푸시 서비스로 나가는 https(443)를 운영 방화벽에서 허용한다. 브라우저는 `http://localhost`를 예외로 허용하고, 운영은 HTTPS가 전제다 |

### 2-3. 역할별 접근 범위와 권한 이력

플랫폼 관리자 기능은 역할로 나누고, 플랫폼·Argus 모두 계정 권한의 부여·변경·말소를 사유와 함께 이력으로 남긴다(안전조치기준 §5①③). 정책은 [정책정의서](policy.md) 4-5(플랫폼)·4-6(Argus).

**플랫폼 역할 → 기능 표** (`platform-api` `app/auth/deps.py`의 `PERMISSIONS`)

| 기능 | ADMIN | OPS | CS | MARKETING |
|---|---|---|---|---|
| 회원 목록·상세·검색 | ✅ | ✅ | ✅ | ✅ |
| 주문, 1:1 문의(답변 포함) | ✅ | ✅ | ✅ | — |
| 환불계좌 전체 보기 | ✅ | ✅ | ✅ | — |
| 회원 CSV 다운로드 | ✅ | ✅ | — | — |
| DB 접속 토큰 발급(메뉴 "DB 직접 접근") | ✅ | ✅ | — | — |
| 계정·권한 관리 | ✅ | — | — | — |

- 서버가 라우트마다 역할을 검사해 403 `FORBIDDEN`을 돌려준다. 거부는 행위자를 기록한 뒤에 일어나므로 접속기록 `FAILURE`로 Argus 원장에 간다(권한 밖 시도가 점검 대상이 된다). 화면은 `/admin/auth/me`의 `permissions`로 메뉴·버튼을 숨기지만 판단은 언제나 서버가 한다. 마케팅의 회원 상세에는 최근 주문을 싣지 않는다(주문 접근이 없는 역할에게 우회로 보여 주지 않게).
- **플랫폼 계정·권한 관리**(ADMIN, `/admin/accounts`): 부여(임시 비밀번호를 응답에서 한 번만 보이고 argon2id 해시만 저장, 첫 로그인 때 비밀번호 변경 강제 — 그전에는 `/me`·비밀번호 변경·로그아웃 외 403 `PASSWORD_CHANGE_REQUIRED`), 변경(역할·팀), 말소(퇴직). 같은 트랜잭션에서 권한 이력과 Argus 명부 동기화 이벤트(outbox, 역할 값은 보내지 않음)를 남긴다.
- **Argus 계정 관리**(담당자, `/api/users`. 관리 화면 메뉴 "계정"은 v0.2에서 노출 — API·권한 이력·운영 스크립트는 동작한다): 담당자로 전환, 취급자로 전환(명부 연결이 있는 계정만), 비활성화, 재활성화(명부에서 재직 중일 때만), 잠금 해제. 비밀번호는 화면에서 다루지 않는다. 운영 스크립트 `create-officer`·`unlock`도 `--reason`이 필수이고 같은 이력을 남긴다(처리자 = 운영 스크립트). 명부 동기화가 만들거나 막은 계정도 이력에 남는다(처리자 = 시스템).
- 공통: 모든 변경에 사유 필수, 본인 계정 변경 불가(403 `SELF_CHANGE_FORBIDDEN` — 자기 권한 상승 방지).

| 권한 이력 | 위치 | 구분 | 보호 |
|---|---|---|---|
| `operator_permission_history` | 플랫폼 DB (마이그레이션 0009) | GRANT·CHANGE·REVOKE, 변경 전·후 역할·팀·재직 상태, 사유, 처리자, 일시 | UPDATE·DELETE 트리거로 거부. 기존·시드 계정은 GRANT "초기 계정" |
| `argus_user_history` | Argus DB (마이그레이션 0020) | GRANT·CHANGE·REVOKE·RESTORE·UNLOCK, 변경 전·후 역할·상태, 사유, 처리자, 일시 | UPDATE·DELETE 트리거(소유자 포함), 앱 계정은 SELECT·INSERT만. 계정 행이 정리돼도 남도록 FK 없이 아이디를 함께 저장 |

- 계정·권한 화면과 비밀번호 변경은 회원 개인정보 처리가 아니라 접속기록에서 제외한다(`@access_log_exempt`) — 권한 이력이 증적이다(룰 변경 이력과 같은 방식).
- 직원 정보 테이블(`operator`·`operator_permission_history`)은 보호 대상 등록부의 데이터 유형 분류 대상이 아니다 — 분류 기준은 정보주체(회원)다(3-4).
- 남은 한계(8-6): 권한 이력은 TRUNCATE를 막지 않는다(원장만 TRUNCATE까지 막음). 보관 3년 뒤 파기는 v0.2. 플랫폼 계정 잠금 해제는 아직 스크립트다. 역할이 바뀌어도 이미 발급된 DB 접속 토큰은 만료까지 쓸 수 있다.

### 2-4. 원장 보호 (§8③)

| 층 | 막거나 잡는 것 | 구현 |
|---|---|---|
| DB 권한 | 앱 계정의 수정·삭제 | 앱 계정에 UPDATE·DELETE·TRUNCATE 권한 없음 |
| 트리거 | 소유자를 포함한 수정·삭제 | UPDATE 행 트리거(0002), DELETE 행 트리거 + TRUNCATE 문장 트리거(0017 — TRUNCATE는 행 트리거를 거치지 않는다) |
| 해시체인 | 중간 행의 수정·삭제·끼워 넣기 | 단일 append 함수가 체인을 이어 붙이고, 검증 스크립트와 보고서 생성이 전체를 재계산 |
| 보고서 기준점 | 끝부분 삭제, 권한자의 전체 재계산 | 점검 보고서 스냅샷 `integrity`에 `total`·`last_id`·`last_hash`. 다음 보고서가 직전 보고서의 마지막 행이 같은 해시로 남아 있는지 대조해 일치 / 불일치 / 비교 대상 없음(`MATCH`·`MISMATCH`·`NONE`)을 싣고, 불일치면 보고서 맨 위에 경고 |

- 해시체인만으로는 끝부분 삭제를 잡지 못한다(남은 체인이 그대로 이어진다). 직전 보고서의 기준점과 대조하면 체인 검증은 통과해도 불일치로 드러난다.
- **한계와 운영 전제**: 테이블 소유자·슈퍼유저는 트리거를 끌 수 있다(`ALTER TABLE … DISABLE TRIGGER`). 보고서도 같은 argus DB에 있으므로, 보고서를 출력해 결재문서(관리대장)에 붙이는 운영을 전제로 한다. 출력본에 남은 마지막 id와 해시(화면·인쇄에 64자 전체)가 DB 밖 기준점이다(안내서 95쪽 "위·변조 확인 정보를 별도 저장매체 또는 관리대장에"). 체인 머리를 WORM 저장소 등에 주기적으로 남기는 외부 앵커링은 v0.2(8-6).
- 보관기간이 지난 기록의 파기 배치(v0.2)는 지금 트리거에 막힌다. 그때 파기 전용 경로(파기 롤만 통과 + 파기 이력에 체인 기준점 기록)로 다시 설계한다.

## 3. 접속기록 수집 구조 (에이전트형 미들웨어)

### 3-1. 상용 솔루션 방식과의 대응

| 상용 솔루션 (Java/WAS) | Argus (Python/FastAPI) | 적용 |
|---|---|---|
| Servlet Filter — 모든 요청 통과 | **ASGI 미들웨어** | 1단계 — 식별자·접속일시·접속지 |
| ThreadLocal — 요청 ↔ SQL 연결 | **contextvars** | 1단계 — 요청 컨텍스트에 사용자·수행업무 보관 |
| URL → 업무 매핑 설정 | **라우트 데코레이터** (`@access_log(action=..., data_category=...)`) + 명시적 제외 `@access_log_exempt("사유")` | 1단계 — 수행업무·데이터 유형. **`/admin` 라우트에 둘 다 없으면 앱 기동 거부** |
| JDBC 드라이버 교체 — SQL·결과셋 가로채기 | **SQLAlchemy 이벤트 훅** | **업그레이드 경로** — 정보주체·건수 자동 추출 |
| BCI (바이트코드 삽입) | 몽키패칭 / OpenTelemetry 자동 계측 | 채택 안 함 |
| 네트워크 미러링 | — | 채택 안 함 |

### 3-2. 한 건이 만들어지는 흐름

1. 취급자가 관리자 UI에서 요청 → Caddy가 실제 접속 IP를 헤더로 전달 → platform-api 미들웨어 진입. 로그인 토큰에서 **식별자**, 요청에서 **접속일시·접속지(IP)** 확보. (접속지 IP는 **Caddy가 넘긴 헤더만 신뢰**하도록 trusted proxy 설정)
   - **화면 서버(Next.js)는 신뢰 프록시가 아니다**: Next.js rewrite 프록시는 원래 요청자 IP를 `X-Forwarded-For`에 넣지 않으면서 **클라이언트가 보낸 `X-Forwarded-For`는 그대로 전달**한다(Next.js 소스로 확인). 화면 서버를 신뢰하면 누구든 헤더 한 줄로 **접속지를 위조**할 수 있다(§2 3호 접속지 정보의 신뢰성 훼손). 따라서 로컬에서는 화면 경유 요청의 접속지가 화면 서버 IP로 기록되고(로컬은 Docker 포트 포워딩으로 원래 IP가 어차피 보이지 않아 실질 손실 없음), 운영에서는 Caddy가 `/api`를 **화면을 거치지 않고 API로 직접** 보낸다.
2. 라우트 데코레이터가 **수행업무·데이터 유형**을 컨텍스트에 기록.
3. 핸들러가 처리 결과로 **처리한 정보주체(회원 내부 PK) 또는 건수**를 컨텍스트에 기록. (1단계는 명시적 기록, 이후 SQLAlchemy 훅으로 자동화 검토)
   - **대상이 정해진 요청**(상세 조회·수정 등)은 업무 로직보다 **먼저** 대상 PK를 기록한다 — 업무가 실패해도 "누구를 대상으로 시도했는지"가 남도록.
   - 정보주체를 기록하기 **전에** 실패한 요청(입력 검증 오류 400 등)은 `subject.count = 0`으로 적재한다.
4. **응답 헤더를 보내기 직전** 미들웨어가 컨텍스트를 모아 **접속기록 1건(event_id, 결과 상태 포함)을 outbox에 적재** — 업무 트랜잭션과 **별도 트랜잭션**. **적재에 실패하면 응답을 막고 500 `ACCESS_LOG_UNAVAILABLE`을 반환한다(fail-closed).**
5. platform-relay가 outbox를 읽어 **Argus 수집 API로 전송** → 성공 응답 시 outbox에서 삭제, 실패 시 재시도.
6. Argus는 event_id로 중복을 걸러 **원장에 append**.

- 로깅 지점은 **관리자 라우트에만** 적용한다(§8① 단서: 정보주체 제외).
- 고객 UI 요청은 미들웨어가 기록하지 않는다.
- 로그아웃은 수행업무 `LOGOUT`(데이터 유형 `NONE`, 정보주체 없음)으로 기록한다 — 접속 시간대를 확인할 수 있게(안내서 FAQ 147). 로그인한 사용자의 로그아웃만 기록하고, 쿠키가 없거나 만료된 요청은 행위자가 없어 기록하지 않는다(응답은 같은 204). Argus 자체 로그아웃도 같은 방식이다.
- 검색은 조건을 URL이 아니라 **POST 본문**으로 받는다(`/admin/{members,orders,inquiries}/search`) — 이름·연락처 같은 검색어가 웹 서버 로그·브라우저 기록에 남지 않게. 접속기록에는 조건의 키 이름만(`request.query_keys`, 정렬) 남고, 정보주체는 결과로 화면에 보인 회원 PK 전부다. 결과가 0건이어도 `READ`로 기록한다(무엇을 찾으려 했는지는 키 이름으로 남는다).
- 역할 검사로 거부된 요청(403)도 `FAILURE`로 적재된다(2-3).
- **`request.path`에는 실제 URL이 아니라 라우트 템플릿**(`/admin/members/{member_id}`)을 싣는다 — 경로 변수에 실린 값이 원장에 남지 않게. 대상 회원은 `subject.ids`로 이미 기록된다.
- 처리되지 않은 예외도 `result=FAILURE`로 적재한 뒤 예외를 다시 던진다.

**적재 시점을 "응답 직후"가 아니라 "응답 헤더 직전 + fail-closed"로 둔 이유**

| 구분 | 내용 |
|---|---|
| 문제 | "응답 직후" 적재는 적재가 실패해도 CSV 등 개인정보가 **기록 없이 이미 나간 상태**가 된다 |
| 원칙 | **기록할 수 없으면 내보내지 않는다** |
| 대가 | 응답이 적재 시간만큼 늦어지고, 플랫폼 DB 장애 시 관리자 기능이 멈춘다 |
| 한계 | 수정(UPDATE)은 업무 커밋이 먼저라 적재 실패 시 "수정은 됐는데 500"이 가능하다 — 보호 효과는 주로 **조회·다운로드** |
| 구현 | 응답 시작 메시지를 가로채야 하므로 순수 ASGI 미들웨어, 가장 바깥에 배치(쿠키 연장 미들웨어보다 바깥) |

**문패 누락 시 기동 거부**: 관리자 라우트를 새로 만들며 데코레이터를 빠뜨리면 기록 누락이 **조용한 사고**가 된다. 기동 시 전 `/admin` 라우트를 검사해 문패(`@access_log`)도 제외 표시(`@access_log_exempt`)도 없으면 앱이 뜨지 않게 해 **즉시 드러나는 실패**로 바꾼다.

### 3-3. outbox 테이블

| 컬럼 (예시) | 용도 |
|---|---|
| `event_id` (UUID) | 기록 고유번호. Argus 중복 판별 기준 |
| `payload` (JSON) | 접속기록 본문 (§2 3호 필드 + 확장 필드 + 결과 상태) |
| `attempts`, `next_retry_at` | 재시도 관리 |
| `created_at` | 적재 시각 |

- 전달 보장: **at-least-once 전송(재시도) + 수신 측 멱등(event_id)** → 결과적으로 정확히 한 번 저장.
- 원래 Transactional Outbox는 업무 변경과 같은 트랜잭션으로 묶지만, Argus는 ①조회(READ)에는 업무 쓰기 트랜잭션이 없고 ②실패한 수정 시도도 감사상 의미가 있어 **별도 트랜잭션**으로 적재한다.

### 3-4. DB 직접 접근 — 게이트웨이 중계 (2티어)

> pgaudit 감사로그 수집안(6절)을 대체하는 설계다.

```
[DB 툴(DBeaver 등)] ──(사용자=플랫폼 아이디, 비밀번호=DB 접속 토큰)──▶ [db-gateway] ──(공용 계정, 연결 1:1)──▶ [platform-db]
                                                                       │
                                                                       ├─ 원문(SQL·매개변수) → [gateway-data 볼륨] (게이트웨이만 마운트)
                                                                       ├─ 접속기록(정규화 SQL 등, access_path=DB) → [게이트웨이 버퍼] (같은 gateway-data 볼륨)
                                                                       └─ 게이트웨이 전송 루프 ──HMAC(출처 PLATFORM)──▶ Argus 수집 API ①
```

| 항목 | 설계 |
|---|---|
| 구조 | **게이트웨이(프록시형) 중계**. PostgreSQL 통신(프로토콜 v3)을 중계하며 SQL과 결과를 가로챈다. platform-db 포트는 **게이트웨이·앱만** 접근 가능(호스트·외부 미공개) → **네트워크 경로 기준으로** 게이트웨이 우회가 구조적으로 불가. 호스트(서버) 관리자 권한으로 컨테이너 안에서 직접 접속하는 경로(`docker compose exec platform-db psql`)는 앱 설계로 막을 수 없다 → 8-6 "2티어 한계" |
| 인증 | 플랫폼 관리자 화면 로그인 → **DB 접속 토큰 발급**(1시간 고정, 시간 내 재사용 가능, 사유 입력 없음) → DB 툴 접속 시 `사용자 = 본인 플랫폼 아이디`, `비밀번호 = 토큰` → 게이트웨이가 토큰을 검증하고 아이디와 토큰의 주인이 같은지 확인 → **공용 계정**으로 DB에 연결 |
| 계정 상태 | 연결 시 플랫폼 계정 상태(퇴직·잠금)를 다시 확인한다(관리자 인증의 "매 요청 계정 상태 재확인"과 같은 원칙). 이를 위해 게이트웨이는 **`operator`를 조회한다** — 사용자 연결과 별개인 게이트웨이 자체 연결로, 조회에 실패하면 접속을 거부한다(fail-closed). 같은 조회로 인증 실패 시 "존재하는 아이디인지"(실패 기록 여부)도 판단한다. 연결은 **토큰 만료 시각에 게이트웨이가 끊는다** |
| 공용 계정 | 플랫폼 DB의 기존 앱 계정. 비밀번호는 게이트웨이·platform-api 컨테이너의 `.env`에만 있고 사람은 모른다. DB에 사람별 계정을 만들지 않는다 |
| 실사용자 귀속 | 토큰 검증은 **연결 단위** → 그 연결의 모든 SQL에 실사용자를 붙인다. **사용자 연결 1개 = DB 연결 1개**(커넥션 풀링 금지 — 풀링하면 SQL과 사람의 대응이 깨짐). DB 자체 로그엔 공용 계정만 보이므로 "누가"의 기준 기록은 **게이트웨이 → Argus 원장**이다 |
| 원장 기록 | 실사용자 + DB 계정 + **정규화 SQL**(리터럴을 `$1`…로 치환, 예: `WHERE email = $1`) + 테이블·컬럼 + 건수 + **원문 참조·지문**. 필드는 [API명세서_시스템간](api-spec.md) 2-3 `context` |
| 원문 저장 (D안) | SQL 원문·매개변수는 **게이트웨이 저장소(`gateway-data` 볼륨)에만** 둔다. Argus는 원문을 갖지 않는다(절대 규칙 #3 유지 — 매개변수에 이메일·이름이 실릴 수 있음). 지문 = SHA-256(원문 레코드)로, Argus 원장의 지문과 대조해 원문의 위·변조·유실을 확인한다. **조회 결과(행 데이터)는 저장하지 않는다** |
| 정보주체 식별 (C안) | **결과 열에서 회원번호 추출 — SQL은 해석하지 않는다.** PostgreSQL 응답의 결과 열 설명(RowDescription)은 각 열이 어느 테이블의 몇 번째 열인지(**테이블 OID·열 번호**)를 알려 준다. 게이트웨이는 보호 대상 등록부의 회원 식별 열(기본값 7개 — `member.id`, `orders`·`member_consent`·`refund_account`·`inquiry`·`shipping_address`의 `member_id`, `retained_member_record.original_member_id`)의 (OID, 열 번호)를 카탈로그에서 한 번 받아 두고, 결과 행(DataRow)에서 **그 열의 값만** 읽는다. 조인·별칭이어도 열의 출처로 찾는다. 확장 쿼리는 Bind의 결과 형식 코드로 텍스트·바이너리(int2·int4·int8)를 가리고, 이름 있는 문장을 다시 실행하면 기억해 둔 열 설명을 쓴다. 찾으면 고유 회원번호를 `subject_ids`(1,000개 상한, 넘으면 `truncated`, `count`는 전체)로, `subject_unresolved = false`. 회원 열이 결과에 있는데 0행이면 "아무도 처리하지 않음"(빈 목록, 미특정 아님). **미특정으로 남는 경우**: 결과에 회원 열이 없는 조회(`SELECT name, email FROM member`), 식·함수·뷰 결과(OID 0), `public` 스키마의 실제 테이블이 아닌 것(사용자가 만든 복사 테이블 등), 결과를 돌려주지 않는 실행(RETURNING 없는 UPDATE·DELETE)·COPY, 값 해석에 하나라도 실패한 실행(일부만 적으면 "이 사람들만 봤다"로 오해되므로 실행 전체를 미특정), 카탈로그 조회 실패(질의는 막지 않는다). 이때는 건수 + 원문 참조로 남는다. 결과 값은 원장에도 원문 저장소에도 남기지 않고 회원번호만 원장으로 간다. 회원 열 OID 조회는 게이트웨이 자체 연결이라 기록하지 않는다 |
| 수행업무 매핑 | `SELECT` → `READ` / `INSERT` → `CREATE` / `UPDATE`·`MERGE` → `UPDATE` / `DELETE`·`TRUNCATE` → `DELETE` / `COPY … TO` → `DOWNLOAD` / 연결 인증 → `LOGIN`(성공·실패. 존재하지 않는 아이디는 기록하지 않음 — API명세서 2-4 v0.4 규칙과 동일). **구현 세부**: `COPY … FROM` → `CREATE` / **안을 볼 수 없는 실행** — `SELECT 사용자함수()` → `READ`, `CALL`·`DO`·SQL `EXECUTE`(준비된 문장 실행) → `UPDATE`, 데이터 유형 `MEMBER_BASIC`, `subject_unresolved = true`(`NONE`이면 미특정 룰에도 안 걸리고 `PAYMENT`면 결제수단 룰 오탐) / `EXPLAIN`은 안의 문장 기준(`ANALYZE`는 실제 실행) / **파서가 못 읽은 문장**은 `READ`·`MEMBER_BASIC`·미특정으로 보수적으로 전송(대개 DB도 거부해 `FAILURE`) / fastpath 함수 호출은 기록할 수 없어 **연결 종료** / DB 연결 종료는 기록하지 않는다(로그아웃 `LOGOUT`은 화면 경유만) |
| 데이터 유형 | 문장이 건드린 테이블로 정한다. 판정 표는 **Argus 보호 대상 등록부**에서 받는다(아래 "보호 대상 등록부 연동"): 테이블의 데이터 유형 = 그 테이블에 등록된 개인정보 컬럼 중 가장 민감한 것. 초기 등록(= 등록부를 받지 못할 때 쓰는 고정 표): `refund_account` → `PAYMENT`(계좌번호는 암호문이지만 결제수단 테이블 접근 자체가 점검 대상) / `member`·`member_consent`·`retained_member_record`·`shipping_address` → `MEMBER_BASIC` / `inquiry` → `INQUIRY` / `orders`·`payment`(PG 거래 정보) → `ORDER` / 그 외 → `NONE`. 여러 테이블이면 **가장 민감한 것**(PAYMENT > MEMBER_BASIC > INQUIRY > ORDER > NONE). v0.1 판정은 테이블 단위다 — 개인정보 컬럼을 건드리지 않은 조회도 그 테이블의 유형으로 기록한다(`SELECT *`·식·함수에서 누락되지 않게 넓게 본다). 직원 계정(`operator`)·권한 이력(`operator_permission_history`) 같은 직원 정보 테이블은 분류 대상이 아니다 — 분류 기준은 정보주체(회원)이고, 이런 테이블은 등록부에 미분류로 남아 담당자가 확인한다(접근은 `NONE`으로 기록) |
| 기록 제외 | **사용자 테이블을 하나도 참조하지 않는 문장** — 시스템 카탈로그(`pg_catalog`·`information_schema`)만 읽는 문장, 테이블 없는 `SELECT`(`SELECT version()`), 시스템 함수 FROM(`pg_get_keywords()`) 등 DB 툴의 메타데이터·상태 조회(Argus 전송만 제외하고 **원문 저장소에는 남긴다**). **단 제외하지 않는 것**: 사용자 스키마의 함수·프로시저 호출, `DO`·`CALL` — 테이블 이름 없이도 내부에서 개인정보 테이블을 읽거나 고칠 수 있음(게이트웨이가 내부를 볼 수 없으므로 `subject_unresolved`로 기록, 매핑은 아래 "수행업무 매핑" 구현 세부). 트랜잭션 제어·`SET`·`SHOW`도 제외. **DDL·DCL은 v0.1에서 게이트웨이 원문 저장소에만** 남기고 Argus 전송은 v0.2(명령어 통제와 함께 — 수행업무 코드에 해당 값이 없음) |
| 보호 대상 등록부 연동 | **등록부 받기**: 기동 시 + 5분마다 `GET /ingest/v1/protection-registry`(빈 본문 HMAC 서명, 출처 `PLATFORM`)로 판정 표(테이블 → 데이터 유형, 회원 식별 열, 등록부 버전)를 받는다. 응답은 키를 정확히 검증해 값 칸이 섞이면 버린다. 받을 때마다 `gateway-data/registry.json`에 저장한다. **받지 못하면**(fail-closed — 기록이 `NONE`으로 빠져 탐지에서 누락되지 않게): 마지막으로 받은 등록부를 쓰고(재기동해도 파일에서 복원), 한 번도 받지 못했으면 고정 표(초기 등록과 같은 내용, 버전 `builtin`)를 쓴다. 실패하면 30초 뒤 다시 시도한다. **DB 구조 목록 보내기**: 기동 시 + 1시간마다 `POST /ingest/v1/db-schema`. `pg_catalog`만 읽어 `public` 스키마 테이블·컬럼의 **이름과 자료형만** 보낸다(데이터 값을 읽는 쿼리는 쓰지 않는다). Argus는 값·예시 칸이 있으면 400으로 거부한다. 등록은 이 목록에 있는 컬럼만 받고(오타 방지), 목록에 있는데 분류되지 않은 컬럼은 "미분류"로 드러난다(새 테이블·컬럼이 점검 대상에서 조용히 빠지지 않게). 등록부 API(`/api/protection*`)와 게이트웨이 판정 연동은 v0.1에 있고, 담당자 관리 화면(메뉴 "보호 대상")은 v0.2에서 노출한다. **버전 기록**: 원장 `context.registry_version`에 판정에 쓴 등록부 버전(`r{이력 id}` 또는 `builtin`)을 남긴다 — 그때 기준으로 왜 그렇게 분류됐는지 설명할 수 있게. DB 이름은 논리 이름 `platform`(실제 DB 이름이 원장·등록부에 퍼지지 않게). 두 요청 모두 게이트웨이 자체 연결·자체 요청이라 접속기록을 남기지 않는다 |
| 기록 실패 시 | **기록할 수 없으면 내보내지 않는다**(3-2와 같은 원칙). 결과 행은 흘려보내되 문장 완료 신호(CommandComplete) 전에 원문 저장·접속기록 적재를 마치고, 실패하면 완료 신호 대신 오류를 보내고 연결을 끊는다 → DB 툴에서는 쿼리 실패가 된다 |
| 구현 언어 | Python(asyncio) — 다른 컴포넌트와 같은 스택. SQL 파싱·정규화는 PostgreSQL 자체 파서를 쓰는 라이브러리 **`pglast` v8.x**(PG18 파서, PG16 문법을 포함) |

**세부 결정**

| 항목 | 결정 |
|---|---|
| 게이트웨이 → Argus 전달 경로 | **게이트웨이 자체 버퍼 + 전송 루프**. 버퍼는 `gateway-data` 볼륨의 로컬 저장소(SQLite 기본안)이고, outbox 개념(event_id·재시도·건별 판정·413 분할·스스로 버리지 않음)과 relay 코드를 그대로 재사용한다. 서명은 **출처 `PLATFORM` 키** → 취급자 매칭 `(source_system, login_id)`이 3티어와 같다. **기각**: 플랫폼 outbox 적재(처음 선택했으나 재검토) — 공용 계정이 DB 소유자라 게이트웨이 접속자가 전송 전 기록을 지우거나 남의 이름으로 위조할 수 있음. 상용 DB 접근제어도 감사 기록을 **감사 대상 DB 밖 자체 저장소**에 둔다(§8③). outbox는 업무 트랜잭션과 기록을 묶기 위한 앱 패턴이라 게이트웨이엔 이유가 없음 |
| 토큰 검증 방식 | **서명 토큰 + 별도 발급 기록**. JWT(HS256) — `sub`=플랫폼 아이디, `jti`=토큰 ID, `aud`=`db-gateway`, `exp`=발급 후 1시간. 서명 키 `DB_GATEWAY_TOKEN_KEY`는 **platform-api·db-gateway에만**, 관리자 로그인 JWT 키와 별개(관리자 쿠키를 DB 비밀번호로 쓰지 못하게). **토큰 검증**은 서명·만료·`aud`·아이디 일치만으로 하고 **발급 기록(`db_access_token`)을 조회하지 않는다**(검증 근거로 쓰면 위장 가능). 계정 상태 확인을 위한 `operator` 조회는 이와 별개다(위 "계정 상태"). 발급 기록은 플랫폼 `db_access_token`(DB스키마 4절)에 감사용으로 남기며 토큰 값은 저장하지 않는다. 발급은 DB 접속 토큰 권한이 있는 역할(ADMIN·OPS, 2-3)만 할 수 있다. **기각**: 토큰을 플랫폼 DB에 저장해 조회 — 공용 계정이 DB 소유자라 게이트웨이로 접속한 사람이 남의 토큰 행을 직접 넣어 위장할 수 있음 |
| DB 툴 ↔ 게이트웨이 구간 TLS | **v0.1부터 적용**. 게이트웨이가 토큰을 읽으려면 DB 툴이 비밀번호를 **평문(cleartext) 방식**으로 보내야 하므로, 게이트웨이가 TLS를 종단하고 **TLS가 아닌 연결은 인증 전에 거부**한다(§7④ 전송구간 암호화). 인증서는 v0.1 자체 서명(키·인증서는 db-gateway에만), DB 툴은 `sslmode=require`. 게이트웨이 ↔ platform-db는 도커 내부망 + SCRAM 인증 |

**구현 순서**: ① 게이트웨이 중계 + 토큰 인증 + 원장 도착(정규화 SQL·테이블·컬럼·건수) + 원문 저장 → ② 회원번호 추출(C안) → ③ 탐지 룰([정책정의서](policy.md) 1-3) → ④ 보호 대상 등록부 연동.
**구현 상태 (v0.1)**: ① 완료 · ② 완료(결과 열 기반 추출, 조건·매개변수 추출은 하지 않음) · ③ 완료(경로별 탐지건, DB 기본 룰 3개, 화면 경로 구분·DB 기록 상세, 경로별 소명 안내, DB 전월 기준선 시드) · ④ 완료.

**3티어와의 차이**: 3티어는 앱이 회원번호를 직접 기록해 누락이 거의 없고, 2티어는 게이트웨이가 결과 열로 **추론**한다. 결과에 회원 열이 없는 조회와 결과를 돌려주지 않는 변경은 "정보주체 미특정"으로 남는다 — 2티어의 구조적 한계다(v0.2: 시점 복구(PITR) 재현, UPDATE·DELETE용 DB 트리거, 유일값 역조회로 축소).

**정보주체 기록 방식 — 결과 열 추출과 남은 숙제**

- **채택**: 결과 열에서 회원번호를 추출한다(위 "정보주체 식별 (C안)"). 결과에 회원 열이 없는 조회와 결과를 돌려주지 않는 변경은 미특정으로 남고, 이 건들은 원문 SQL 기록으로 갈음한다.
- **미특정 건의 보완안(SQL 재현 방식)**: "SQL을 저장해 두고, 사고 시 당시 백업에서 다시 실행해 대상을 찾는다".
- **근거**: 개인정보보호위원회 「개인정보의 안전성 확보조치 기준 안내서」(2024.10) 인쇄 90쪽(PDF 97번째 장). **검색조건문(쿼리)으로 대량의 개인정보를 처리한 경우** 그 검색조건문을 정보주체 정보로 기록할 수 있다. 다만 테이블 변경 등으로 추적이 어려울 수 있으므로 **"해당시점의 데이터베이스를 백업하는 등"** 책임 추적성 확보에 필요한 조치를 해야 한다. 예시: `SELECT * FROM student WHERE name LIKE '김%'`, `UPDATE member SET membership='VIP' …`. (안내서 PDF 원문에서 해당 쪽을 직접 확인)
- **해석 정리**: 안내서 문구는 **대량 처리**를 전제로 한다. Argus 원문 저장소는 매개변수까지 남기므로 단건 조회(`WHERE id = 123`)도 원문만으로 대상이 드러나 이 해석과 어긋나지 않는다. 다만 미특정 건은 Argus 원장(정규화 SQL)만으로 대상을 알 수 없으므로 원문 저장소가 접속기록의 일부로서 보관·무결성·열람 통제를 갖춰야 한다(8-6). 남은 조건은 책임 추적성 조치(시점 백업)이고, v0.2 "사고 조사(재현) 체계"에서 다룬다
- **현재 충족 범위**: 결과에 회원 열이 있는 조회는 회원번호가 원장에 남는다. 미특정 건의 쿼리 기록은 게이트웨이 원문 저장소(SQL·매개변수 + 지문)에 있지만 책임추적성 조치는 없다. 백업이 하루 1회·7일 보관이라 당시 상태를 만들 수 없어 미특정 건은 부분 충족이다(8-6 "2티어 한계").
- **재현 방식의 숙제** (v0.2 후보 "사고 조사(재현) 체계", 10절):
  1. 시점 복구(PITR·WAL 보관)가 필요하다. 하루 1회 백업으로는 문장 실행 시점을 만들 수 없다.
  2. **백업 보관 기간 ↔ 파기 정책 충돌**. 재현이 성립하려면 백업을 접속기록 보관 기간(1년, 5만 명 이상 2년)만큼 둬야 하는데, 이는 "탈퇴 즉시 파기·백업 7일"(8-4, DB스키마 4-1)과 정면으로 부딪친다.
  3. 재현 불가 SQL이 있다. `ORDER BY` 없는 `LIMIT`, `now()`·`random()`, 트랜잭션·세션 상태에 기대는 문장.
  4. 재현 자체도 개인정보 처리다. 격리 환경에서 하고 재현 행위도 기록해야 한다.
  5. 원문 저장소 암호화(안내서 "필요시 암호화").
- **두 방식의 관계**: 추출 방식(C안)은 회원번호만 남기므로 위 1·2번 충돌이 없고, 재현 방식은 미특정 건까지 다룰 수 있지만 백업 보관 정책을 바꿔야 한다. 두 방식은 배타적이지 않다 — v0.1은 추출 + 원문 SQL 보존이고, 재현 체계는 v0.2다.
- **상용 사례 (공개 자료 한도)**: 국내 3티어 접속기록 솔루션(UBI SAFER-PSM)은 요청·응답 분석으로 정보주체를 자동 식별한다. IBM Guardium은 반환 결과 검사 규칙(extrusion rule)을 둔다. 국내 DB 접근제어(DBSafer 등)는 SQL·건수·실사용자 기록 수준까지만 확인됐다 → 사고 조사는 SQL 로그 + 백업 복구에 의존하는 셈이다.

**기각한 대안 (인증)**: A. 웹 로그인 + IP 묶기 — 로컬 Docker에선 모두 같은 내부 IP / B'. 임시 DB 계정(동적 자격증명) — 실계정이라 게이트웨이 우회 가능, 만료 처리(`VALID UNTIL`은 신규 로그인만 검사)·CREATEROLE 보호 부담 / C. PC Agent 재현 — 범위 과대.

## 5. 상용 솔루션 리서치 요약 (2026-09-23)

**공통 원리**: 조회(SELECT)는 DB에 흔적을 남기지 않으므로, 어떤 솔루션도 고객사 업무 DB에서 접속기록을 "읽어오지" 않는다. **행위가 일어나는 지점(WAS·네트워크·DB 통신)에서 가로채 기록을 만들고, 솔루션의 수집 서버로 전송**한다. 업무시스템 경유 접근에 대해서는 **WAS Agent(SW) 방식이 현재 주류**이며, 네트워크 방식은 유실 우려·암호화 트래픽 문제로 선호도가 낮아지는 추세.

| 제품 | 공개된 수집 방식 | 비고 |
|---|---|---|
| **INFOSAFER** (피앤피시큐어) | 3티어: WAS TRACER 센서를 업무시스템에 설치해 "WAS 내 세션정보 파싱" → 운영장비로 직접 전송. 2티어: "DB 통신 파싱", DBSAFER 연동 또는 DB 서버 로그 수집 | DBSCANNER로 DB 내 개인정보 위치 자동 검출. 국정원 검증 암호모듈 + WORM 백업 |
| **UBI SAFER-PSM** (이지서티) | BCI, FILTER, CONTENTS FILTERING, CLOUD FILTERING. Agent(SW) 방식을 주로 사용. "소스 코드 수정 없이 부하 최소화", "OSI 7계층 네트워크 콘텐츠 필터링" | 자사 주장: 24년 연속 매출 1위, 누적 22,781개 시스템 |
| **WEEDS BlackBox Suite** (위즈코리아) | SW: BCI 플러그인 + Java 필터 + JDBC 드라이버 교체 / 네트워크: 콘텐츠 필터링 + 미러링 / DB 로컬로깅 | 자사 주장: 조달청 누적 점유율 1위, 약 1,000개 고객사. 구축 전 ID 체계·DB 정보·개인정보 활용 현황 환경 분석 |

**3-tier 실사용자 식별의 핵심**: 요청 진입점(필터/BCI)에서 세션 사용자를 잡아 요청 스레드에 보관하고, 같은 스레드에서 실행된 SQL·결과셋(JDBC 계층)을 그 사용자에게 연결한다. WAS가 공용 DB 계정 하나로 접속해도 실제 취급자가 식별되는 이유. (벤더 내부 구조는 비공개이며, 이 설명은 각 벤더가 명시한 기술의 일반적 동작 원리에 기반함)

**실무 경험과의 대응**: 작성자는 재직 당시 DBSAFER(DB 접근제어) 연동으로 **개발자의 SQL 직접 접근 기록을 점검**했고, 백오피스 경유 조회·수정 기록은 **쿼리로 추출해 정보보안팀에 제출**만 했다(점검은 팀 내 다른 담당자). → Argus 1단계는 이 "추출 → 전달 → 판단" 수작업을 자동화하고, 2단계는 작성자가 직접 수행했던 DB 직접 접근 점검을 담는다.

**2티어(DB 접근제어) 조사 (공개 자료)**: DBSAFER·쿼리파이 DAC·INFOSAFER(2티어)의 공개 로그 항목은 **쿼리 원문·테이블·컬럼·건수·실사용자** 수준이며, 정보주체 단위 기록은 확인하지 못했다. Argus 2티어(3-4절)는 같은 게이트웨이 구조에 **결과·조건에서 회원번호를 추출**(C안)해 "누가 몇 건"에서 "누가 누구를"로 한 단계 더 간다. `ORDER BY` 없는 `LIMIT`처럼 재실행으로도 대상을 특정할 수 없는 조회가 있어, 결과에서 추출하는 방식이 유일한 방법이다. → **C안은 보류**: v0.1은 상용 DB 접근제어와 같은 수준(SQL·건수·실사용자 + 원문 저장)이다. 3-4 "정보주체 기록 방식".

| 실무 경험 (DBSafer) | Argus 2티어 v0.1 |
|---|---|
| PC Agent로 사번 로그인 | 관리자 화면에서 DB 접속 토큰 발급(Agent 방식은 v0.2) |
| 명령어(DML·DDL·DCL) **범위별 사전 결재** — 쿼리 단위가 아니라 "쓸 수 있는 명령어 범위" 승인 | **v0.2로 이월**(명령어 통제). 결재는 "할 수 있었다"의 근거일 뿐 "왜 했는가"의 근거가 아니므로 **소명은 여전히 필요** |

## 6. 범위 밖 / 한계

- **DB 직접 접속(DBA·개발자의 SQL 툴 접속)**: 앱 레벨 Agent로는 기록되지 않음 → **DB 접근 게이트웨이 중계로 다룬다(3-4절)**. 게이트웨이가 실사용자·정규화 SQL·테이블·컬럼·건수를 기록해 동일 수집 API(`access_path=DB`)로 보낸다. 정보주체는 결과 열에서 회원번호를 추출한다. 처음 검토한 pgaudit 감사로그 수집안은 폐기했다 — 공용 계정 뒤의 실사용자와 조회 결과의 정보주체를 알 수 없음.
- **2티어 v0.2 이월**: 명령어 통제(범위 결재·범위 밖 거부·`FAILURE` 기록·승인 ID 연결) / 권한 그룹·DB 롤 분리(§5③) / Agent 방식 인증 / 정보주체 미특정 축소(시점 복구(PITR) 재현, UPDATE·DELETE용 DB 트리거, 유일값 역조회) / DDL·DCL의 Argus 전송과 DCL(GRANT·REVOKE) 실행 탐지 룰
- **개인정보 자산(테이블·컬럼) 자동 검출(DB 스캔)**: 상용의 DBSCANNER에 해당. v0.1은 게이트웨이가 `pg_catalog`에서 테이블·컬럼 이름과 자료형만 모아 보내고, 등록부에 없는 컬럼을 "미분류"로 드러내는 데까지다(3-4 "보호 대상 등록부 연동"). 분류는 담당자가 한다.
- **v0.2 계획** (8-6·10절에 이미 있는 3티어 버퍼 이전·사고 조사(재현) 체계·해시체인 외부 앵커링 외):
  - 보호 대상: 관리 화면 노출(메뉴 "보호 대상"·"계정"), 컬럼 단위 판정(v0.1은 테이블 단위), 자동 식별(컬럼 이름 패턴·샘플 값 검사로 개인정보를 추정하고 담당자가 확인), 여러 DB·여러 시스템
  - 화면 경유 점검 대상 대조: 화면 경유 수집 지점의 데이터 유형은 코드의 문패(데코레이터)에 적혀 있어, DB 직접 접근의 판정 출처인 보호 대상 등록부와 따로 관리되고 어긋날 수 있다. CI에서 화면별 실제 조회 테이블과 문패를 비교하고, 화면 수집 지점 목록을 현황에 보이고, 최종적으로 문패에는 테이블만 적고 데이터 유형은 등록부에서 가져와 기준을 하나로 만든다
  - 알림: 이메일 알림
  - 원장·이력: 보관기간 만료 파기 배치와 파기 전용 경로(2-4), 권한 이력의 TRUNCATE 차단과 3년 뒤 파기(2-3)
  - 권한: 플랫폼 계정 잠금 해제 화면, DB 접속 토큰 폐기 목록(`jti` 차단)과 연결 때 역할 재확인(8-6)
- **정보주체 자동 추출**: 1단계는 핸들러가 명시적으로 기록. 자동화는 SQLAlchemy 훅 업그레이드 경로로 남김.

| Vercel + Render | 기각 | 배포처 통일 불가, 유휴 시 슬립·DB 보관 기한 등 요금제 제약 |
| Railway (PaaS 통일) | 기각 | 운영 부담은 가장 적으나, 인프라 통제항목이 추상화되어 서버·네트워크 통제를 직접 설계·점검하기 어렵고 2단계 pgaudit 제약 가능성(pgaudit안은 이후 폐기했으나, 게이트웨이 방식도 DB 포트를 게이트웨이에만 여는 **망 구성 통제**가 핵심이라 VM 쪽이 유리) |
| 하이브리드: Vercel(Next.js) + VPS(FastAPI+DB) | 기각 | ①CDN·SSR 이점은 대중 대상 서비스용 — 사용자가 사내 취급자·정보보호 담당자라 무의미 ②Next.js 2개 → 관리 지점 2곳 ③Vercel 경유 요청은 FastAPI에 Vercel IP로 보여 **접속기록의 "접속지 정보" 정확성이 흔들림** ④백오피스·Argus 화면이 기본적으로 인터넷에 공개되어 IP 기반 접근통제가 어려움 ⑤"Vercel 요청만 라우팅"은 브라우저 직접 호출·비고정 출발지 IP 때문에 성립하기 어려움 |
| **VM 1대 + Docker Compose** | **채택** | 배포처 단일화, 로컬=운영 동일 구성, 서버·네트워크·DB 통제를 직접 설계하고 나중에 스스로 점검 가능 |

### 7-2. VM 구성

```
┌──────────── VM 1대 (Linux, RAM 2GB 이상) ─────────────┐
│  클라우드 방화벽: 80/443 외부 오픈, SSH(22)는 키 인증만     │
│   + DB 게이트웨이 포트는 관리자 허용 IP만                  │
│                                                        │
│  Docker Compose                                        │
│   ├ caddy          ← 웹 입구(유일), HTTPS 자동 발급         │
│   ├ platform-web   ├ platform-api   ├ platform-relay   │
│   ├ platform-db    ├ db-gateway     └ gateway-data(볼륨, db-gateway만) │
│   ├ argus-web      ├ argus-api      ├ argus-worker     │
│   ├ argus-db       └ argus-attachments(볼륨, argus-api만) │
│   └ backup (일 1회 pg_dump)                             │
│     ※ DB·API는 내부 도커 네트워크에만 존재, 외부 비노출       │
│     ※ platform-db 포트는 db-gateway·platform-api·relay      │
│       (+ 일회성 migrate·seed)만 내부망으로 접근             │
│       (DB 툴 입구는 db-gateway 하나)                        │
└────────────────────────────────────────────────────────┘
```

| Caddy 역할 | 내용 |
|---|---|
| 라우팅 | `shop.<도메인>` → platform-web(고객 `/`, 관리자 `/admin` — 한 앱) / `shop.<도메인>/api` → platform-api / `argus.<도메인>` → argus-web / `argus.<도메인>/api` → argus-api |
| HTTPS | 인증서 자동 발급·갱신 (§7④ 전송구간 암호화) |
| 접근통제 | 플랫폼 관리자 경로(`/admin`, `/api/admin`)·Argus 전체를 **허용 IP 목록**으로 제한 (허용 IP는 코드가 아닌 서버 설정으로 관리). 고객 화면은 공개. 고객용 앱 분리는 기각(컨테이너 증가) |
| 실제 IP 전달 | 취급자 IP를 헤더로 전달 → 앱은 Caddy만 trusted proxy로 신뢰. **`/api`는 화면 서버를 거치지 않고 API로 직접 라우팅**(3-2 #1) |
| 기타 | 업로드 크기 제한(소명 첨부 5MB), 보안 헤더 |

- **시크릿 배포 범위**: 환불계좌 암호화 키 `PAYMENT_ENCRYPTION_KEY`는 platform-api·platform-seed에만, 첨부 볼륨은 argus-api에만 붙인다 — 컨테이너별 최소 시크릿·최소 마운트.

- **DB 툴 입구 = `db-gateway` 포트 하나**: platform-db의 호스트 포트 공개를 없애고 게이트웨이 포트만 연다. 운영에서는 게이트웨이 포트를 클라우드 방화벽에서 **관리자 허용 IP로만** 연다(Caddy를 거치지 않는 TCP 입구이므로 IP 제한을 방화벽에서 건다). 원문 저장 볼륨 `gateway-data`는 db-gateway에만 붙이고 **백업 대상**에 넣는다(Argus 원장의 지문과 함께 복구돼야 대조 가능).

- 로컬 개발(Walking Skeleton)에서는 Caddy·backup 없이 시작하고 첫 배포 때 추가한다.
- 로컬에서는 브라우저 → 화면 서버(Next.js rewrite, 같은 출처 프록시) → API 구조로 CORS 없이 동작한다.

**배포 체크리스트 — 접속지 신뢰성**
- [ ] Caddy가 클라이언트가 보낸 `X-Forwarded-For`를 **덮어쓰는지**(신뢰 프록시 설정) 확인
- [ ] API의 `*_TRUSTED_PROXIES`가 **Caddy 주소만** 담는지 확인
- [ ] `/api` 경로가 화면 서버를 거치지 않고 API로 직접 가는지 확인
- [ ] 위조 헤더(`X-Forwarded-For: 8.8.8.8`)를 붙인 요청 → 원장에 실제 IP가 기록되는지 실측
- [ ] 보안 헤더(CSP·X-Frame-Options 등)는 Caddy에서 부여

### 7-3. 배포 대상

- 배포 대상은 컨테이너 기반 클라우드 VM이며 업체는 정하지 않았다. Compose 기반이라 어느 VM에서든 같은 구성으로 기동할 수 있고, CI/CD 파이프라인(8절)은 업체와 무관하게 동작한다.
- 운영 방침: 서버를 상시 유지하지 않는다. 기본 제공물은 **시연 영상 + README**이고, 라이브 서버는 시연이 필요할 때 기동한다.
- x86(amd64) VM만 사용하므로 이미지는 amd64 단일 빌드.

## 8. CI/CD 파이프라인

### 8-1. 흐름

> 아래 흐름도는 **목표 상태**다. 항목별 도입 시점은 **8-5를 따른다**(대상 파일·산출물이 아직 없는 항목은 그것이 생기는 시점에 추가).

```
[feature 브랜치] ──PR──▶ ① CI (PR 검사)
                          ├ lint·타입체크 (ruff / eslint·tsc)
                          ├ 테스트 (pytest + Postgres 서비스 컨테이너)
                          ├ 보안 스캔 [report-only]
                          │   ├ gitleaks (시크릿)
                          │   ├ CodeQL (SAST, Python·JS) — GitHub 기본 설정
                          │   └ Trivy config (Dockerfile — compose 파일은 Trivy가 인식하지 않아 대상 외)
                          ├ 도커 빌드 가능 여부 확인 (push 안 함)
                          └ Skeleton 시나리오 E2E — 별도 Compose 프로젝트로 전체 스택 기동 + 시나리오 + 해시체인 검증
        │ merge
        ▼
[main] ──────────────────▶ ② 빌드 & 게시
                          ├ 변경된 앱만 이미지 빌드 (경로 필터)
                          ├ Trivy 이미지 스캔 [report-only, 결과는 Security 탭]
                          └ GHCR에 push (태그: 커밋 SHA)
        │ 릴리스 태그 v*
        ▼
[tag v1.2.0] ────────────▶ ③ 배포 (CD)
                          ├ 해당 SHA 이미지에 버전 태그 부여
                          ├ SSH로 VM 접속
                          ├ DB 백업(pg_dump) → 마이그레이션(Alembic, 일회성 컨테이너)
                          ├ docker compose pull && up -d
                          └ 헬스체크(/healthz) 실패 시 직전 버전 태그로 롤백

[상시] Dependabot — 의존성 취약점 알림 + 업데이트 PR 자동 생성
[상시] GitHub push protection — 시크릿이 포함된 push 자체를 차단
```

### 8-2. 설계 결정

| 항목 | 결정 | 이유 |
|---|---|---|
| 브랜치 | main + feature 브랜치, **1인 개발이어도 PR로 병합** | PR·CI 결과가 그대로 **변경관리 증적**이 됨 |
| 배포 트리거 | **릴리스 태그(v*) 푸시** (main 머지 시 자동 배포 아님) | 서버가 상시 기동 상태가 아니고, 버전 단위 이력·롤백이 명확 |
| 이미지 레지스트리 | GHCR (공개 레포 → 무료) | 이미지에 시크릿이 들어가지 않도록 Trivy가 이미지 내 시크릿도 검사 |
| 보안 스캔 정책 | **report-only로 시작** → 보안성 검토 단계에서 결과를 근거로 조치 → 이후 Critical/High에서 배포 차단(gate)으로 전환 | 기존 방침("보안 조치는 기능 구현 후 별도 점검 단계")과 정합. "파이프라인이 쌓아둔 결과로 취약점을 추적·조치했다"는 증적 확보 |
| DB 마이그레이션 | 배포 시 **백업 → 마이그레이션 → 기동** 순서, 하위 호환되는 변경 위주 | 롤백 시 앱은 이전 이미지로, DB는 백업 복구(수동) |
| 롤백 | 이전 버전 태그로 compose 재기동 | 이미지 태그가 불변이라 재현 가능 |

### 8-3. 시크릿·설정 관리

| 대상 | 보관 위치 |
|---|---|
| VM 접속 SSH 키, 호스트 정보 | GitHub Actions Secrets |
| DB 비밀번호, 플랫폼→Argus HMAC 키, 결제수단 암호화 키(§7②) | **VM의 `.env` 파일**(레포에 없음, 권한 600). 암호화 키는 DB와 분리 보관(§7⑥ 취지) |
| **2티어 시크릿** | 플랫폼 DB **공용 계정 비밀번호**(db-gateway·platform-api만, 사람에게 공유 안 함) / 플랫폼→Argus **HMAC 키(출처 PLATFORM)**를 db-gateway에도 전달 / **DB 접속 토큰 서명 키 `DB_GATEWAY_TOKEN_KEY`**(platform-api·db-gateway만, 관리자 JWT 키와 별개) / **게이트웨이 TLS 키·인증서**(db-gateway만). 모두 `.env` 또는 마운트 파일 — 컨테이너별 최소 시크릿 원칙(7-2) |
| 웹 푸시 VAPID 키 | `ARGUS_VAPID_PUBLIC_KEY`·`ARGUS_VAPID_PRIVATE_KEY`·`ARGUS_VAPID_SUBJECT` — `.env`, argus-api·argus-worker만(2-2) |
| 관리자 허용 IP 목록 | VM의 Caddy 설정 |
| 레포 규칙 | `.env`·키 파일 gitignore, 시드 데이터 100% 가상(Faker), README에 "모든 데이터는 가상" 명시 |

### 8-4. 백업

- 일 1회 `pg_dump` (platform DB, argus DB 각각), **보관 7일** 후 자동 삭제.
- **Argus 첨부 볼륨(`argus-attachments`)도 백업 대상** — DB의 첨부 행(해시)과 파일이 함께 복구돼야 무결성 검사를 통과한다.
- **게이트웨이 원문 볼륨(`gateway-data`)도 백업 대상** — Argus 원장의 원문 참조·지문과 대조할 원문이 함께 복구돼야 한다.
- 백업 파일도 개인정보(가상)·접속기록을 포함하므로 **암호화 저장**.
- **파기 정책과의 관계**: 원본에서 파기된 데이터가 백업에 남는 기간을 보관 주기(7일)로 한정 — 파기 정책 설명 시 함께 명시.
- **2티어 책임추적성과의 충돌**: 안내서는 쿼리로 정보주체를 갈음할 때 "해당 시점 DB 백업 등"을 요구한다. 7일·일 1회 백업으로는 충족하지 못한다. 보관 기간을 늘리면 위 파기 원칙과 충돌한다 → v0.2 "사고 조사(재현) 체계"에서 함께 정한다(3-4 "정보주체 기록 방식", 10절).

### 8-5. 구현 시점

| 시점 | 구현 범위 |
|---|---|
| Walking Skeleton 착수 시 (M0) | ① CI(lint·테스트·gitleaks), CodeQL, Dependabot, push protection |
| **첫 Dockerfile이 추가되는 PR (M1)** | ① **Trivy config + 도커 빌드 가능 여부 확인** 추가 |
| 프론트엔드 앱이 추가되는 PR (M5) | ① eslint·tsc, Dependabot에 npm 생태계 추가 |
| 시나리오 E2E가 생기는 PR (M6) | ① **e2e job** — 실행마다 일회용 `.env`(무작위 값) 생성 → 별도 Compose 프로젝트(`argus-e2e`)로 빈 DB에서 전체 스택 기동 → API 수준 시나리오(화면 서버 경유) + 해시체인 검증 → 볼륨까지 정리. 로컬과 같은 스크립트(`scripts/e2e.sh`)를 써서 README 경로가 CI에서 그대로 검증됨 |
| Skeleton 로컬 동작 후 | ② 이미지 빌드·**Trivy 이미지 스캔**·GHCR |
| 첫 배포 시 | ③ CD, VM 세팅, Caddy, 백업 |

- **원칙: 점검 도구는 점검 대상이 생기는 PR에서 함께 도입한다.** 대상이 없을 때 미리 넣지 않고(빈 스캔·오류 방지), 대상이 생긴 뒤 미루지도 않는다(점검 공백 방지).
- Trivy는 **config(설정 파일 대상, PR 단계)** 와 **image(빌드 산출물 대상, main 빌드 단계)** 로 성격이 달라 도입 시점을 나눈다. config까지 image 스캔 시점("Skeleton 로컬 동작 후")으로 미루면 M1~M6 동안 추가되는 Dockerfile이 검사 없이 누적된다.

### 8-6. 알려진 개선 과제 (보안성 검토 단계로 이관)

- **SSH 포트 외부 노출**: GitHub Actions 러너의 출발지 IP가 고정되지 않아 우선 키 인증만으로 운영. 보안성 검토 단계에서 Tailscale 또는 클라우드 IAP 터널로 **SSH 공개 노출 제거**를 개선 과제로 수행.
- **시크릿 관리 고도화**: VM `.env` → 클라우드 Secret Manager 이관 검토.
- **보안 스캔 gate 전환**: report-only → Critical/High 차단.
- **DAST**: OWASP ZAP 기본 스캔을 배포 후 점검 단계에서 수행.
- **GitHub Actions 커밋 SHA 고정**: 태그(`@v4`) 대신 SHA로 고정해 공급망 공격 대비.
- **해시체인 외부 앵커링**: 해시체인만으로는 ①끝부분 레코드 삭제 ②권한자의 전체 재계산을 탐지하지 못한다. v0.1은 점검 보고서에 원장 기준점(마지막 id·해시)을 싣고 다음 보고서가 대조하며, 출력본을 DB 밖 기준점으로 삼는다(2-4). 남은 과제는 체인 머리를 DB 밖(WORM 저장소, 외부 로그 등)에 자동으로 주기 기록하는 것이다. 상용 솔루션의 WORM 백업(5절 INFOSAFER)과 같은 취지. 상세는 [DB스키마](db-schema.md) 3-5 "알려진 한계"
- **`access_log` TRUNCATE·DELETE 방어**: DELETE 행 트리거와 TRUNCATE 문장 트리거로 소유자까지 막는다(마이그레이션 0017, 2-4). 소유자·슈퍼유저는 트리거 자체를 끌 수 있어 보고서 출력본과의 대조가 운영 전제다. 파기 배치(v0.2)는 파기 전용 경로로 다시 설계한다
- **append 경로 강제**: 앱 계정이 append 함수를 거치지 않고 직접 INSERT하는 것을 DB가 막지 못함(검증 시 체인 불일치로 사후 탐지는 됨) → `SECURITY DEFINER` append 함수 + 앱에는 EXECUTE만. 현재는 정규화 로직 이중 구현(SQL·Python) 위험 때문에 기각
- **HMAC 신·구 키 병행**: [API명세서_시스템간](api-spec.md) 1-2 #4가 규정하지만 Skeleton은 출처당 키 1개 → 키 교체 시 무중단 전환을 위해 구현
- **로그인 실패 제한의 한계**: ①잠금 해제가 시간 경과로 풀리지 않고, 플랫폼은 스크립트로만 푼다(Argus는 계정 API·운영 스크립트, 모두 사유 필수·계정 이력) → 일부러 틀려 정상 사용자를 잠그는 서비스 거부 가능 ②계정 단위로만 계산 → 여러 계정에 흔한 비밀번호를 대입하는 password spraying 미탐지 ③IP 단위 제한 없음 ④존재하지 않는 ID 대입은 Argus에 보이지 않음(정책정의서 4-3의 대가)
- **JWT 로그아웃 후 토큰 유효**: 로그아웃해도 토큰은 만료(30분) 전까지 유효 → 서버 측 폐기 목록 또는 세션 저장소 검토
- **취급자 명부 소속 이력**: Argus 명부는 현재 상태만 보유 — 부서 이동 후 과거 기록을 조회하면 현재 소속으로 보임. 탐지는 수 분 내 판정·`log_summary`·`rule_snapshot`으로 보완. 필요 시 명부 이력화
- **DB 접속 토큰 즉시 폐기 불가**: 서명 토큰이라 발급 후 1시간 안에는 되돌릴 수 없다. 게이트웨이가 연결 시 계정 상태(퇴직·잠금)를 재확인하고 퇴직자 룰이 잡지만, **이미 맺은 연결**은 만료까지 유지된다 → 폐기 목록(`jti` 차단)은 v0.2 검토. 게이트웨이는 연결 때 재직·잠금만 확인하고 역할은 다시 보지 않으므로, 발급 뒤 역할이 DB 접속 토큰 권한이 없는 역할로 바뀌어도 그 토큰은 만료까지 쓸 수 있다
- **게이트웨이 자체 서명 인증서**: `sslmode=require`는 암호화만 하고 서버 인증서를 검증하지 않아 **중간자 공격에 열려 있다** → 운영 배포 시 사설 CA 배포 + `verify-full` 또는 공인 인증서
- **relay ↔ argus-api 구간 평문(http)**: 도커 내부망 통신. HMAC으로 무결성·인증은 확보되나 기밀성은 내부망에 의존 — API명세서 1-1은 HTTPS 전제
- **DB 직접 접속 기록**: DBeaver 등으로 DB에 직접 접속한 조회는 앱 Agent가 기록하지 못한다 → **게이트웨이 중계로 해소**(3-4절). 남는 한계는 아래 "2티어 한계"
- **2티어 한계**:
  - **공용 계정 = 플랫폼 DB 소유자**: 게이트웨이로 접속한 사람은 모든 테이블(outbox·operator·토큰 발급 기록 포함)을 읽고 고칠 수 있다. 명령어 통제·DB 롤 분리는 v0.2. v0.1은 **행위가 전부 기록된다**는 것으로 사후 통제
  - **3티어 outbox 노출**: 위와 같은 이유로 DB 경로에서 3티어 접속기록(전송 전 outbox 행)을 지우거나 가짜 행을 넣을 수 있다. 3티어 outbox는 "사람이 업무 DB에 직접 못 들어온다"는 전제의 설계였고, 2티어가 그 전제를 바꿨다. 행은 전송 즉시 지워져 노출은 수 초이고 그 행위 자체는 게이트웨이가 기록한다(2티어 기록은 게이트웨이 자체 버퍼라 해당 없음). 탐지 룰 후보 "DB 경로로 보안 테이블 접근"(정책정의서 1-3). **⭐ v0.2 필수 과제: 3티어 버퍼를 DB 밖(platform-api 볼륨)으로 이전** — 상용 WAS Agent도 업무 DB가 아닌 로컬 큐에 버퍼링. 이전 시 "적재 실패 → 응답 차단(fail-closed)" 보장을 로컬 저장소 기준으로 다시 만들어야 함 (10절 미결)
  - **정보주체 미특정**: 결과 열에서 회원번호를 추출하지만, 결과에 회원 열이 없는 조회(`SELECT name, email FROM member` 등)·식·뷰 결과, 결과를 돌려주지 않는 UPDATE·DELETE, COPY는 미특정(건수 + 원문 참조)으로 남는다. 안내서 해석상 원문 SQL 기록으로 "처리한 정보주체 정보"를 갈음하되, 책임추적성 조치(시점 백업)가 없어 이 건들은 부분 충족이다. 원문 저장소가 사실상 접속기록의 일부가 되므로 보관 기간·무결성·열람 통제도 접속기록 수준이어야 한다(3-4 "정보주체 기록 방식"). 결과의 고유 회원번호 집합은 메모리 상한이 없고(전송은 1,000개 상한), DBeaver(pgjdbc) 실측은 하지 않았다 — psycopg의 확장 질의·바이너리 결과·재사용 문장 테스트로 대신했다
  - **게이트웨이 원문 저장소**: 매개변수에 개인정보가 실릴 수 있음 — 접근은 볼륨 마운트로만 제한, 열람 기록·파기 배치는 v0.2
  - **접속지(IP)**: 로컬 Docker에서는 DB 툴 접속 IP가 도커 브리지 주소로 보인다(3-2 화면 서버와 같은 성격의 로컬 한계)
  - **토큰 발급 사유 없음**: 소명이 사후 기억에 의존 — 관련 티켓 첨부로 보완
  - **호스트 관리자 경로 우회** (보안성 검토 후보): 서버에서 `docker compose exec platform-db psql`로 접속하면 게이트웨이를 거치지 않아 기록이 남지 않는다. 서버 관리자 권한 경로라 앱 설계로 못 막음 → 대응은 인프라 통제: 서버 접근 인원 최소화(docker 그룹 포함), OS 감사 로그(auditd 등)로 `docker exec` 실행 기록, 서버 접속 자체를 별도 접근통제·기록(ISMS-P 2.6.6 원격접근·2.9.4 로그 관리 관점)
  - **연결당 `LOGIN` 다건**: DBeaver는 한 번 접속에 연결 여러 개(실측 4개)를 맺어 `LOGIN`도 여러 건 남는다 — 연결 단위 귀속의 증거라 v0.1은 모두 기록, 화면·탐지에서 묶어 보이는 것은 v0.2 후보
- **플랫폼 DB 계정 1개(소유자) 운영**: 플랫폼은 감시 대상 시스템(최소 구현)이라 Argus 같은 권한 분리를 하지 않음 — 보안성 검토의 발견사항 후보
- **DEAD 건 운영 알림·재처리 도구 부재**: 현재 ERROR 로그뿐 (API명세서 9절 미결)
- **플랫폼 개인정보 표시제한 미적용 — 위험 수용**: 플랫폼 관리자 회원 목록·CSV에 이름·이메일·전화·주소가 **마스킹 없이** 노출. v0.1은 Argus 기능 우선, 표시제한은 실제 데이터가 있는 플랫폼에 두는 것이 맞아 **보안성 검토 발견사항 → 조치**(마스킹 + 사유 입력 해제, 해제 행위를 Argus 원장에 기록) 사이클로 진행 — 정책정의서 6절
- **고객 로그인 실패 정책·탈퇴 즉시 파기 재확인**: 5회 → 15분 자동 해제가 무차별 대입을 충분히 늦추는지, 즉시 파기와 법정 보존 분리보관의 정합성 — 정책정의서 4-3, DB스키마 4-1
- **플랫폼 기능 구현에서 이월된 점검 항목** (보안 관련은 보안성 검토 단계로):
  - 분리보관 데이터의 **연락처 범위**(이름·이메일·전화) — 최소수집 관점
  - **분리보관 테이블의 접근 권한 분리 미이행** — 플랫폼 DB 계정 하나라 DB스키마 4-1 "분리보관 = 별도 테이블 + 접근 권한 분리" 중 권한 분리가 안 돼 있음(발견사항 후보)
  - **회원가입 409로 이메일 존재 여부 노출**(이메일 인증 없음)
  - 고객 로그아웃 후에도 토큰은 만료 전까지 유효(관리자와 같음)
  - **소명 첨부 백신 검사 없음**(형식 판정 + 내려받기 강제까지)
  - 담당자 플랫폼 계정의 권한 과다 — 정책정의서 4-4. 담당자 자기 건 검토(직무 분리)는 서버가 막는다(403 `SELF_REVIEW_FORBIDDEN`, 정책정의서 3-5)
- **계정·권한 이력의 보호 범위**: 플랫폼 `operator_permission_history`·Argus `argus_user_history`(2-3)는 UPDATE·DELETE만 트리거로 막고 TRUNCATE는 막지 않는다(원장만 TRUNCATE까지). 3년 보관 뒤 파기는 v0.2. Argus 운영 스크립트의 `set-password`는 권한 변경이 아니어서 이력을 남기지 않는다
- **웹 푸시 종단 확인**: 실제 브라우저·푸시 서비스까지의 발송은 로컬·CI에 VAPID 키가 없어 확인하지 않았다(암호화·서명은 구독자 쪽 복호화 테스트로 확인, 2-2). 푸시 서비스에는 알림 발송 시각이 남는다
- **게이트웨이의 계정 상태 확인도 공용 계정 소유 테이블에 의존**: 퇴직·잠금 재확인은 `operator`를 읽는데, 이 테이블도 공용 계정(DB 소유자) 소유라 게이트웨이로 접속한 사람이 자기 재직 상태를 되돌릴 수 있다. 그 UPDATE 자체는 2티어 접속기록으로 원장에 남아 사후 탐지는 가능 — 근본 대응은 v0.2 **DB 롤 분리**(게이트웨이 중계 계정에서 `operator` 쓰기 권한 제거)
