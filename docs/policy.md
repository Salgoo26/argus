## 1. 탐지 룰 모델

### 1-1. 룰 유형

룰은 두 유형으로 나뉜다. 이 구분이 데이터 모델과 배치 로직을 좌우한다.

| 유형 | 판정 방식 | 필요 요소 |
|---|---|---|
| **EVENT (단건형)** | 접속기록 1건만 보고 조건식으로 판정 | 조건식 |
| **AGGREGATE (집계형)** | 일정 윈도우 내 로그를 집계해 임계치와 비교 | 조건식(대상 필터) + 집계 방식 + 임계치 |

> 조건식과 임계치는 대립 개념이 아니다. 집계형 룰은 "조건식으로 대상을 좁힌 뒤, 그 집계값을 임계치와 비교"하는 구조이므로 둘 다 사용한다.

### 1-2. 룰 스펙 (룰 빌더가 다뤄야 할 필드)

**공통**

| 필드 | 설명 |
|---|---|
| 룰 ID / 룰명 | |
| 유형 | EVENT / AGGREGATE |
| 심각도 | 상 / 중 / 하 |
| 활성 여부 | on / off |
| **적용 접근 경로** | `APP` / `DB` / 전체 — 룰이 어느 접근 경로의 로그에 적용되는지 (요구사항정의서 1-2절). 1단계 기본 룰은 모두 `APP` |
| 조건식 | 수행업무 종류, 대상 데이터 유형, 시간대, 요일 등의 조합 (AND/OR) |
| 그룹핑 키 | 기본값 `(취급자, 룰, 날짜)` — 2절 참고 |
| 설명 | 담당자가 남기는 룰 취지 |

> **접근 경로를 룰 단위로 지정하는 이유**: DB 직접 접근과 응용프로그램 경유 접근은 정상 기준선이 반대다. 응용 경유는 조회가 일상이라 양·시간 이상치를 보지만, DB 직접 접근은 운영 DB 개인정보 조회 자체가 이례적이다. 같은 "조회 100건"이라도 경로에 따라 의미가 다르므로 룰을 경로별로 분리 적용해야 한다.
> (구현: 조건식 JSON 안이 아니라 `detection_rule.access_path` **독립 컬럼**으로 둔다 — DB스키마 3-3절)

**AGGREGATE 전용**

| 필드 | 설명 | 예시 |
|---|---|---|
| 집계 윈도우 | 집계 기간 | 1시간 / 1일 / 1개월 |
| 집계 대상 | 무엇을 셀 것인가 | 로그 건수 / 처리 건수 합 / 고유 정보주체 수 |
| 비교 방식 | 절대 임계치 / 기준선 대비 비율 | |
| 기준선 | (비율 비교 시) 비교 대상 | 전월 동기 / 직전 3개월 평균 |
| 임계치 | | 100건 / 200% |

### 1-3. 기본 제공 룰 (1단계: 접근 경로 = APP)

| 룰 | 유형 | 조건식 | 임계치 | 심각도 |
|---|---|---|---|---|
| 야간 접속 | EVENT | 접속일시 22:00~06:00 AND 수행업무 ∈ {조회, 다운로드} | — | 중 |
| 주말 접속 | EVENT | 접속일시 요일 ∈ {토, 일} | — | 하 |
| 결제수단 정보 조회 | EVENT | 대상 데이터 = 결제수단 | — | 상 |
| 대량 다운로드 | EVENT | 수행업무 = 다운로드 AND 대상 건수 ≥ 50 | — | 상 |
| 대량 조회 | AGGREGATE | 수행업무 = 조회 | 1시간 내 100건 이상 | 상 |
| 전월 대비 급증 | AGGREGATE | 수행업무 = 조회 | 당월 누적 ≥ 전월 동기 × 200% | 중 |
| **퇴직자 계정 접속** (2026-09-23 추가) | EVENT | **행위 시점에 이미 퇴직 상태였던 계정의 모든 접속** | — | 상 |

> **대량 다운로드가 EVENT인 이유**: 안전조치기준 §2 3호가 "처리한 정보주체 정보"를 기록하도록 요구하므로, 다운로드 로그에 대상 건수가 함께 남는다. 따라서 로그 1건만으로 판정 가능하다.
>
> **퇴직자 계정 접속 룰의 판정 기준 (2026-09-23 신설)**: 4-2절에서 재직상태를 "퇴직자 계정의 접속 탐지" 용도로 유지한다고 정했으나 정작 기본 룰 목록에 없어 보완했다. 판정은 **현재 재직상태가 아니라 행위 시점 기준**(`퇴직시각 ≤ 접속일시`)으로 한다. 현재 상태로 판정하면 ①퇴직 전 정상 접속이 소급 탐지되고 ②늦게 도착한 로그가 오판정되기 때문이다. 이를 위해 취급자 동기화 시 **퇴직 시각**을 함께 받는다(API명세서 3-1절).

**2단계(DB 직접 접근) 룰 후보** — 2단계 착수 시 확정:
- 개인정보 테이블 대상 SELECT
- WHERE 조건 없는 전체 조회
- 결제수단 테이블 접근
- 개인정보 테이블 DML(UPDATE/DELETE)
- 결과 건수 N건 이상

### 1-4. 패턴 기반 탐지 (후순위)

규칙 기반을 1차로 구현하고, 여유가 되면 패턴/통계 기반 탐지(baseline 이탈 등)를 추가한다. 요구사항정의서 5-3절의 "통계적 이상탐지"와 동일 항목.

## 2. 탐지건 단위 및 그룹핑

### 2-1. 문제

조건 충족 로그 1건 = 탐지 1건으로 두면, 주말에 100건 조회한 취급자에게 소명 요청이 100회 발생한다. 실무에서 성립하지 않는다.

### 2-2. 정책

| 구분 | 탐지건 단위 |
|---|---|
| EVENT 룰 | **`(취급자 계정, 룰, 날짜)` 단위로 그룹핑**하여 1건 생성. 해당 그룹에 속한 로그들은 탐지건의 하위 근거로 첨부 |
| AGGREGATE 룰 | 집계 단위가 곧 탐지건 (예: "cs_kim의 9/15 14:00~15:00 대량조회" = 1건) |

- 그룹핑 키는 룰별로 변경 가능하도록 룰 스펙에 포함한다(기본값은 위와 같음).
- **소명은 탐지건 단위로 1회** 요청·제출한다.
- 탐지건은 하위 로그 목록을 함께 보여주어, 담당자가 실제 행위를 확인할 수 있게 한다.

### 2-3. 하위 로그 추가 대상 (2026-09-23 신설)

같은 그룹에 이미 탐지건이 있을 때, **진행 중인 건에만 하위 로그를 추가**한다.

| 기존 탐지건 상태 | 새 로그 처리 |
|---|---|
| 진행 중 (`DETECTED` / `REQUESTED` / `SUBMITTED` / `REJECTED`) | 기존 건에 하위 로그 추가 |
| **종결 (`APPROVED` / `DISMISSED` / `ESCALATED`)** | **새 탐지건을 생성** |

> **왜 필요한가**: 기존 정책("있으면 하위 로그만 추가")대로면, 오전에 소명을 받아 승인·종결한 건이 있는 상태에서 오후에 같은 취급자가 같은 행위를 또 해도 **이미 닫힌 건에 조용히 붙어 아무도 다시 보지 않게 된다.** 승인은 "그때까지의 행위"에 대한 판단이므로, 종결 후의 새 행위는 새 판단 대상이어야 한다.
> (구현: `detection`에 부분 유니크 인덱스를 걸어 진행 중 건이 그룹당 1개만 존재하도록 DB 차원에서 보장 — DB스키마 3-4절, 동작 검증 완료)

## 3. 탐지건 상태 전이

### 3-1. 상태

| 상태 | 의미 |
|---|---|
| `DETECTED` | 탐지됨, 미조치 |
| `REQUESTED` | 소명 요청됨 (취급자 제출 대기) |
| `SUBMITTED` | 소명 제출됨 (담당자 검토 대기) |
| `APPROVED` | 소명 승인 → **종결** |
| `REJECTED` | 소명 반려 (재요청 또는 에스컬레이션 대기) |
| `DISMISSED` | 담당자가 소명 불요로 판단 → **종결** (오탐·예외 등) |
| `ESCALATED` | 정보보안팀 이관 → **종결**(서비스 스코프 경계 밖) |

### 3-2. 전이

```
DETECTED ──[소명요청]──> REQUESTED ──[취급자 제출]──> SUBMITTED
   │                                                      │
   │                                          ┌───[승인]──┴──[반려]───┐
   │                                          ▼                       ▼
   └──[소명불요]──> DISMISSED            APPROVED                 REJECTED
                                                                     │
                                                    ┌───[재요청]─────┴──[에스컬레이션]──┐
                                                    ▼                                   ▼
                                              REQUESTED (round +1)                 ESCALATED
```

- **반려(`REJECTED`)는 독립 상태로 둔다.** 반려 직후 재요청할지 에스컬레이션할지는 담당자 판단이며, 그 판단 전 상태가 실무에 존재하기 때문이다.
- 재요청 시 `REQUESTED`로 되돌아가되 **round 카운터를 +1** 한다(반복 횟수 추적 → 요구사항 LOG-14 "소명 이력 누적"과 연결).
- `ESCALATED`는 플래그 및 보고서 표기까지만 담당한다. 이관 이후 프로세스는 아웃오브스코프(POV 스코프 경계).
- 모든 상태 전이는 **누가·언제·무슨 사유로** 바꿨는지 이력으로 남긴다(점검 수행 증적, ISMS-P 대응).

## 4. 취급자 모델

### 4-1. 권한 매트릭스 제외 (2026-09-15 결정)

기능별 권한 매트릭스와 "권한 외 접근 시도" 탐지 룰은 **채택하지 않는다.**

**사유(실무 근거)**: 조직에서 팀·권한이 다르면 애초에 해당 시스템·DB 접근 자체가 차단된다. 권한 없는 계정이 조회에 성공했다면 그것은 탐지 대상이 아니라 이미 발생한 보안사고다. 따라서 점검 서비스의 탐지 룰로 다루는 것이 적절하지 않다.

> 단, 감시 대상 플랫폼 쪽에는 관리자 메뉴 노출과 권한 차등 부여(PLT-10·14)를 위한 **역할(role) 구분은 필요**하다. 이는 탐지 룰의 대상이 아니라 무대장치의 기능이다.

### 4-2. 유지하는 속성

권한 매트릭스는 빼되, 취급자 계정의 다음 속성은 유지한다.

| 속성 | 용도 |
|---|---|
| 계정 식별자 | 접속기록 매칭, 소명 요청 대상 지정 |
| 소속(팀) | 보고서 팀별 집계, 향후 "소속과 무관한 데이터 조회" 류 룰의 여지 |
| 재직 상태 + **퇴직 시각** | 퇴직자 계정의 접속 탐지 (1-3절 — 행위 시점 기준 판정에 퇴직 시각이 필요) |

- 안전조치기준 §5③(권한 부여·변경·말소 내역 3년 보관)은 법정 의무이므로 이력 기록 자체는 유지하되, 구현 우선순위는 Should로 둔다.
- **취급자 정보의 최소수집**: 취급자(직원) 정보도 개인정보다. Argus가 보유하는 것은 계정·이름·소속·재직상태·퇴직시각으로 한정하고, 연락처·사번·권한 상세는 받지 않는다.
- **2단계 주의**: DB 직접 접근 로그의 식별자는 DB 계정(또는 접근제어 경유 시 그 사용자 ID)이므로, 플랫폼 관리자 계정과 **동일인 매핑**이 필요하다. 2단계 착수 시 검토.

### 4-3. 관리자 인증·로그인 실패 정책 (2026-09-30 신설, 구현 M2)

플랫폼 관리자(취급자) 로그인에 적용한다. Argus 사용자(A4·A5) 로그인(M4)도 같은 기준을 따른다.

| 항목 | 기준 | 근거 |
|---|---|---|
| 로그인 실패 제한 | **5회 연속 실패 시 계정 잠금**, 성공하면 실패 횟수 0으로 초기화 | 안전조치기준 §5⑥ (일정 횟수 이상 인증 실패 시 접근 제한) |
| 잠금 해제 | 관리 스크립트로만 해제 (관리 UI는 범위 밖) | |
| 미사용 시 차단 | **30분 미사용 시 인증 만료** (요청마다 만료 연장) | 안전조치기준 §6④ (일정 시간 미사용 시 자동 접속 차단) |
| 상태 재확인 | 매 요청마다 계정 상태(퇴직·잠금) 확인 — 로그인 후 퇴직·잠금되면 즉시 차단 | §5② (업무 변경 시 지체 없이 권한 변경·말소) |
| 퇴직자 | 로그인 거부 | |

**응답·기록 원칙**

- **계정 존재 여부를 드러내지 않는다.** 없는 ID와 틀린 비밀번호는 같은 응답(401)을 주고, 없는 ID도 더미 해시로 검증을 수행해 **응답 시간**으로도 구분되지 않게 한다.
- **잠김·퇴직(403)은 비밀번호가 맞았을 때만 알려준다** — 비밀번호를 모르는 사람에게 "이 계정은 존재하고 잠겨 있다"를 알려주지 않는다.
- **접속기록**: 존재하는 계정의 실패(비밀번호 오류·잠김·퇴직자)는 `LOGIN`/`FAILURE`로 기록한다. **존재하지 않는 ID의 실패는 기록하지 않는다** — ID 칸에 잘못 입력된 비밀번호가 append-only 원장에 영구 저장되는 것을 막기 위함이며, 그 값은 §2 3호의 취급자 식별자도 아니다. 로그아웃은 개인정보 처리가 없어 기록 대상이 아니다.
- 입력 길이 상한(`login_id` 64자, 비밀번호 256자) — 초대형 비밀번호로 해시 계산 시간을 늘리는 공격 방지.

**알려진 한계** (보안성 검토 단계 과제 — 아키텍처 설계서 8-6): 시간 경과로 풀리지 않는 잠금은 일부러 틀려 정상 사용자를 잠그는 서비스 거부에 쓰일 수 있음 / 계정 단위 계산이라 password spraying 미탐지 / IP 단위 제한 없음 / 존재하지 않는 ID 대입은 Argus에 보이지 않음 / 로그아웃 후에도 토큰은 만료 전까지 유효.

> 이 정책을 보안성 검토 이후로 미루지 않고 M2에서 구현한 이유: 설계(아키텍처 1절 "rate limit 대체")와 법정 기본 통제(§5⑥)에 이미 있는 항목이다. 비워 두고 나중에 채우는 것보다 **기본 통제를 먼저 갖추고 그 한계를 스스로 찾아 개선**하는 쪽이 설득력이 있다고 판단했다.

## 5. 보관 및 파기 정책

### 5-1. 보관기간

| 대상 | 기간 | 근거 |
|---|---|---|
| 플랫폼 접속기록 | **1년** | 안전조치기준 §8① (본 프로젝트는 5만명 미만이며 고유식별정보·민감정보를 처리하지 않으므로 2년 요건 비해당) |
| Argus 자체 접속기록 | 1년 | 동일 (자기참조 구조) |
| 탐지·소명 이력 | 접속기록과 동일 이상 | 점검 수행 증적 (ISMS-P 대응) |
| 권한 부여·변경·말소 이력 | 3년 | 안전조치기준 §5③ |
| 회원 개인정보 | 탈퇴 시 지체 없이 파기 | PIPA §21① |
| 계약·청약철회, 대금결제·재화공급 기록 | 5년 | 전자상거래법 시행령 §6 |
| 소비자 불만·분쟁처리 기록 | 3년 | 전자상거래법 시행령 §6 |

> **주의**: 결제수단 정보(카드번호·계좌번호)는 고유식별정보가 **아니다**(고유식별정보 = 주민등록번호·여권번호·운전면허번호·외국인등록번호). 따라서 §8① 2년 요건은 발동하지 않으나, §7②5·6호 **암호화 의무는 적용된다.**
>
> **탐지 근거의 보존 (2026-09-23 보완)**: 접속기록이 1년 후 파기되면 탐지건의 하위 근거 로그도 사라져 "탐지·소명 이력은 접속기록과 동일 이상 보관"이 형해화된다. 따라서 탐지건 생성 시 **근거 로그의 요약(건수·시각 범위·수행업무·처리 건수 합 등)을 탐지건에 스냅샷으로 남긴다.** 요약에는 정보주체 식별값을 담지 않는다.

### 5-2. 점검 주기

점검 주기는 Argus에서 **설정값**으로 둔다. 2026.7.1 고시 §8②는 점검 주기·방법·사후조치절차를 내부 관리계획으로 정하도록 조직 자율에 위임하고 있다(2024.10 안내서의 "월 1회 이상" 문구는 현행 고시 원문에 없음 — 요구사항정의서 2절 주석). 기본값은 월 1회로 두되 담당자가 변경할 수 있게 한다.

### 5-3. 자동 파기 배치

파기는 수동이 아닌 **일 1회 배치**로 자동 이행한다.

| 항목 | 내용 |
|---|---|
| 실행 주기 | 일 1회 |
| 대상 | ① 보관기간이 만료된 접속기록 ② 탈퇴 후 법정 보존의무가 없는 회원 개인정보 ③ 보유기간이 만료된 기타 항목 |
| 파기 방식 | 복원 불가능한 삭제 — 논리삭제(flag)가 아닌 실제 삭제. 안전조치기준 §13①3호 "복원되지 않도록 초기화 또는 덮어쓰기" |
| 분리보관 | 법정 보존의무로 남기는 항목은 다른 개인정보와 **분리하여 저장·관리** (PIPA §21③) — 별도 테이블로 옮기고 접근 권한을 달리 부여하며, 보존 목적에 필요한 최소 항목만 담는다 (DB스키마 4-1절) |
| 파기 이력 | 파기일시, 대상 유형, 파기 건수, 적용 근거를 기록. **이력에 개인정보 자체를 남기지 않는다**(파기한 정보가 이력에 남으면 모순) |
| 백업과의 관계 | 서버 백업(일 1회, 7일 보관)에도 파기 대상이 남아 있으므로, 원본 파기 후 최대 7일 내에 백업에서도 소멸한다 (아키텍처 설계서 8-4절) |

**이 배치가 갖는 의미**: 파기 이행 여부는 ISMS-P 점검에서 반복적으로 확인되는 항목이며, 자동 배치 + 파기 이력은 그 자체로 증적이 된다. 구현 후 보안성/ISMS-P 점검 실습 단계에서 활용한다.

> **검토 메모**: 파기 배치는 시스템 계정이 수행하는 행위이므로 §2 3호의 "개인정보처리시스템에 접속하는 자"에 해당하는지 해석의 여지가 있다. 실무에서는 시스템 계정 명의로 기록하는 것이 일반적이므로 동일하게 기록하되, 탐지 룰 평가 대상에서는 제외(화이트리스트)한다.

## 6. 정보주체 식별값 노출 통제

액터별_플로우 8절이 정한 화면 마스킹 정책(정보보호 담당자만 사유 입력 후 해제, 취급자는 해제 불가)에 더해, 아래를 보완한다.

### 6-1. 점검 보고서 export (2026-09-23 신설)

| 항목 | 정책 |
|---|---|
| 기본 | 보고서는 **마스킹된 식별값**으로 생성한다 |
| 예외 | 식별값을 포함한 보고서가 필요하면 **사유를 입력**해야 하며, 정보보호 담당자만 가능 |
| 기록 | 보고서 생성은 Argus 접속기록에 `EXPORT`로 기록하고, 언마스킹 보고서인 경우 사유를 함께 남긴다 |

> **왜 필요한가**: 화면에서는 마스킹을 강제하는데 보고서 파일로는 그냥 빠져나갈 수 있다면, 마스킹 정책 전체가 무력화된다. 보고서는 파일로 조직 밖으로 이동할 수 있어 화면보다 통제가 더 중요하다. 근거는 §12①(출력 시 용도 특정·출력 항목 최소화)로 화면 표시에 적용한 것과 같다.

### 6-2. 정보주체 ID 검색

접속기록을 정보주체 식별값으로 검색하는 행위(LOG-02)도 식별값을 평문으로 다루는 행위이므로, Argus 접속기록에 `READ`로 기록하고 **검색 조건의 키 이름만** 남긴다(검색어 값은 기록하지 않는다).

### 6-3. Argus 자체 기록의 식별자 중복 축적 방지

Argus에서 탐지건·로그를 조회할 때마다 회원 식별자를 Argus 접속기록에 다시 적재하면 식별자가 중복 축적되어 최소처리 원칙에 반한다. 따라서 Argus 자체 기록에는 **처리 건수만** 남기고, 예외적으로 마스킹 해제(`UNMASK`)만 대상 탐지건 ID를 남긴다(API명세서 2-7절).
