## 1. 탐지 룰 모델

### 1-1. 룰 유형

룰은 두 유형으로 나뉜다. 이 구분이 데이터 모델과 배치 로직을 좌우한다.

| 유형 | 판정 방식 | 필요 요소 |
|---|---|---|
| **EVENT (단건형)** | 접속기록 1건만 보고 조건식으로 판정 | 조건식 |
| **AGGREGATE (집계형)** | 일정 윈도우 내 로그를 집계해 임계치와 비교 | 조건식(대상 필터) + 집계 방식 + 임계치 |

> 조건식과 임계치는 대립 개념이 아니다. 집계형 룰은 "조건식으로 대상을 좁힌 뒤, 그 집계값을 임계치와 비교"하는 구조이므로 둘 다 사용한다.

### 1-2. 룰 스펙 (룰 빌더가 다뤄야 할 필드)

**공통**

| 필드 | 설명 |
|---|---|
| 룰 ID / 룰명 | |
| 유형 | EVENT / AGGREGATE |
| 심각도 | 상 / 중 / 하 |
| 활성 여부 | on / off |
| **적용 접근 경로** | `APP` / `DB` / 전체 — 룰이 어느 접근 경로의 로그에 적용되는지 (요구사항정의서 1-2절). 1단계 기본 룰은 모두 `APP` |
| 조건식 | 수행업무 종류, 대상 데이터 유형, 시간대, 요일 등의 조합 (AND/OR) |
| 그룹핑 키 | 기본값 `(취급자, 룰, 날짜)` — 2절 참고 |
| 설명 | 담당자가 남기는 룰 취지 |

> **룰 적용 대상 (2026-10-01, 기능 레이어 1)**: 탐지 룰은 **감시 대상 시스템(플랫폼)의 기록에만** 적용한다. Argus 자체 접속기록(출처 ARGUS, LOG-17)은 원장에 남기기만 하고 룰로 평가하지 않는다 — 그대로 두면 담당자가 밤에 검토할 때 **담당자 본인 탐지건**이 생기고(자기 점검·이해충돌), 취급자의 주말 소명 제출이 다시 탐지된다. Argus 자체 기록 점검은 **접속기록 조회 화면의 출처 필터로만** 한다(실무에서도 점검 시스템 자체 기록까지 정기 검토하지 않는 경우가 많음 — 법 요건(§8②)과 관행 사이에서 "볼 수는 있다"를 남김).
>
> **룰 관리 (2026-10-01, 기능 레이어 6)**: 담당자 전원이 룰 빌더로 생성·수정·켜기/끄기. **삭제는 없다** — 탐지건이 룰을 참조하고 "그 시점에 운영한 룰"이 점검 근거이므로, 쓰지 않는 룰은 끄고 목록 필터로 관리한다. 매 변경은 버전 +1과 변경 후 룰 전체를 이력으로 남긴다(변경 사유 입력은 받지 않음 — 운영 부담 대비 단순함 우선). 룰 유형(EVENT/AGGREGATE)은 만든 뒤 바꿀 수 없고, 고친 룰은 **다음 순찰부터** 적용(과거 기록 재판정 없음).

> **접근 경로를 룰 단위로 지정하는 이유**: DB 직접 접근과 응용프로그램 경유 접근은 정상 기준선이 반대다. 응용 경유는 조회가 일상이라 양·시간 이상치를 보지만, DB 직접 접근은 운영 DB 개인정보 조회 자체가 이례적이다. 같은 "조회 100건"이라도 경로에 따라 의미가 다르므로 룰을 경로별로 분리 적용해야 한다.
> (구현: 조건식 JSON 안이 아니라 `detection_rule.access_path` **독립 컬럼**으로 둔다 — DB스키마 3-3절)

**AGGREGATE 전용**

| 필드 | 설명 | 예시 |
|---|---|---|
| 집계 윈도우 | 집계 기간 | 1시간 / 1일 / 1개월 |
| 집계 대상 | 무엇을 셀 것인가 | 로그 건수 / 처리 건수 합 / 고유 정보주체 수 |
| 비교 방식 | 절대 임계치 / 기준선 대비 비율 | |
| 기준선 | (비율 비교 시) 비교 대상 | 전월 동기 / 직전 3개월 평균 |
| 임계치 | | 100건 / 200% |
| **기준선 최소 건수** (`min_baseline`, 2026-10-01) | (비율 비교 시) 전월 같은 기간 집계값이 이보다 작으면 **판정하지 않음**(0 포함) | 20 |

> **`min_baseline`을 둔 이유 (기능 레이어 4)**: 기준선이 작으면 비율이 튄다. 실제로 9/3 13시 기준 평범한 취급자가 2.33배로 탐지됐는데, 전월 같은 기간(8/1 토 ~ 8/3 월 오전)의 기준선이 3건뿐이었다. **월초·휴일 직후의 실제 오탐 원인**이라 시드 조정이 아니라 룰 속성으로 둔다. 기준선 0은 비율 자체를 정할 수 없다(신규 취급자·첫 달). 기각: 기준선 0을 "판정 불가 → 탐지" — 신규 취급자마다 첫 달 매번 탐지됨.
>
> **집계 윈도우는 한국 시각 고정 구간**(매시 정각·0시·1일) — 슬라이딩 윈도우는 탐지건 단위가 정해지지 않고 같은 행위가 여러 건으로 겹친다. 대신 정각 경계에 걸친 몰아치기는 놓친다(알려진 한계).

### 1-3. 기본 제공 룰 (1단계: 접근 경로 = APP)

| 룰 | 유형 | 조건식 | 임계치 | 심각도 |
|---|---|---|---|---|
| 야간 접속 | EVENT | 접속일시 22:00~06:00 AND 수행업무 ∈ {조회, 다운로드} | — | 중 |
| 주말 접속 | EVENT | 접속일시 요일 ∈ {토, 일} | — | 하 |
| 결제수단 정보 조회 | EVENT | 대상 데이터 = 결제수단 | — | 상 |
| 대량 다운로드 | EVENT | 수행업무 = 다운로드 AND 대상 건수 ≥ 50 | — | 상 |
| 대량 조회 | AGGREGATE | 수행업무 = 조회 | 1시간 내 100건 이상 | 상 |
| 전월 대비 급증 | AGGREGATE | 수행업무 = 조회 | 당월 누적 ≥ 전월 동기 × 200% (전월 동기 20건 미만이면 판정 안 함) | 중 |
| **퇴직자 계정 접속** (2026-09-23 추가) | EVENT | **행위 시점에 이미 퇴직 상태였던 계정의 모든 접속** | — | 상 |

> **대량 다운로드가 EVENT인 이유**: 안전조치기준 §2 3호가 "처리한 정보주체 정보"를 기록하도록 요구하므로, 다운로드 로그에 대상 건수가 함께 남는다. 따라서 로그 1건만으로 판정 가능하다.
>
> **퇴직자 계정 접속 룰의 판정 기준 (2026-09-23 신설)**: 4-2절에서 재직상태를 "퇴직자 계정의 접속 탐지" 용도로 유지한다고 정했으나 정작 기본 룰 목록에 없어 보완했다. 판정은 **현재 재직상태가 아니라 행위 시점 기준**(`퇴직시각 ≤ 접속일시`)으로 한다. 현재 상태로 판정하면 ①퇴직 전 정상 접속이 소급 탐지되고 ②늦게 도착한 로그가 오판정되기 때문이다. 이를 위해 취급자 동기화 시 **퇴직 시각**을 함께 받는다(API명세서 3-1절).
>
> **명부에 없는 계정 = 판정 불가 → 탐지 (2026-10-01, 기능 레이어 1)**: 행위자가 취급자 명부에 없으면 퇴직 여부를 판정할 수 없으므로, 보류하지 않고 **퇴직자 계정 접속 룰로 탐지**하고 상태 이력에 "취급자 명부에 없는 계정 — 퇴직 여부를 판정할 수 없어 탐지"를 남긴다(fail-closed). relay가 명부를 기록보다 먼저 보내므로 정상이면 생기지 않고, 생겼다면 동기화 실패나 명부 밖 계정이라 그 자체가 점검 대상이다. 기각: 순찰 정지(계정 하나가 끝내 동기화되지 않으면 **모든 룰의 탐지가 멈춤**), 보류 테이블(스키마 변경·작업량).
>
> **야간 구간 경계**: 시작 포함·끝 미포함, 분 단위(22:00:00 ~ 05:59:59), 한국 시각.

**2단계(DB 직접 접근) 룰** — 2026-10-05 2티어 설계 확정 → **2026-10-06 기본 3개로 축소(사용자 결정, 구현 순서 ③-1 · 마이그레이션 0012 시드)**. 모두 `access_path = DB`. 시드는 [[DB스키마.md]] 3-6.

|---|---|---|---|---|
| DB 직접 야간 접근 | EVENT | 접속일시 22:00~06:00 AND 대상 데이터 ∈ {회원 기본, 주문, 문의, 결제수단} | — | **상** |
| DB 직접 주말 접근 | EVENT | 접속일시 요일 ∈ {토, 일} AND 대상 데이터 ∈ {회원 기본, 주문, 문의, 결제수단} | — | **중** |

> **기본 3개로 줄인 이유 (2026-10-06, 사용자 결정)**: "주간/야간" 짝은 3티어와 같은 야간+주말이며, 안내서의 비정상 행위 예시("업무시간 외·휴무일")와 일치한다. 나머지는 **담당자가 룰 빌더로 추가**한다(룰 빌더는 이미 접근 경로 선택을 지원). 기각: 10/05의 5개 룰(DB 경로 개인정보 조회·결제수단 테이블 접근·개인정보 변경·대량 처리·정보주체 미특정). 미특정 룰은 회원번호 추출(구현 순서 ②)이 **보류**되어 모든 DB 기록이 미특정이므로 제외했다.
>
> - **심각도**: 같은 3티어 룰보다 한 단계 높게(야간 상·주말 중). 급증은 3티어와 같은 중. DB 직접 접근은 평소 드문 경로이기 때문이다.
> - **조건**: 개인정보 데이터를 처리한 문장만 본다. DB 툴 접속(`LOGIN`)·업무 외 테이블까지 잡으면 접속 한 번에 탐지가 여러 건 생긴다.
> - **경로 분리**: 탐지건 묶음 기준·집계·전월 기준선 모두 경로별이다(1-5). "전체" 경로 룰도 화면 경유와 DB 직접을 한 탐지건에 섞지 않는다.
> - **퇴직자 계정 접속 룰은 화면 경유(APP)에만 둔다** (2026-10-06, 사용자 결정 — 10/05의 "APP → 전체" 변경 취소). DB 경로는 토큰 발급과 게이트웨이 로그인 때 재직을 확인한다(fail-closed, 아키텍처 설계서 3-4). 퇴직 전에 열어 둔 연결이 이어지는 틈은 남는다.

- **룰 빌더로 추가할 수 있는 예 (10/05 검토안)**: DB 경로 개인정보 조회(중), 결제수단 테이블 접근(상), 개인정보 변경(상), 대량 처리 ≥100건(상)
- **v0.2 후보**: WHERE 조건 없는 전체 조회(SQL 형태 조건 필드 필요) / **DB 경로로 보안 테이블 접근**(`outbox`·`operator`·`db_access_token` — 공용 계정이 소유자라 3티어 기록을 전송 전에 지우거나 위조할 수 있음, 아키텍처 설계서 8-6. 조건식에 테이블 필드 필요) / DCL(GRANT·REVOKE) 실행 탐지(DDL·DCL의 Argus 전송과 함께) / 정보주체 미특정 룰(회원번호 추출 ② 재논의 결과에 따라)
- **소명의 성격 (사용자 실무 경험)**: DB 직접 접근은 대량 다운로드 외에 **내부 담당자 요청에 따른 대량 조회·수정**이 많다 → 소명 근거는 요청 티켓·메일 등 업무 요청 기록(3-3 관련 티켓 첨부). 토큰 발급 시 사유를 받지 않으므로(사용자 결정 — 이상 징후 시 소명 단계가 있음) 소명이 사후 기억에 의존하는 대가가 있다.

### 1-4. 패턴 기반 탐지 (후순위)

규칙 기반을 1차로 구현하고, 여유가 되면 패턴/통계 기반 탐지(baseline 이탈 등)를 추가한다. 요구사항정의서 5-3절의 "통계적 이상탐지"와 동일 항목.

### 1-5. 접근 경로(3티어·2티어) 구분 원칙 (2026-10-05 신설, 사용자 요구)

> 사용자 실무 경험: 화면 경유(3티어)와 DB 직접 접근(2티어)은 **성격이 다른 기록**이고 **보고도 따로** 했다. 따라서 Argus는 두 경로를 **기록부터 보고까지 한 번도 섞지 않고** 구분해 보여준다. 탐지·소명·검토 기준도 경로별로 다를 수 있다.

| 영역 | 구분 방식 |
|---|---|
| 용어(화면 표기) | `APP` = **화면 경유(3티어)**, `DB` = **DB 직접(2티어)**. 담당자·취급자 화면 모두 같은 표기 |
| 접속기록 | `access_path`로 구분. 조회·검색 화면에 경로 표시·필터(구현됨, LOG-02). DB 경로 기록은 정규화 SQL·테이블·컬럼·건수·정보주체 미특정 여부를 함께 표시 |
| 탐지 룰 | 경로별로 따로 둔다(1-2 "적용 접근 경로", 1-3). 두 경로는 정상 기준선이 반대 |
| 탐지건 | **탐지건 하나는 한 경로만** 담는다. 탐지건에 경로를 저장하고(DB스키마 `detection.access_path`), 적용 경로가 "전체"인 룰도 **경로별로 따로 탐지건을 만든다**(2-2 그룹핑 키에 경로 포함). 목록·상세·대시보드에 경로 표시·필터 |
| 취급자 화면 | 내 탐지건에 경로 표시. DB 경로 건은 근거 로그에 정규화 SQL·테이블·건수를 보여줘 무엇을 소명해야 하는지 알 수 있게 한다(원문 SQL·매개변수는 보여주지 않음 — Argus 미보유) |
| 소명 작성 기준 | 3-3 "경로별 소명 기준" — 양식은 같고 **작성 안내와 담당자 검토 기준이 다르다** |
| 보고 | 점검 보고서(LOG-09)는 **경로별로 나눠** 집계·서술한다(3티어 섹션 / 2티어 섹션). 합산 수치만 보여주지 않는다. **생성 때 범위(전체 / 화면 경유 / DB 직접)를 고른다** — 전체면 두 섹션, 한 경로면 그 섹션만(2026-10-07, 사용자 동의 — 경로별로 보고처가 다른 조직은 단일 경로 보고서로). Argus 자체 접속기록은 경로 섹션에 섞지 않는다(감시 대상 기록만) |
| 통계 기준선 | AGGREGATE 룰의 기준선(전월 동기 등)은 룰의 적용 경로 안에서만 계산한다 — 경로가 섞이면 기준선이 무의미 |

## 2. 탐지건 단위 및 그룹핑

### 2-1. 문제

조건 충족 로그 1건 = 탐지 1건으로 두면, 주말에 100건 조회한 취급자에게 소명 요청이 100회 발생한다. 실무에서 성립하지 않는다.

### 2-2. 정책

| 구분 | 탐지건 단위 |
|---|---|
| EVENT 룰 | **`(취급자 계정, 룰, 접근 경로, 날짜)` 단위로 그룹핑**하여 1건 생성(경로는 2026-10-05 추가 — 1-5, 한 탐지건 = 한 경로). 해당 그룹에 속한 로그들은 탐지건의 하위 근거로 첨부. **날짜는 한국 시각(KST) 기준** (2026-10-01, 구현 M3) |
| AGGREGATE 룰 | 집계 단위가 곧 탐지건 (예: "cs_kim의 9/15 14:00~15:00 대량조회" = 1건). 적용 경로가 "전체"면 경로별로 따로 집계 (2026-10-05) |

- 그룹핑 키는 룰별로 변경 가능하도록 룰 스펙에 포함한다(기본값은 위와 같음).
- **소명은 탐지건 단위로 1회** 요청·제출한다.
- 탐지건은 하위 로그 목록을 함께 보여주어, 담당자가 실제 행위를 확인할 수 있게 한다.

### 2-3. 하위 로그 추가 대상 (2026-09-23 신설)

같은 그룹에 이미 탐지건이 있을 때, **진행 중인 건에만 하위 로그를 추가**한다.

| 기존 탐지건 상태 | 새 로그 처리 |
|---|---|
| 진행 중 (`DETECTED` / `REQUESTED` / `SUBMITTED` / `REJECTED`) | 기존 건에 하위 로그 추가 |
| **종결 (`APPROVED` / `DISMISSED` / `ESCALATED`)** | **새 탐지건을 생성** |

> **왜 필요한가**: 기존 정책("있으면 하위 로그만 추가")대로면, 오전에 소명을 받아 승인·종결한 건이 있는 상태에서 오후에 같은 취급자가 같은 행위를 또 해도 **이미 닫힌 건에 조용히 붙어 아무도 다시 보지 않게 된다.** 승인은 "그때까지의 행위"에 대한 판단이므로, 종결 후의 새 행위는 새 판단 대상이어야 한다.
> (구현: `detection`에 부분 유니크 인덱스를 걸어 진행 중 건이 그룹당 1개만 존재하도록 DB 차원에서 보장 — DB스키마 3-4절, 동작 검증 완료)

**AGGREGATE 예외 — 집계 윈도우는 한 번만 판단 (2026-10-01, 기능 레이어 4)**: 같은 (룰, 취급자, 윈도우)의 탐지건이 **종결됐으면** 그 윈도우에 기록이 더 쌓여도 새 탐지건을 만들지 않는다(진행 중이면 기록 추가·집계값 갱신). 위 원칙을 그대로 적용하면 집계는 누적이라 승인 뒤에도 같은 윈도우가 계속 기준을 넘어 **순찰(5분)마다 새 건**이 생긴다 — 월 윈도우는 한 달 내내. 한계: 승인 뒤 같은 시간·같은 달에 더 한 행위는 탐지되지 않는다(접속기록 조회로는 보이고, EVENT 룰은 그대로 동작). 기각: 종결 뒤 새 기록만으로 다시 기준을 넘을 때 새 건 — 정확하지만 비율 룰에서 뜻이 모호.

## 3. 탐지건 상태 전이

### 3-1. 상태

| 상태 | 의미 |
|---|---|
| `DETECTED` | 탐지됨, 미조치 (자동 소명 요청이 가지 않은 건 — 담당자 수동 처리 대상) |
| `REQUESTED` | 소명 요청됨 (취급자 제출 대기). **자동 요청(요청자 = 시스템) 또는 담당자 수동 요청** |
| `SUBMITTED` | 소명 제출됨 (담당자 검토 대기) |
| `APPROVED` | 소명 승인 → **종결** |
| `REJECTED` | 소명 반려 (재요청 또는 에스컬레이션 대기) |
| `DISMISSED` | 담당자가 소명 불요로 판단하거나 **요청을 취소** → **종결** (오탐·예외 등, 사유 필수) |
| `ESCALATED` | 정보보안팀 이관 → **종결**(서비스 스코프 경계 밖) |

### 3-2. 전이

```
            (탐지 배치: 자동 소명 요청 조건 충족 시 생성 즉시 전이 — 요청자 = 시스템)
                 ┌───────────────────────────┐
                 │                           ▼
DETECTED ──[소명요청(수동)]──> REQUESTED ──[취급자 제출]──> SUBMITTED
   │                            │                              │
   │                   [요청 취소(오탐)]          ┌───[승인]──┴──[반려]───┐
   │                            │                 ▼                       ▼
   └──[소명불요]──> DISMISSED <─┘             APPROVED                 REJECTED
                                                                         │
                                                        ┌───[재요청]─────┴──[에스컬레이션]──┐
                                                        ▼                                   ▼
                                                  REQUESTED (round +1)                 ESCALATED
```

**자동 소명 요청 (2026-10-01, 구현 M4 — 사용자 결정)**

| 항목 | 기준 |
|---|---|
| 동작 | 탐지 배치가 탐지건을 **새로 만들 때**, 같은 트랜잭션에서 즉시 `REQUESTED`(1차, 요청자 = 시스템, 메시지 "자동 소명 요청 — 룰 이름") |
| 조건 | 룰의 `auto_request`가 켜짐(기본 켜짐) **그리고** 행위자에게 재직 중이며 비활성(`DISABLED`)이 아닌 A5 계정이 있음. 잠김(`LOCKED`)·비밀번호 미설정 계정에도 요청은 간다(풀면 되는 일시 상태) |
| 조건 불충족 | `DETECTED`로 남기고 **담당자가 수동 처리** — 계정 없음·비활성·퇴직·미동기화 등. 퇴직자 접속은 원래 담당자 사안 |
| 기존 건 | 이미 진행 중인 `DETECTED` 건에 기록이 보태져도 자동 요청하지 않음(생성 시에만) |
| 하루 1건 | 그룹핑 `(취급자, 룰, KST 날짜)` 덕분에 하루 여러 번 걸려도 요청은 1번 |

- **왜 자동인가**: 수동 요청이면 담당자가 모든 탐지건을 먼저 검토해야 해 **병목·방치 위험**이 크다. 사람의 판단은 "요청할지"가 아니라 "소명을 받아들일지"에 집중시킨다.
- **담당자 요청 취소** `REQUESTED → DISMISSED`(사유 필수): 담당자는 전체 탐지건 목록을 보고, 오탐으로 판단되면 취급자 제출 전에 요청을 취소한다. 요청 후 제출 전에 퇴직해 건이 멈추는 경우도 이 전이로 닫는다.
- **취급자의 "오탐 취소 요청" 경로는 두지 않는다**(기각) — 흐름이 복잡해지고 취급자가 오탐 여부를 판단할 기준도 모호하다. 취급자는 소명 내용으로 사정을 설명한다.
- **부작용**: 오탐도 일단 취급자에게 간다 → 룰의 세밀한 설정(룰별 `auto_request` 조정)과 담당자의 빠른 요청 취소가 중요해진다.

**전이 거부 규칙 (2026-10-01, 구현 M4)**: 상태 전이는 **허용 목록(전이 표)** 하나로 정의하고 표에 없는 조합은 거부한다. 검사 순서와 응답:

| 순서 | 검사 | 실패 시 |
|---|---|---|
| 1 | 볼 수 있는 건인가 | `404` — 남의 건은 존재 여부도 드러내지 않음 |
| 2 | 역할이 맞는가 (제출은 취급자 본인, 그 외는 담당자) | `403 FORBIDDEN` |
| 3 | 현재 상태에서 허용된 전이인가 | `409 INVALID_TRANSITION` |

- 사유가 필요한 전이(소명 불요·요청 취소·반려)와 소명 내용은 앞뒤 공백 제거 후 1자 이상.

- **반려(`REJECTED`)는 독립 상태로 둔다.** 반려 직후 재요청할지 에스컬레이션할지는 담당자 판단이며, 그 판단 전 상태가 실무에 존재하기 때문이다.
- 재요청 시 `REQUESTED`로 되돌아가되 **round 카운터를 +1** 한다(반복 횟수 추적 → 요구사항 LOG-14 "소명 이력 누적"과 연결).
- `ESCALATED`는 플래그 및 보고서 표기까지만 담당한다. 이관 이후 프로세스는 아웃오브스코프(POV 스코프 경계).
- 모든 상태 전이는 **누가·언제·무슨 사유로** 바꿨는지 이력으로 남긴다(점검 수행 증적, ISMS-P 대응). 시스템(탐지 배치)이 한 전이는 행위자 NULL. 상태 전이는 Argus 접속기록이 아니라 이 **상태 이력**으로 남긴다(Argus 접속기록 대상은 LOGIN·READ·UNMASK·EXPORT — API명세서 2-7).

### 3-3. 소명 근거 (2026-10-02 신설, 기능 레이어 7)

소명 = **텍스트(필수) + 근거자료 첨부(선택) + 관련 업무 티켓(선택)**.

| 구성 | 규칙 |
|---|---|
| 텍스트 | 필수, 5,000자 |
| 첨부 | PNG·JPG·PDF, 파일당 5MB, 차수당 3개. 내부 업무 요청이 근거면 결재 문서 PDF·지라 티켓 캡처·요청 메일 등. 형식·무결성·권한·기록 규칙은 DB스키마 3-4 "소명 첨부 규칙" |
| 관련 업무 티켓 | 플랫폼 1:1 문의 번호(`INQ-n`)를 **별도 입력칸**에 최대 3개. 서버는 형식만 검사하고 **실제 근거인지는 취급자·담당자가 판단**. 담당자는 링크로 플랫폼에서 내용을 확인 |

- **Argus는 티켓 내용을 보유하지 않는다**(사용자 제안) — 문의 제목·본문을 받으면 절대 규칙 #3(원본 개인정보 금지)과 두 시스템 분리가 깨진다. 담당자의 플랫폼 열람은 다시 플랫폼 접속기록으로 Argus에 남는다(감시자도 감시됨).
- 기각: ①플랫폼 → Argus 티켓 동기화 후 검색·선택(새 시스템 간 API·동기화로 복잡) ②Argus가 플랫폼을 실시간 조회해 본문 표시(규칙 #3·네트워크 분리 위반) ③원장 기반 후보 목록("이 취급자가 연 티켓") — 사용자 판단: 직접 조회하지 않은 티켓을 처리하는 경우(업무 이관)도 있고 원장엔 내용이 없어 결국 링크가 필요.
- 소명과 티켓의 **자동 대조**는 v0.2(내부 업무 요청 티켓과 함께 설계).

**경로별 소명 기준 (2026-10-05, 사용자 요구 — 1-5)**: 양식(텍스트 + 첨부 + 관련 티켓)은 같고, 소명 화면의 **작성 안내**와 담당자 **검토 기준**이 경로에 따라 다르다.

| | 화면 경유(3티어) | DB 직접(2티어) |
|---|---|---|
| 전형적인 행위 | 고객 응대 중 회원 조회, 정기 업무의 목록·다운로드 | **내부 담당자 요청에 따른 대량 조회·수정**, 데이터 보정, 장애 대응 (사용자 실무 경험) |
| 작성 안내 | 어떤 고객·업무를 처리하던 중이었는지, 관련 문의 티켓(`INQ-n`) | **누가 요청했는지(요청자·부서), 요청 근거(티켓·메일·결재 문서 첨부), 작업 목적, 대상 범위(조건·건수)**, 변경이면 변경 전후 확인 방법 |
| 담당자 검토 기준 | 업무 맥락(티켓)과 조회 대상·시점이 맞는가 | **요청 근거가 실재하고 작업 범위가 요청 범위를 넘지 않는가**. 앱을 우회한 변경이면 앱으로 할 수 없었던 이유가 있는가 |
| 근거 특성 | 플랫폼 문의 티켓(링크로 확인) | 대부분 플랫폼 밖 기록(지라·메일·결재) → **첨부가 주 근거**. 토큰 발급 사유를 받지 않으므로(사용자 결정) 소명이 유일한 사유 기록 |

- v0.1은 **안내 문구·검토 기준 분리**까지. 2티어 전용 입력칸(요청자·요청 티켓 번호 등)과 명령어 결재(v0.2 명령어 통제) 연결은 v0.2 검토.

## 4. 취급자 모델

### 4-1. 권한 매트릭스 제외 (2026-09-15 결정)

기능별 권한 매트릭스와 "권한 외 접근 시도" 탐지 룰은 **채택하지 않는다.**

**사유(실무 근거)**: 조직에서 팀·권한이 다르면 애초에 해당 시스템·DB 접근 자체가 차단된다. 권한 없는 계정이 조회에 성공했다면 그것은 탐지 대상이 아니라 이미 발생한 보안사고다. 따라서 점검 서비스의 탐지 룰로 다루는 것이 적절하지 않다.

> 단, 감시 대상 플랫폼 쪽에는 관리자 메뉴 노출과 권한 차등 부여(PLT-10·14)를 위한 **역할(role) 구분은 필요**하다. 이는 탐지 룰의 대상이 아니라 무대장치의 기능이다.

### 4-2. 유지하는 속성

권한 매트릭스는 빼되, 취급자 계정의 다음 속성은 유지한다.

| 속성 | 용도 |
|---|---|
| 계정 식별자 | 접속기록 매칭, 소명 요청 대상 지정 |
| 소속(팀) | 보고서 팀별 집계, 향후 "소속과 무관한 데이터 조회" 류 룰의 여지 |
| 재직 상태 + **퇴직 시각** | 퇴직자 계정의 접속 탐지 (1-3절 — 행위 시점 기준 판정에 퇴직 시각이 필요) |

- 안전조치기준 §5③(권한 부여·변경·말소 내역 3년 보관)은 법정 의무이므로 이력 기록 자체는 유지하되, 구현 우선순위는 Should로 둔다.
- **취급자 정보의 최소수집**: 취급자(직원) 정보도 개인정보다. Argus가 보유하는 것은 계정·이름·소속·재직상태·퇴직시각으로 한정하고, 연락처·사번·권한 상세는 받지 않는다.
- ~~**2단계 주의**: DB 직접 접근 로그의 식별자는 DB 계정(또는 접근제어 경유 시 그 사용자 ID)이므로, 플랫폼 관리자 계정과 **동일인 매핑**이 필요하다. 2단계 착수 시 검토.~~ → **해소 (2026-10-05, 2티어 설계 확정)**: DB 접속 토큰은 플랫폼 관리자 화면에 로그인한 사람에게 발급되고, DB 툴의 사용자 이름도 **본인 플랫폼 아이디**다. 게이트웨이가 토큰의 주인과 아이디가 같은지 확인하므로 DB 접근 기록의 식별자가 곧 플랫폼 아이디(= Argus 명부 아이디, 4-4)다 → 별도 매핑 표가 필요 없다. DB 계정(공용)은 `context.db_user`로 따로 남는다.

### 4-4. 아이디 일원화 — 플랫폼 백오피스 아이디 = Argus 아이디 (2026-10-02, 사용자 원칙)

- 한 사람은 플랫폼 관리자 화면과 Argus에서 **같은 아이디**를 쓴다. 취급자(A5)는 동기화로 자연히 같고, **정보보호 담당자(A4)도 플랫폼 계정을 가진다**(소명 티켓 링크로 문의를 열어 보기 위해 — 3-3).
- 담당자의 플랫폼 계정은 동기화로 Argus 명부에도 들어가며, Argus 담당자 계정 생성 시 그 명부 계정을 담당자로 전환한다(API명세서 3-1). 소속·권한은 기존 값(OPS/ADMIN) — 플랫폼 소속 목록과 Argus 명부 검증을 바꾸지 않기 위함(정보보호팀 소속은 필요해지면 추가).
- **보안성 검토 이월**: ①담당자의 플랫폼 계정이 일반 관리자와 같은 권한(CSV 다운로드 포함 — 플랫폼 권한 차등 PLT-14는 범위 밖) ②담당자 본인의 플랫폼 행위가 탐지되면 자동 소명 요청이 가지 않아(A5 아님) **담당자가 자기 건을 검토**하게 됨 — 직무 분리 문제.

### 4-3. 관리자 인증·로그인 실패 정책 (2026-09-30 신설, 구현 M2)

플랫폼 관리자(취급자) 로그인에 적용한다. Argus 사용자(A4·A5) 로그인(M4)도 같은 기준을 따른다. **고객(정보주체) 로그인은 아래 "고객 인증"을 따른다.**

| 항목 | 기준 | 근거 |
|---|---|---|
| 로그인 실패 제한 | **5회 연속 실패 시 계정 잠금**, 성공하면 실패 횟수 0으로 초기화 | 안전조치기준 §5⑥ (일정 횟수 이상 인증 실패 시 접근 제한) |
| 잠금 해제 | 관리 스크립트로만 해제 (관리 UI는 범위 밖) | |
| 미사용 시 차단 | **30분 미사용 시 인증 만료** (요청마다 만료 연장) | 안전조치기준 §6④ (일정 시간 미사용 시 자동 접속 차단) |
| 상태 재확인 | 매 요청마다 계정 상태(퇴직·잠금) 확인 — 로그인 후 퇴직·잠금되면 즉시 차단 | §5② (업무 변경 시 지체 없이 권한 변경·말소) |
| 퇴직자 | 로그인 거부 | |

**응답·기록 원칙**

- **계정 존재 여부를 드러내지 않는다.** 없는 ID와 틀린 비밀번호는 같은 응답(401)을 주고, 없는 ID도 더미 해시로 검증을 수행해 **응답 시간**으로도 구분되지 않게 한다.
- **잠김·퇴직(403)은 비밀번호가 맞았을 때만 알려준다** — 비밀번호를 모르는 사람에게 "이 계정은 존재하고 잠겨 있다"를 알려주지 않는다.
- **접속기록**: 존재하는 계정의 실패(비밀번호 오류·잠김·퇴직자)는 `LOGIN`/`FAILURE`로 기록한다. **존재하지 않는 ID의 실패는 기록하지 않는다** — ID 칸에 잘못 입력된 비밀번호가 append-only 원장에 영구 저장되는 것을 막기 위함이며, 그 값은 §2 3호의 취급자 식별자도 아니다. 로그아웃은 개인정보 처리가 없어 기록 대상이 아니다.
- 입력 길이 상한(`login_id` 64자, 비밀번호 256자) — 초대형 비밀번호로 해시 계산 시간을 늘리는 공격 방지.

**알려진 한계** (보안성 검토 단계 과제 — 아키텍처 설계서 8-6): 시간 경과로 풀리지 않는 잠금은 일부러 틀려 정상 사용자를 잠그는 서비스 거부에 쓰일 수 있음 / 계정 단위 계산이라 password spraying 미탐지 / IP 단위 제한 없음 / 존재하지 않는 ID 대입은 Argus에 보이지 않음 / 로그아웃 후에도 토큰은 만료 전까지 유효.

**고객 인증 (2026-10-01 결정, 기능 레이어 7 — 고객 화면 최소판)**

| 항목 | 기준 | 이유 |
|---|---|---|
| 계정 체계 분리 | 고객 `member` / 관리자 `operator`는 **권한(role)이 아니라 계정 체계 자체가 다름**. 로그인 입구·세션 쿠키도 분리(고객 `customer_session`, 관리자 `platform_session`). 판단은 항상 서버 | |
| **토큰 audience 분리** | 토큰에 audience(고객용/관리자용)를 넣고 검증한다 | 같은 키로 서명하고 id만 넣으면 **고객 3번 토큰이 관리자 3번으로 통과**할 수 있음(토큰 바꿔치기). 테스트로 고정 |
| 로그인 실패 | **5회 연속 실패 → 15분 잠금(자동 해제)**. 잠긴 동안의 실패는 세지 않음(잠금이 끝없이 연장되지 않게), 잠김은 비밀번호가 맞을 때만 알림 | 비밀번호 찾기가 없어 영구 잠금은 고객이 스스로 풀 수 없음. 관리자(영구 잠금·스크립트 해제)와 다름 |

| 가입 수집 항목 | ~~이메일·비밀번호·이름만, 휴대전화·주소는 마이페이지에서 선택 입력~~ → **(2026-10-07 보강) 이메일·비밀번호·이름·휴대폰 번호(필수)**. 휴대폰은 주문·배송 연락용. **생년월일·성별은 선택으로도 받지 않는다**(쓸 목적이 없음). 주소는 회원 정보가 아니라 **배송지**(마이페이지에서 등록, 여러 개). 이메일은 소문자 정규화, 로그인 아이디라 정정 대상 아님(이메일 인증이 없어 소유 확인 수단이 없음) | 최소수집 §16① |

| 고객 행위 기록 | Argus 접속기록 대상 아님 | §8① 단서(정보주체 제외) — 절대 규칙 #4 |

- 고객 로그인 실패 정책은 **보안성 검토 때 재확인**한다(15분 자동 해제가 무차별 대입을 충분히 늦추는지 등).

> **탐지 근거의 보존 (2026-09-23 보완)**: 접속기록이 1년 후 파기되면 탐지건의 하위 근거 로그도 사라져 "탐지·소명 이력은 접속기록과 동일 이상 보관"이 형해화된다. 따라서 탐지건 생성 시 **근거 로그의 요약(건수·시각 범위·수행업무·처리 건수 합 등)을 탐지건에 스냅샷으로 남긴다.** 요약에는 정보주체 식별값을 담지 않는다.

### 5-2. 점검 주기

점검 주기는 Argus에서 **설정값**으로 둔다. 2026.7.1 고시 §8②는 점검 주기·방법·사후조치절차를 내부 관리계획으로 정하도록 조직 자율에 위임하고 있다(2024.10 안내서의 "월 1회 이상" 문구는 현행 고시 원문에 없음 — 요구사항정의서 2절 주석). 기본값은 월 1회로 두되 담당자가 변경할 수 있게 한다.

### 5-3. 자동 파기 배치

파기는 수동이 아닌 **일 1회 배치**로 자동 이행한다.

| 항목 | 내용 |
|---|---|
| 실행 주기 | 일 1회 |
| 대상 | ① 보관기간이 만료된 접속기록 ② 탈퇴 후 법정 보존의무가 없는 회원 개인정보 ③ 보유기간이 만료된 기타 항목 |
| 파기 방식 | 복원 불가능한 삭제 — 논리삭제(flag)가 아닌 실제 삭제. 안전조치기준 §13①3호 "복원되지 않도록 초기화 또는 덮어쓰기" |
| 분리보관 | 법정 보존의무로 남기는 항목은 다른 개인정보와 **분리하여 저장·관리** (PIPA §21③) — 별도 테이블로 옮기고 접근 권한을 달리 부여하며, 보존 목적에 필요한 최소 항목만 담는다 (DB스키마 4-1절) |
| 파기 이력 | 파기일시, 대상 유형, 파기 건수, 적용 근거를 기록. **이력에 개인정보 자체를 남기지 않는다**(파기한 정보가 이력에 남으면 모순) |
| 백업과의 관계 | 서버 백업(일 1회, 7일 보관)에도 파기 대상이 남아 있으므로, 원본 파기 후 최대 7일 내에 백업에서도 소멸한다 (아키텍처 설계서 8-4절) |

**이 배치가 갖는 의미**: 파기 이행 여부는 ISMS-P 점검에서 반복적으로 확인되는 항목이며, 자동 배치 + 파기 이력은 그 자체로 증적이 된다. 구현 후 보안성/ISMS-P 점검 실습 단계에서 활용한다.

> **검토 메모**: 파기 배치는 시스템 계정이 수행하는 행위이므로 §2 3호의 "개인정보처리시스템에 접속하는 자"에 해당하는지 해석의 여지가 있다. 실무에서는 시스템 계정 명의로 기록하는 것이 일반적이므로 동일하게 기록하되, 탐지 룰 평가 대상에서는 제외(화이트리스트)한다.

## 6. 정보주체 식별값 노출 통제

액터별_플로우 8절이 정한 화면 마스킹 정책(정보보호 담당자만 사유 입력 후 해제, 취급자는 해제 불가)에 더해, 아래를 보완한다.

> **⚠ 2026-10-01 결정 — Argus 식별값 해제(언마스킹)는 v0.2 이후로 보류** (기능 레이어 2, 사용자 결정)
> - **이유**: Argus는 절대 규칙 #3에 따라 회원 **내부 PK만** 보유한다. 해제해도 회원번호뿐이라 실무 가치가 제한적이다. 실제 개인정보(이름·이메일·전화·주소)는 **플랫폼에 있고**, 지금 플랫폼 관리자 화면·CSV는 **마스킹 없이 표시**된다 → 표시제한 통제는 플랫폼에 두는 것이 맞다.
> - **진행**: v0.1 이후 보안성 검토·ISMS-P 점검에서 "플랫폼 개인정보 표시제한 미적용"을 **발견사항**으로 다루고, 조치로 플랫폼 관리자 화면에 마스킹 + 사유 입력 해제를 구현 → 해제 행위가 Argus 원장에 남는 것으로 이행 증적을 만든다(점검 → 조치 사이클).
> - **유지**: Argus의 회원번호 **마스킹은 그대로**. 점검 보고서(기능 레이어 9)는 v0.1에서 **마스킹 보고서만** 만든다(아래 6-1의 언마스킹 export·`EXPORT` 사유는 함께 보류).
> - **위험 수용**: 플랫폼 관리자 화면·CSV의 표시제한 미적용은 v0.1의 **알려진 미흡 사항**이다(아키텍처 설계서 8-6).

### 6-1. 점검 보고서 export (2026-09-23 신설)

| 항목 | 정책 |
|---|---|
| 기본 | 보고서는 **마스킹된 식별값**으로 생성한다 |
| 예외 | 식별값을 포함한 보고서가 필요하면 **사유를 입력**해야 하며, 정보보호 담당자만 가능 — **v0.2 이후(언마스킹 보류와 함께)** |
| 기록 | 보고서 생성은 Argus 접속기록에 `EXPORT`로 기록하고, 언마스킹 보고서인 경우 사유를 함께 남긴다. **구현(2026-10-07)**: `EXPORT` + `context.report_id`, 건수 = 보고서에 실린 마스킹 식별값 수. 보고서를 다시 여는 것은 `READ` + `report_id` |
| 식별값 표시 (2026-10-07, 사용자 결정) | 탐지건마다 **마스킹 식별값 앞 3개 + "외 N명"**(고유 정보주체 수 기준). DB 직접 건은 **"미특정 N건"**(회원번호 추출 보류 — 1-3) |
| 내용 = 생성 시점 스냅샷 (2026-10-07) | 생성 때 집계를 `summary`에 고정한다 — 나중에 탐지건 상태가 바뀌어도 **보고한 내용이 그대로** 남아야 점검 증적이 된다. 머리에 **점검 수행 확인**(원장 해시체인 전체 재계산 결과 §8③, 기간 중 탐지 배치 실행·실패 §8②)을 싣고, 경로별 섹션에 접속기록·탐지건·소명 수치와 탐지건 목록(심각도 순 최대 50)을 싣는다 |
| 형식 (2026-10-07) | **서버에 파일을 만들지 않는다.** 보고서 화면(인쇄용)이 스냅샷을 그리고, 담당자가 브라우저의 "인쇄 / PDF로 저장"으로 파일을 만든다(외부 라이브러리 없음). 경로 섹션마다 새 쪽 — 경로별로 떼어 보고할 수 있게 |

> **왜 필요한가**: 화면에서는 마스킹을 강제하는데 보고서 파일로는 그냥 빠져나갈 수 있다면, 마스킹 정책 전체가 무력화된다. 보고서는 파일로 조직 밖으로 이동할 수 있어 화면보다 통제가 더 중요하다. 근거는 §12①(출력 시 용도 특정·출력 항목 최소화)로 화면 표시에 적용한 것과 같다.

> **알려진 한계 (2026-10-07)**: 브라우저 인쇄·PDF 저장은 클라이언트 동작이라 Argus가 기록할 수 없다 — 생성(`EXPORT`)과 열람(`READ`)만 남는다. 보고서 화면 열람 자체가 기록되므로 실무상 충분하다고 보고, 보안성 검토 때 다시 확인한다.

### 6-2. 정보주체 ID 검색

접속기록을 정보주체 식별값으로 검색하는 행위(LOG-02)도 식별값을 평문으로 다루는 행위이므로, Argus 접속기록에 `READ`로 기록하고 **검색 조건의 키 이름만** 남긴다(검색어 값은 기록하지 않는다).

### 6-3. Argus 자체 기록의 식별자 중복 축적 방지

Argus에서 탐지건·로그를 조회할 때마다 회원 식별자를 Argus 접속기록에 다시 적재하면 식별자가 중복 축적되어 최소처리 원칙에 반한다. 따라서 Argus 자체 기록에는 **처리 건수만** 남기고, 예외적으로 마스킹 해제(`UNMASK`)만 대상 탐지건 ID를 남긴다(API명세서 2-7절).
