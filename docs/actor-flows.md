# 액터별 플로우 (Argus)

> 작성 2026-09-21 · 최종 개정 2026-10-10
> 관련 문서: [요구사항정의서](requirements.md), [정책정의서](policy.md), [DB스키마](db-schema.md), [API명세서_시스템간](api-spec.md)
> 서비스명: Argus — 그리스 신화의 눈 100개 달린 파수꾼. "접속기록을 지켜보는 눈"

> 일반적으로 "유저플로우"라 부르지만, 이 프로젝트는 액터가 5종이고 시스템 자동 동작까지 포함하므로 **액터별 플로우(업무흐름도)**로 명명한다.

## 1. 액터 정의

| # | 액터 | 소속 시스템 | 법적 지위 | 접속기록 대상 |
|---|---|---|---|---|
| A1 | 고객 | 플랫폼 | **정보주체** | **❌ 대상 아님** |
| A2 | CS 담당자 | 플랫폼 | 개인정보취급자 | ✅ |
| A3 | 운영·마케팅 담당자 | 플랫폼 | 개인정보취급자 | ✅ |
| A4 | **정보보호 담당자** | Argus | 점검 수행자 (주 사용자) | ✅ (Argus 자체 기록) |
| A5 | 개인정보취급자(소명자) | Argus | = A2·A3과 **동일인** | ✅ (Argus 자체 기록) |
| S | 시스템 배치 | 양쪽 | 시스템 계정 | 기록하되 탐지 제외 |

### 1-1. 접속기록 생성 원칙

안전조치기준 §8① 단서: **"개인정보처리시스템에 접속한 자(다만, 정보주체는 제외한다)"**

→ **고객(A1)의 모든 행위는 접속기록 대상이 아니다.** 가입·로그인·주문·결제·문의 등 고객이 자기 정보를 다루는 행위는 아무리 발생해도 Argus로 전송되지 않는다. 접속기록은 **취급자(A2~A5)가 타인의 개인정보를 처리한 기록**만을 의미한다.

> 구현 시 혼동하기 쉬운 지점. 플랫폼의 로깅 지점은 **관리자 UI에만** 심는다.

### 1-2. 액터 간 연결 구조

```
   ┌─────────────── 플랫폼 ───────────────┐      ┌──────── Argus ────────┐
   │                                      │      │                       │
   │  A1 고객 ──(정보 제공)──> [고객 DB]   │      │                       │
   │                             ▲        │      │                       │
   │  A2 CS 담당자 ──(조회/수정)─┤        │      │   A4 정보보호 담당자   │
   │  A3 운영 담당자 ─(조회/DL)──┘        │      │        │              │
   │            │                         │      │        │ 소명 요청     │
   │            └── 접속기록 생성 ─────────┼─API─>│        ▼              │
   │                                      │      │   A5 취급자(소명)     │
   └──────────────────────────────────────┘      └───────────────────────┘
                     ▲                                      │
                     └──────── 동일 인물 ────────────────────┘
```

**핵심**: A2·A3(플랫폼에서 일하는 취급자)과 A5(Argus에서 소명하는 취급자)는 같은 사람이다. 같은 인물이 플랫폼에서 업무를 보다가, Argus에서 그 행위에 대한 소명을 요구받는다. 이 동선이 두 시스템을 잇는 연결고리다.

## 2. F-01. 고객 플로우 (플랫폼 / A1)

| # | 행위 | 시스템 동작 | 접속기록 | 요구사항 |
|---|---|---|---|---|
| 1 | 회원가입 | 이메일·비밀번호·이름·휴대폰 번호(필수). 동의는 이용약관(필수)·개인정보 수집·이용(필수)·만 14세 이상 확인(필수)·마케팅 수신(선택)을 따로 받고 항목마다 목적·항목·보유 기간을 보여 준다 → 계정 생성, 비밀번호 일방향 해시. 동의 이력 기록(항목·버전·시각·IP) | ❌ | PLT-01 |
| 2 | 로그인 | 인증. 5회 실패 시 15분 잠금(정책정의서 4-3 고객 인증) | ❌ | PLT-02 |
| 3 | 상품 조회 → 주문 | **로그인 필수**(비로그인 → 로그인 화면 → 원래 상품). **등록된 배송지 선택**(없으면 "마이페이지에서 배송지를 등록해 주세요" 안내) → 주문 생성, 주문에 배송 정보 스냅샷 저장 | ❌ | PLT-04 |
| 4 | 결제 | 결제할 때마다 **PG 목업 결제창에서 카드사 선택 + 카드번호·유효기간 직접 입력**. 카드번호는 결제창(브라우저) 안에만 두고(형식 확인 없음) **플랫폼 서버로 보내지 않는다**(실제로도 카드번호는 PG만 받음) → 플랫폼은 카드사·PG 거래번호·승인 시각·금액만 저장. 카드 저장·관리 없음 | ❌ | PLT-05 |
| 4a | 환불계좌 등록 (마이페이지) | **계좌번호 앱 레벨 암호화 저장**(§7②6호) | ❌ | PLT-05 |
| 4b | 배송지 관리 (마이페이지) | 배송지 등록·수정·삭제·기본 지정 | ❌ | PLT-03 |
| 5 | 1:1 문의 등록 | 티켓 생성 → **CS 조회의 업무 근거가 됨** | ❌ | PLT-06 |
| 6 | 마이페이지 — 내 정보 열람·정정(이름·휴대폰, 이메일 제외), 비밀번호 변경, **선택 동의 철회·재동의** | | ❌ | PLT-03 |
| 7 | 회원 탈퇴 | **v0.1: 탈퇴 처리 트랜잭션에서 즉시 파기**(회원·동의 이력 실제 삭제, PIPA §21). 법정 보존의무 항목 **분리보관**(§21③)은 주문 기능과 함께 | ❌ | PLT-03 |
| 8 | 개인정보 처리방침·이용약관 열람 | 처리방침에 적은 항목과 실제 저장 항목이 일치함을 보여 준다 | ❌ | PLT-01 |

> **고객 화면 최소판**: 고객 행위는 Argus 접속기록 대상이 아니므로, 고객 화면은 Argus 시연용이 아니라 처리시스템이 갖춰야 할 개인정보 처리 단계(수집·동의·열람·정정·철회·파기, ISMS-P 3영역 처리 단계별 요구사항)를 구현하는 범위다. 화면은 platform-web 한 앱에서 URL 경로로 나눈다(고객 `/`, 관리자 `/admin`). 제외(v0.2 이후): 비밀번호 찾기, 이메일·휴대폰 인증, 실제 PG 결제, 소셜 로그인.

> 5번(문의 등록)이 단순한 고객 기능이 아니다. 이 티켓의 존재 여부가 나중에 **"CS가 이 고객을 조회한 데 업무적 이유가 있었는가"**를 판정하는 근거가 된다(스트레치: 업무시스템 연동 대조).

## 4. F-03. 운영·마케팅 담당자 플로우 (플랫폼 / A3)

| # | 행위 | 시스템 동작 | 접속기록 (수행업무 / 정보주체) | 탐지 연관 |
|---|---|---|---|---|
| 1 | 관리자 로그인 | | ✅ `LOGIN` / — | 야간·주말 접속 룰 |
| 2 | 회원 목록 조회 (검색·필터) | 이름·이메일·연락처(부분 일치)·상태·가입일로 검색. 조건은 요청 본문으로 보낸다 | ✅ `READ` / 결과로 보인 회원 전부(0건도 기록, 검색 조건은 키 이름만) | 대량 조회 룰 |
| 3 | 회원 상세 조회 | | ✅ `READ` / member_xxx | 전월 대비 급증 룰 |
| 4 | 주문 목록·회원 상세 조회 | 환불계좌는 **끝 4자리만** | ✅ `READ` / 주문(ORDER)·회원 기본(MEMBER_BASIC) | — |
| 4a | **환불계좌 "전체 보기"** | 확인 창("환불계좌 전체 번호를 조회합니다. 계속할까요?")을 거쳐 복호화한 전체 번호 | ✅ `READ` / member_xxx (대상=**결제수단**) | **결제수단 조회 룰(심각도 상)** — 볼 때마다 소명 |
| 5 | 회원 목록 다운로드 | CSV/Excel export | ✅ `DOWNLOAD` / 대상 건수 N | **대량 다운로드 룰(심각도 상)** |
| 6 | 로그아웃 | | ✅ `LOGOUT` / — | — |

> **관리자 로그인·로그아웃 기록 규칙** (F-02·F-03 공통): 로그인 실패는 존재하는 계정일 때만 `LOGIN`/`FAILURE`로 기록하고, 존재하지 않는 ID의 실패는 기록하지 않는다. 로그아웃은 `LOGOUT`으로 기록한다(로그인한 사용자만 — 인증되지 않은 로그아웃 요청은 행위자가 없어 기록하지 않음). 5회 연속 실패 시 계정이 잠긴다. 로그인 화면에는 감시 고지 문구 없이 시스템 소개 문구만 있다. 상세는 [정책정의서](policy.md) 4-3절.
>
> **역할별 접근 범위** (F-02·F-03 공통, [정책정의서](policy.md) 4-5): 회원 조회·검색은 모든 역할, 주문·1:1 문의·환불계좌 전체 보기는 ADMIN·OPS·CS, 회원 CSV 다운로드·DB 접속 토큰(메뉴 "DB 직접 접근")은 ADMIN·OPS만 쓸 수 있다. 예를 들어 마케팅 담당자는 4번 주문 조회, 4a 전체 보기, 5번 다운로드를 할 수 없다 — 메뉴·버튼이 보이지 않고, 직접 요청하면 `403`이며 그 시도는 접속기록에 `FAILURE`로 남는다.

### 4-1. 플랫폼 ADMIN 계정·권한 관리

ADMIN 역할만 관리자 메뉴 "계정·권한"을 쓴다. 계정·비밀번호 화면은 회원 개인정보 처리가 아니어서 접속기록 대상이 아니며, 모든 변경은 권한 이력(`operator_permission_history`)에 남는다.

| # | 행위 | 시스템 동작 | 권한 이력 | 요구사항 |
|---|---|---|---|---|
| 1 | 계정 목록 확인 | 아이디·이름·팀·역할·재직 상태·최근 변경 | — | PLT-14 |
| 2 | 계정 부여 | 아이디·이름·팀·역할·사유 입력 → 임시 비밀번호를 한 번만 보여 줌 → Argus 명부 동기화(역할 값은 보내지 않음) | `GRANT` | PLT-14 |
| 3 | (새 관리자) 첫 로그인 | 비밀번호 변경 화면으로 이동. 바꾸기 전에는 다른 요청이 `403 PASSWORD_CHANGE_REQUIRED` | — | PLT-14 |
| 4 | 역할·팀 변경 | 사유 필수. 같은 값이면 `409 NO_CHANGE` → 명부 동기화 | `CHANGE` | PLT-14 |
| 5 | 말소(퇴직 처리) | 사유 필수 → 이후 로그인·세션·DB 접속 토큰 발급 불가, 명부에 퇴직 시각 동기화(Argus 퇴직자 계정 접속 룰의 기준) | `REVOKE` | PLT-14 |
| 6 | 권한 이력 확인 | 대상·기간으로 검색(조건은 요청 본문) | — | PLT-14 |

- 본인 계정은 역할·팀 변경과 말소 모두 할 수 없다(`403 SELF_CHANGE_FORBIDDEN`).
- 잠금 해제는 관리 스크립트로 한다(화면 없음).

## 5. F-04. 탐지 배치 (시스템 / S)

| # | 동작 |
|---|---|
| 1 | 주기 도래 (5분~1시간, 설정값) |
| 2 | 직전 실행 이후 수집된 신규 접속기록 조회 (`id` 커서) |
| 3 | 활성 룰 평가 — 룰의 접근 경로로 대상 로그를 먼저 거른 뒤, **EVENT**는 로그 단건 조건식 판정, AGGREGATE는 윈도우 집계 후 임계치 비교 |
| 4 | 조건 충족 시 그룹핑 키(EVENT 룰은 `(취급자, 룰, 접근 경로, 날짜, 데이터 유형, 행위 구분)`, 정책정의서 2-2)로 **진행 중인** 탐지건 조회 → 없으면 생성(`DETECTED`), 있으면 하위 로그만 추가(붙은 시각 기록 — 소명 제출 뒤 추가 기록 판정용). 같은 그룹의 기존 건이 이미 종결(`APPROVED`·`DISMISSED`·`ESCALATED`)됐다면 새 탐지건을 생성 (정책정의서 2-3절) |
| 5 | **자동 소명 요청** — 탐지건을 새로 만들 때 룰의 `auto_request`가 켜져 있고 행위자에게 로그인 가능한 A5 계정이 있으면 같은 트랜잭션에서 `REQUESTED`(1차, 요청자 = 시스템). 아니면 `DETECTED`로 남겨 담당자가 수동 처리 (정책정의서 3-2) |
| 6 | 알림 생성 — 상 탐지건은 담당자 전원에게, 소명 요청은 해당 취급자에게(받는 사람·심각도별 수단은 정책정의서 3-6). 웹 푸시 대상은 순찰마다 발송 |
| 7 | 소명 기한 판정 — 제출되지 않은 요청의 기한 임박(남은 24시간 이하)·초과를 판정해 취급자와 담당자 전원에게 알림(차수마다 한 번씩, 상태는 바꾸지 않음 — 정책정의서 3-4) |

> 4번의 "있으면 하위 로그만 추가"가 소명 폭증을 막는 핵심 로직이다. 같은 사람이 같은 날 같은 성격의 처리로 같은 룰에 10번 걸려도 탐지건은 1개, 소명도 1회다. 단, 승인·종결 이후의 새 행위는 새 판단 대상이므로 종결된 건에 붙이지 않는다.

## 8. 정보주체 식별값 마스킹 정책

### 8-1. 대상

접속기록의 `처리한 정보주체 정보` 필드에는 회원 테이블의 **내부 식별자(PK)**를 기록한다(예: `member_10293`). 이름·이메일 등은 직접 기록하지 않는다.

> **표기 규칙**: 저장·전송 시에는 `subject_type=MEMBER` + `subject_ids=["10293"]`처럼 순수 식별자만 쓰고, `member_10293`은 화면·보고서 표시 표기다. 마스킹 표시는 `member_10***`. ([DB스키마](db-schema.md) 2-1절)

> **이 내부 PK도 개인정보다.** PIPA §2 1호 나목은 "해당 정보만으로는 특정 개인을 알아볼 수 없더라도 다른 정보와 쉽게 결합하여 알아볼 수 있는 것"을 개인정보로 정의한다. 회원 테이블과 결합하면 즉시 식별되므로 결합 용이성이 인정되며, 따라서 마스킹 대상이다.

### 8-2. 정책

| 구분 | 정보보호 담당자 (A4) | 취급자 (A5) |
|---|---|---|
| 기본 표시 | 마스킹 (`member_10***`) | 마스킹 (`member_10***`) |
| 마스킹 해제 | **가능** (점검 업무상 필요) | **불가** |
| 해제 시 사유 입력 | **필수** | — |
| 해제 행위 로깅 | **Argus 접속기록에 `UNMASK`로 기록** | — |

**취급자에게 해제를 허용하지 않는 이유**: 본인이 과거에 처리했던 정보라 하더라도, 소명에 필요한 것은 행위 시각·수행업무·건수이지 대상 식별값이 아니다. "9/15 23시에 회원 40건 다운로드"만으로 대부분 소명이 가능하다. 반대로 해제를 허용하면 Argus가 취급자에게 개인정보를 재차 제공하는 결과가 되어 최소처리 원칙에 반한다.

**사유 입력을 요구하는 근거**: 안전조치기준 §12①("개인정보의 출력 시 용도를 특정하여야 하며, 용도에 따라 출력 항목을 최소화")의 취지를 화면 표시에 적용한 것.

> **보고서 export에도 적용**: 화면에서만 마스킹하고 보고서 파일로는 그대로 빠져나가면 정책 전체가 무력화된다. 보고서도 기본 마스킹이며, 언마스킹 보고서는 사유 필수 (정책정의서 6-1절).

## 9. Argus 자체 접속기록 — 자기참조 구조

Argus는 `처리한 정보주체 정보`를 보유하므로 **그 자체가 개인정보처리시스템**이며, Argus를 사용하는 정보보호 담당자(A4)와 취급자(A5)도 개인정보취급자다. 따라서 Argus 내부 행위도 §8의 적용을 받는다.

| 행위 | 기록 여부 | 비고 |
|---|---|---|
| Argus 로그인 | ✅ `LOGIN` | |
| Argus 로그아웃 | ✅ `LOGOUT` | 로그인한 사용자만 |
| 탐지건 상세 조회 | ✅ `READ` | 마스킹 상태로 조회. **정보주체는 건수만 기록**(식별자 중복 축적 방지 — 정책정의서 6-3절) |
| **마스킹 해제** (v0.2) | ✅ `UNMASK` | 사유와 대상 탐지건 ID를 함께 기록 — 가장 민감한 행위 |
| 탐지건·접속기록 검색, 취급자 내 접속기록 | ✅ `READ` | 검색 조건은 키 이름만 기록. 취급자가 남의 아이디·Argus 자체 기록을 요청하면 거부하고 `FAILURE`로 기록 |
| 본인 건 처리 시도(거부) | ✅ `UPDATE` / `FAILURE` | 정책정의서 3-5. 사유 문장은 기록하지 않음 |
| 상태 전이·룰 변경·계정 관리·보호 대상 등록 | ❌ | 상태 이력·룰 변경 이력·계정 이력·등록부 이력이 증적 |
| 알림 조회 | ❌ | 정보주체 처리 없음 |
| 보고서 export | ✅ `EXPORT` | 언마스킹 보고서면 사유 함께 기록 |

**범위**: Argus 자체 접속기록은 기록·보관까지만 구현한다. 이 기록을 Argus 자신의 탐지 룰로 평가하는 것(점검자에 대한 자동 점검)은 범위 밖이며, Argus 자체 기록은 접속기록 검색(출처 ARGUS)으로 정기 점검한다(정책정의서 1-2).

> **"감시자는 누가 감시하는가(Quis custodiet ipsos custodes)"** — §8②는 개인정보처리자 일반에 적용되므로 논리적으로는 Argus 운영자도 자기 접속기록을 점검해야 한다. 자동 점검은 구현하지 않되, 기록을 남기고 검색으로 점검할 수 있게 해 이 구조에 대응한다.
