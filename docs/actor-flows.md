### 1-1. 접속기록 생성 원칙

안전조치기준 §8① 단서: **"개인정보처리시스템에 접속한 자(다만, 정보주체는 제외한다)"**

→ **고객(A1)의 모든 행위는 접속기록 대상이 아니다.** 가입·로그인·주문·결제·문의 등 고객이 자기 정보를 다루는 행위는 아무리 발생해도 Argus로 전송되지 않는다. 접속기록은 **취급자(A2~A5)가 타인의 개인정보를 처리한 기록**만을 의미한다.

> 구현 시 혼동하기 쉬운 지점. 플랫폼의 로깅 지점은 **관리자 UI에만** 심는다.

### 1-2. 액터 간 연결 구조

```
   ┌─────────────── 플랫폼 ───────────────┐      ┌──────── Argus ────────┐
   │                                      │      │                       │
   │  A1 고객 ──(정보 제공)──> [고객 DB]   │      │                       │
   │                             ▲        │      │                       │
   │  A2 CS 담당자 ──(조회/수정)─┤        │      │   A4 정보보호 담당자   │
   │  A3 운영 담당자 ─(조회/DL)──┘        │      │        │              │
   │            │                         │      │        │ 소명 요청     │
   │            └── 접속기록 생성 ─────────┼─API─>│        ▼              │
   │                                      │      │   A5 취급자(소명)     │
   └──────────────────────────────────────┘      └───────────────────────┘
                     ▲                                      │
                     └──────── 동일 인물 ────────────────────┘
```

**핵심**: A2·A3(플랫폼에서 일하는 취급자)과 A5(Argus에서 소명하는 취급자)는 **같은 사람**이다. 같은 인물이 플랫폼에서 업무를 보다가, Argus에서 그 행위에 대한 소명을 요구받는다. 이 동선이 두 시스템을 잇는 연결고리다.

## 8. 정보주체 식별값 마스킹 정책 (2026-09-21 확정)

### 8-1. 대상

접속기록의 `처리한 정보주체 정보` 필드에는 회원 테이블의 **내부 식별자(PK)**를 기록한다(예: `member_10293`). 이름·이메일 등은 직접 기록하지 않는다.

> **표기 규칙 (2026-09-23)**: 저장·전송 시에는 `subject_type=MEMBER` + `subject_ids=["10293"]`처럼 순수 식별자만 쓰고, `member_10293`은 **화면·보고서 표시 표기**다. 마스킹 표시는 `member_10***`. ([[DB스키마.md]] 2-1절)

> **이 내부 PK도 개인정보다.** PIPA §2 1호 나목은 "해당 정보만으로는 특정 개인을 알아볼 수 없더라도 **다른 정보와 쉽게 결합**하여 알아볼 수 있는 것"을 개인정보로 정의한다. 회원 테이블과 결합하면 즉시 식별되므로 결합 용이성이 인정되며, 따라서 마스킹 대상이다.

### 8-2. 정책

| 구분 | 정보보호 담당자 (A4) | 취급자 (A5) |
|---|---|---|
| 기본 표시 | 마스킹 (`member_10***`) | 마스킹 (`member_10***`) |
| 마스킹 해제 | **가능** (점검 업무상 필요) | **불가** |
| 해제 시 사유 입력 | **필수** | — |
| 해제 행위 로깅 | **Argus 접속기록에 `UNMASK`로 기록** | — |

**취급자에게 해제를 허용하지 않는 이유**: 본인이 과거에 처리했던 정보라 하더라도, 소명에 필요한 것은 행위 시각·수행업무·건수이지 대상 식별값이 아니다. "9/15 23시에 회원 40건 다운로드"만으로 대부분 소명이 가능하다. 반대로 해제를 허용하면 Argus가 취급자에게 개인정보를 재차 제공하는 결과가 되어 최소처리 원칙에 반한다.

**사유 입력을 요구하는 근거**: 안전조치기준 §12①("개인정보의 출력 시 용도를 특정하여야 하며, 용도에 따라 출력 항목을 최소화")의 취지를 화면 표시에 적용한 것.

> **보고서 export에도 적용 (2026-09-23)**: 화면에서만 마스킹하고 보고서 파일로는 그대로 빠져나가면 정책 전체가 무력화된다. 보고서도 기본 마스킹이며, 언마스킹 보고서는 사유 필수 (정책정의서 6-1절).

## 9. Argus 자체 접속기록 — 자기참조 구조

Argus는 `처리한 정보주체 정보`를 보유하므로 **그 자체가 개인정보처리시스템**이며, Argus를 사용하는 정보보호 담당자(A4)와 취급자(A5)도 **개인정보취급자**다. 따라서 Argus 내부 행위도 §8의 적용을 받는다.

| 행위 | 기록 여부 | 비고 |
|---|---|---|
| Argus 로그인 | ✅ `LOGIN` | |
| 탐지건 상세 조회 | ✅ `READ` | 마스킹 상태로 조회. **정보주체는 건수만 기록**(식별자 중복 축적 방지 — 정책정의서 6-3절) |
| **마스킹 해제** | ✅ `UNMASK` | **사유와 대상 탐지건 ID를 함께 기록 — 가장 민감한 행위** |
| 접속기록 검색·열람 | ✅ `READ` | 검색 조건은 키 이름만 기록 |
| 보고서 export | ✅ `EXPORT` | 언마스킹 보고서면 사유 함께 기록 |

**MVP 범위**: Argus 자체 접속기록을 **기록·보관까지만** 구현한다. 이 기록을 Argus 자신의 탐지 룰로 평가하는 것(= 점검자에 대한 점검)은 **확장 포인트**로 둔다.

> **"감시자는 누가 감시하는가(Quis custodiet ipsos custodes)"** — §8②는 개인정보처리자 일반에 적용되므로 논리적으로는 Argus 운영자도 자기 접속기록을 점검해야 한다. MVP에서 자동 점검까지 구현하지는 않되, 이 구조를 인지하고 기록 기반을 마련해두는 것 자체가 설계 완성도의 일부다. 포트폴리오 서술 시 활용 가치가 있는 지점.
